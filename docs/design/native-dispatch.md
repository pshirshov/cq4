# Native dispatch on Pi through the gated subagent extension

Status: design and probe, not implemented. First Task (75) of Idea 36 under Decision 13: *"when the gated subagent extension of https://github.com/7mind/ponygirls is available to the governing Pi session, a role is carried out through it; when it cannot be used, the host launches the child as a separate harness process as today."* This document records what the extension is, what a real Pi 1.0.0 process did with it, which guarantees of a host-launched child survive, what the operator has to decide, and the implementation steps. It changes no code. It is verified by reading it against the sources it cites; the probe it rests on is retained under [`docs/validation/native-dispatch-probe-20261008/`](../validation/native-dispatch-probe-20261008/README.md) ("the probe" below, with `pi-1.0.0/…` file names relative to it).

**The result in one paragraph.** The extension has no programmatic interface: its only entry points are eight tools registered in the governing Pi session and the `/agents` screen. A tool of *another* extension in the same Pi process can call them through Pi's `ctx.executeTool` (probed), so the CQ attached extension (`cq/pi-attached.mjs`) can start, watch and cancel children from inside a `cq_dispatch` call. The host process cannot. What the extension gives is a worktree per writer, per-child models, durable journalled children, interruption and recovery on session re-attach. What it cannot give is the part of a host-launched child that makes CQ's admission work: its children load no extensions, so they cannot call CQ's scoped tools (`search`, `read`, `usage`, `workspace`, the reviewer's `Check`); it returns a result as at most 8,000 characters of final text; it has no structured report, no CQ-grade usage record, no guardian semantics for grace and kill, and its worktrees are not host-owned. The design therefore recommends a narrow first increment: **native dispatch for the Worker role only (`Worker(Implement)`, including a correction round, which is an `Implement` request carrying `previous`), in an attached Pi governing session, with a result file in the workspace, host-side candidate adoption and capture, CQ's own checks, review and correction loop (the extension's gate not used), and the Reviewer, Explorer and Planner staying host-launched.** Everything beyond that, and several choices inside it, are the operator's and are listed in [open questions](#open-questions-for-the-operator). Nothing here has been run with a real model or with CQ in the loop ([not observed](#not-observed)).

## What the extension is

### Start: one model tool, no API

`P/index.ts` registers eight tools in the governing session — `spawn_agent`, `send_message`, `list_agents`, `read_agent`, `wait_agent`, `interrupt_agent`, `close_agent`, `manage_gate` — the `/agents` command, and handlers for `session_start`, `before_agent_start`, `input`, `turn_end` and `session_shutdown`. The `Supervisor` is created inside the closure `bindingFor` and kept in a `Map` that the module does not export. There is **no exported function, no event-bus request, no socket and no command-line entry**. Who can start a child:

| Caller | Can it start a child? | Source |
| --- | --- | --- |
| The governing model, calling `spawn_agent` | yes | `P/index.ts` |
| The operator, in `/agents` (note, task, answer, interrupt, close, resume review) | yes, but not `spawn_agent`: the screen only addresses existing agents | `P/index.ts` `openAgents` |
| A tool of another extension in the same Pi process, through `ctx.executeTool("spawn_agent", …)` | **yes** (probed, scenario F): Pi passes an `ExtensionToolContext` with `executeTool` to a tool's `execute`, and the tools of the extension are `direct`, hence callable | Pi `types.d.ts` (`ExtensionToolContext.executeTool`, `ToolExposure`); `pi-1.0.0/scenario-F-tool-results.json` |
| A background event handler of another extension (`agent_settled`, a timer) | not shown: `executeTool` exists only in the context of a running tool call; whether it stays usable after the call returns is **not observed** | Pi `types.d.ts` |
| The CQ host (the JVM process) | **no**: it is not in the Pi process. It could only ask the CQ extension, which is. | — |
| A child | only when `nesting` is on (`maxDepth` 2): it then holds `spawn_agent`, `interrupt_agent`, `close_agent` | `P/src/policy.ts`, `P/src/worker.ts` |

`spawn_agent` parameters (`P/src/tools.ts` `spawnParameters`, `P/index.ts`): `task_name`, `message` (the task text, at most 64 KiB, `P/src/protocol.ts` `MAX_TEXT_BYTES`), `profile` (`reader` | `writer`), `isolation` (`none` | `worktree` | `sandbox`), `repo_id`, `base_commit`, `skills`/`all_skills`, `context_files`/`all_context_files`, `model` `{provider, id, thinkingLevel}` (needs an allowlist entry), and `gate` (below). It returns at once `{agentId, path, taskRunId, generation, profile, isolation, workdir, status}` (probe, scenario A). A child has **no cwd parameter and no system-prompt parameter**: its working directory is derived from the governing session (below), and its system prompt is Pi's default one (the child's session file in `pi-1.0.0/native-session-sandbox-writer.jsonl` begins with Pi's default preamble); its instructions are the task text plus the context files and skills the governing session passes (`P/src/instructions.ts`, snapshot at most 128 KiB, only files the governing session itself holds).

### Profiles, grants and policy

Two fixed profiles (`P/src/policy.ts`): `reader` = `read grep find ls`; `writer` = those plus `write edit bash`. Every child also holds `send_message`, `wait_agent`, `list_agents`, `read_agent` (`P/src/tools.ts` `CHILD_CONTROL_TOOLS`); a reviewer holds only the read tools plus `submit_gate_decision`. The probe saw exactly 8, 11 and 5 tools in the three requests (`pi-1.0.0/provider-requests.jsonl`, requests 3, 6, 23). The set of proxied tools is closed (`KNOWN_PROXY_TOOLS`): nothing else can be added to a child. Grants are the intersection root ∩ owner ∩ profile; a child is never less isolated than its owner; no manual approvals (`P/README.md`). The root authority is the user-owned file `$PI_CODING_AGENT_DIR/subagents-policy.json` (default `~/.pi/agent/`), read **once per session binding** (`loadPolicy` in `P/index.ts`): `maxDepth`, `nesting`, `repos[]`, `allowedModels` (default `[]`, so an explicit `model` is refused; `null` allows all), `gateBypassAllowed` (default false), `gateMaxRoundsCeiling` (default 3). An invalid file is an error. The file is the only configuration; `nix/hm/pi.nix` generates it declaratively.

### Isolation, worktrees and bases

`P/README.md` *Isolation*, `P/src/supervisor.ts` `bindWorkspace`, `P/src/workspace.ts`:

| `isolation` | Tool jobs | Workspace of a writer | Workspace of a reader |
| --- | --- | --- | --- |
| `worktree` (default) | on the host, as the user, with Pi's environment and network | a **detached Git worktree** of the governing checkout, created with `git worktree add --detach` at the `base_commit` (default the checkout's `HEAD`), at `<PI_CODING_AGENT_DIR>/subagents/<session id>/worktrees/wt-<repo label>-<12 hex of base>-<epoch ms>`, the same project-relative directory as the governing session's cwd | the governing cwd **in place** |
| `none` | on the host | the governing cwd, edited in place | in place |
| `sandbox` | bubblewrap view without network; needs `bwrap` with user namespaces (probe at first use, `SANDBOX_UNAVAILABLE` otherwise) | a worktree of a **registered** repository (`repo_id`, from the policy file) | the repository's read roots |

The worktree is created from the checkout that contains the governing session's cwd as recorded when the session was bound (`describeCheckout(governor().cwd)` in `spawn`); a dirty checkout without `base_commit` is refused (`CONFLICT`). Nothing is merged, committed or removed: *"A worktree writer's changes stay in its worktree"*; releasing a worktree needs an explicit user action. The probe shows the worktree location and base, that the governing checkout stayed clean, and that `git worktree list` of the governing checkout lists the extension's worktrees (so they are registered in the governing repository's `.git/worktrees`, **unlocked**): `pi-1.0.0/scenario-A-tool-results.json`, `marks.json` (`git-worktrees-after-A`). The reader's `workdir` in the probe is the governing checkout itself. Under host isolation *"`reader` is a tool list, not a boundary"* (`P/README.md`): its `read` reaches whatever the user can read, including `~/.pi/agent/auth.json`.

### Return of results

A child's result is **the final assistant text of its generation, cut to 8,000 characters** (`RESULT_TEXT_MAX` in `P/src/worker.ts` and `P/src/supervisor.ts`), returned by `read_agent view=result` as `{taskRunId, outcome, text, detail}`; `detail` carries an error text. Tool results of the extension are cut to 24,000 characters (`TOOL_RESULT_MAX`, `P/index.ts`). There is **no structured result, no schema parameter and no file convention**; files a writer wrote stay in its worktree. Outcomes: `succeeded`, `failed`, `interrupted`, `uncertain` (and, gated, `passed`, `review_limit_reached`, `gate_blocked`, `gate_error`, `candidate_superseded`, `gate_bypassed`; `P/src/types.ts`, `P/src/gate.ts`). *Completion is decided by `agent_settled` plus the last stop reason and the interrupt flag; an aborted or errored run is never success* (`P/src/worker.ts` header). Observed: `pi-1.0.0/scenario-A-tool-results.json`.

### Messages and questions

`send_message` modes `note`, `steer` (running generation only), `task` (a new task run); `request_reply` asks a question, whose text ends a parent's settlement wait with `reason: needs_response`; questions expire after 15 minutes (`QUESTION_TTL_MS`); messages are at most 64 KiB (`MESSAGE_TEXT_MAX`); `wait_agent` waits at most 300 s per call and is cancelled, with the children left running, by new user input or Escape (`P/index.ts`). Not run in the probe (read in source).

### Cancellation and deadlines

`interrupt_agent` requests interruption of the task run, its gate and its descendants and returns `accepted` plus the previous snapshot; *acceptance does not imply termination*, the stopped state is confirmed by the `settled` event (`P/src/supervisor.ts` `interruptSubtree`; probe scenario E: `interrupted`, usage 0/0). The interrupt request to the worker has a 15 s timeout (`INTERRUPT_TIMEOUT_MS`), `close_agent` joins for 15 s (`CLOSE_JOIN_TIMEOUT_MS`), the worker handshake has 30 s (`HANDSHAKE_TIMEOUT_MS`, `P/src/worker-launch.ts`), a proxied tool call 15 min (`TOOL_REQUEST_TIMEOUT_MS`, `P/src/worker.ts`), `bash` 120 s by default and **600 s at most** per command (`P/src/tools.ts`). Searching the sources for a heartbeat, a wall-clock or a run-time limit finds none: **a task run has no execution deadline.** Host-isolated tool jobs run in their own process group, killed when the job ends or is cancelled; *"a pi process that crashes cannot kill them … recovery treats their effects as uncertain"* (`P/docs/ponygirls-subagents.md`).

### Journal, recovery and fencing

`P/src/store.ts`, `P/src/protocol.ts`, `P/docs/ponygirls-subagents.md` *Root lifetime*, *Recovery diagnostics*: one supervisor per governing **session id**; durable state in `$PI_CODING_AGENT_DIR/subagents/<session id>/` (`journal.log` of checksummed length-framed records, `MANIFEST.json`, `checkpoints/`, `sessions/<agent id>/*.jsonl` the children's native Pi sessions, `worktrees/`, `worker-agent-dirs/`, `tmp/`, `root.lock/owner.json` with pid, boot id and process start time; `STORE_VERSION = 1`). A new **root epoch** fences old instances on every recovery; every IPC envelope is checked against the channel's `rootEpoch`, `agentId`, `workerInstanceId`, task-run id and generation. **Recovery happens only when the same session id is attached again** (`index.ts` `bindingFor` → `recover()`); each lost run gets exactly one terminal outcome (`interrupted` or `uncertain`), accepted-but-undispatched tasks keep their IDs for explicit resume, and *"the extension never auto-replays uncertain effects"*. Probe scenario R: after `SIGKILL` of Pi both workers were gone, and `pi --continue` produced `recovered root (settled 2, quarantined 0, queued 0)`, both agents `interrupted` with `usage {0, 0, cost: null, unknown: true}` and nothing replayed (`pi-1.0.0-recovery/`). A **new** Pi session (another session id) never touches the old root.

### Usage

`AgentView.usage = {inputTokens, outputTokens, cost: number | null, unknown: boolean}` per agent, cumulative (`P/src/supervisor.ts` `accountUsage`); the journal records one `usage.reported {agentId, taskRunId, generation, input, output, cost, unknown}` per generation (`pi-1.0.0/journal-excerpt.jsonl`). *"Unknown usage is flagged, never treated as zero"*; a lost generation reports `unknown: true`. **There are no cache, reasoning or total fields and no cost basis** in the extension's record. The children's own session files hold Pi's full per-message usage (`input output cacheRead cacheWrite reasoning totalTokens cost{…}`; `pi-1.0.0/native-session-sandbox-writer.jsonl`). Reviewer rows are separate agents with their own usage (probe scenario C). No budget is enforced (*"No token/cost budgets are enforced yet"*).

### The gate

`gate` on `spawn_agent` (`P/src/gate.ts` `GateSpecInput`): `model {provider, id}` (must be allowlisted, or the policy allowlist `null`), `thinkingLevel`, `prompt` (the frozen rubric), `maxRounds` (default 3; `null` unlimited if `gateMaxRoundsCeiling` is `null`), `checks[] {id, command, timeoutMs ≤ 600000}` (writers only; run by the controller **in the writer's workspace before every review**; a non-zero exit forbids approval), `promisedOutputs[]`. **It is optional per child and there is no way to force it**: omitted, the child is plain. The policy file can only forbid `bypass` and cap rounds. Terminal outcomes `passed | review_limit_reached | gate_blocked | gate_error | candidate_superseded | gate_bypassed`; `manage_gate` (governor only) resumes, retries, bypasses (if the policy allows) or sets limits. The candidate is **a fingerprint** (path, kind, mode, SHA-256 per changed file over the base commit), not a commit. Observed end to end in scenario C.

### The managed reviewer

`createManagedReviewer`, `startReviewerExecution` (`P/src/supervisor.ts`): a protected sibling agent `…/__gate` of profile `reader`, with the **gate's model** (not the writer's), the writer's workdir and read roots, **no skills or context files**, tools `read grep find ls submit_gate_decision`, a **fresh in-memory conversation per evaluation** ("never resumed", only a session file is kept for the transcript), started by a prompt that holds the frozen rubric, the original task, the writer's last response, the candidate id and fingerprint, and the controller's check output. It decides once through `submit_gate_decision` (schema version 1: `approve` / `revise` with blockers / `blocked`, findings with `evidenceRefs`). Probe scenario C.

### Notices

Terminal outcomes and messages addressed to the governing session are delivered once per journal position as a custom message `[subagents]\n<path> task <id> ended <outcome>` (`drainNotices`, `P/index.ts`): appended at `turn_end` while a turn runs, and on `input` queued with `deliverAs: "nextTurn"` while idle. **There is no timer and no wake-up**: in the probe, a child that finished while the session was idle produced no Pi event at all, and its notice reached the model only in the request of the next user prompt, as a user-role message (scenario B). With `--no-session` Pi skips `turn_end` handlers and the drain is inactive (`P/docs/ponygirls-subagents.md`).

### Flake outputs and how Pi loads it

The ponygirls flake (`flake.nix`, systems `x86_64-linux` and `aarch64-darwin`) exposes **no package and no overlay for the extension**. It reaches Pi in two ways: the check `checks.<system>.ponygirls-subagents` (copies the directory, links the SDK, `tsc`, `node --test tests/*.test.ts`) and the Home Manager module `homeManagerModules.dev-llm` (`nix/hm/dev-llm.nix` → `nix/hm/pi.nix`), whose Pi `settings.extensions` list contains `"${../pkg/pi-extensions/ponygirls-subagents}"`, i.e. the directory as a store path; Pi loads a directory with an `index.ts` as an extension. The `pi` wrapper sets `PI_SUBAGENTS_SDK_ROOT` (default) to `<pi derivation>/lib/node_modules/pi-monorepo` — without it `bindingFor` fails with `SANDBOX_UNAVAILABLE`. The extension needs `git` on `PATH`, Node 24 for the type-stripped `.ts` worker, and `bwrap` only for `sandbox`. CQ's own flake (`flake.nix`) has two inputs (nixpkgs, baboon) and no ponygirls input today.

## Guarantees of a host-launched child

For each guarantee: how native dispatch keeps it, what changes, or that it cannot be kept; the mechanism and the CQ source that would change. "Phase 1" is the recommended increment (Worker only). The host-launched path is `ChildRunner.run` (`server/src/main/scala/cq/server/ChildRunner.scala`) with `PiAdapter.launch` (`host/src/main/scala/cq/host/HarnessAdapter.scala`), `HarnessTools` and `JobSupervisor`.

| # | Guarantee today | Native dispatch | Mechanism and CQ source that changes |
| --- | --- | --- | --- |
| 1 | **An isolated, host-owned workspace per Worker**: `jobs.start(WorkspaceSpec(project, session, attempt, repository, base), command)` creates a locked detached worktree outside the checkout under the workspace root, records ownership and the observed `gitCommon`/`gitDirectory` (`docs/design/workspaces.md`, `GitWorkspaceRepository`) | **Changes; partly kept.** The extension creates the worktree, in its own root store, unlocked, registered in the governing repository, with no ownership record, no quarantine and no host removal. The base *can* be pinned: `base_commit` accepts any commit the governing repository resolves, which includes `refs/cq/candidates/*` commits and `candidates.fresh()` (`CandidateWorkspace`, same object store). Host ownership is restored by **adopting** the worktree: after `spawn_agent` returns `workdir`, the host verifies top-level, git common dir, git dir and `HEAD == base` (the checks `CandidateWorkspace.capture` already makes) and stores them as an `Open` `WorkspaceRecord` of a new native kind; a mismatch quarantines it. The host cannot lock or create it, so it never *owns* the creation; the extension never removes a worktree, so release is the host's (`git worktree remove`) after publication | New `NativeWorkspace` adoption in `host` (`WorkspaceService`/`GitWorkspaceRepository` gain `adopt`), `server/…/AttemptSettlement.release`, `server/…/CandidateWorkspace`; `docs/design/workspaces.md` |
| 2 | **Candidate capture by the host**: everything but `.work` committed by the host on the base, ref `refs/cq/candidates/<attempt>` (`CandidateWorkspace.capture`) | **Kept after adoption**, provided the child is `settled` (the host reads `read_agent status` first; a live writer could still change the tree). The worktree shares the object store, so the capture commit lands in the same repository. The `.work/evidence` convention works only when the child's `workdir` is the worktree root, i.e. the governing session's cwd is the checkout top-level (a condition of the [selection rule](#selection-rule)). The extension's gate fingerprint is not used (it is not a commit) | `AttemptSettlement.capture`, `CandidateWorkspace.capture` take the adopted record; no other change |
| 3 | **Per-role tool restrictions** (`HarnessTools.policy`): Pi Worker `read write edit bash` + CQ tools; Explorer/Planner/Reviewer no native tool, CQ tools only | **Changes.** The extension's `writer` = `read grep find ls write edit bash` plus the four control tools; its `reader` = `read grep find ls`. A native Worker is therefore close to a host Worker (adds `grep find ls`, `send_message`, `wait_agent`, `list_agents`, `read_agent`, which touch only the extension's own tree). A native *reader* is **wider** than any host-launched non-Worker, which has no native file tool at all: under `worktree` isolation it reads anything the user can read (`P/README.md`), `auth.json` included. Like Memory 33, role tool policy is policy, not isolation, and the extension adds nothing on the host-isolated modes | `HarnessTools` gains a `native` policy for the Worker role only (`HarnessToolPolicy` is pure data); a native reader is refused in phase 1 |
| 4 | **Scoped CQ reads** (`search`, `read`, `usage`, the local `workspace` tool, the reviewer's `Check`), each child with its own scoped token (`ChildRunner`: `SupervisorAuthority.harnessGrant`, `access.issue`) | **Cannot be kept.** The child loads no extension (`noExtensions: true` in `P/src/worker.ts`; *"Extensions are never loaded in children"*), its tool set is closed, and its `bash` could reach the MCP endpoint only by being handed a bearer token in task text — which the extension journals (`gate.registered` holds `taskText`, mailbox records hold message text) and the model sees. **Not an option.** Consequence: a native child gets the **complete input in its task text**: the host already assembles the complete `ChildExecutionInput` before launch (`InputAssembler`, delivered as `JobCommand.input`, the job bound 256 KiB in `JobSupervisor.scala`, the child input ≤ 192 KiB, `ChildContracts.MaxInputBytes`) and the role instructions (`invocation.system` ≤ 48 KiB); native text is **≤ 64 KiB in total** and the system prompt cannot be set. An input that does not fit is **not eligible** (a selection condition). The Worker loses on-demand reads of items and artifacts and `usage`; the Reviewer would lose `Check` ([review](#independent-review-of-a-natively-dispatched-reviewer)) | `ChildRunner` input path: a `NativePrompt` builder (new, host) that renders `ChildExecutionInput` and the role text as one message with a size check; nothing in `LocalAccess` changes |
| 5 | **Admission of the structured report**, with three separate facts: process success (`JobOutcome.observed(native).succeeded`), native completion (`usage.terminalSeen && !usage.nativeFailure`), and usage gaps (`CollectedUsage.gaps`), then `ChildContracts.report` on the final text (≤ 128 KiB, `ChildContracts.MaxResultBytes` in `host/src/main/scala/cq/host/ChildContracts.scala`) | **Changes.** *Report:* the final text is cut at 8,000 characters, below the 128 KiB bound and below a `Work` report of 16 members with 8,192-character summaries; it **cannot carry the report**. Phase 1 uses a **result file**: the task text tells the Worker to write the report JSON to `.work/report.json` in its workspace; the host reads it from the adopted worktree after `settled` and parses it with `ChildContracts.report` unchanged. *Facts:* there is no process exit status of the child (the worker is not the host's job). The extension's `taskOutcome` collapses process success and native completion into one: `succeeded` stands for both; `failed | interrupted | uncertain` are failures, `uncertain` maps to `JobOutcome` uncertain. Usage gaps stay a separate fact (`unknown`, and the gaps of the session-file parse in row 6). The three are kept distinct in the attempt's outcome gaps; the *meaning* of "process success" for a native child is the worker-less statement "the extension reported `succeeded` and `agent_settled` was seen" and the design says so in the gap text | `ChildRunner.run` splits at `settlement.launch`: the branch `NativeRun` replaces `launch → closeChecks → JobOutcome → collect`; `ChildContracts.report` is called on the file's content; `HarnessOutput` is not used |
| 6 | **Usage per attempt with gaps flagged** (`HarnessUsage.collect`: counters input/output/cacheRead/cacheWrite/reasoning with `Measurement`, `Money` with basis, `UsageCompleteness`, gaps; per-request positions) | **Changes; recoverable.** The extension's record (input, output, cost, `unknown`) is too coarse and has no basis. The child's native session file holds Pi's complete per-message usage (observed), so the host reads **that file** read-only (`sessions/<agent id>/*.jsonl` under the root store, path known from the `workdir`'s sibling layout and the journal) with a new parser that emits the same `CollectedMeter`s as `HarnessUsage.pi`; `unknown: true` from the extension becomes a gap `A request was interrupted before its usage was reported`; a session file that is missing or unparsable is `UsageCompleteness.Unavailable` with a gap, never zero. The governing session's own usage (`cq/piUsage`, `AttachedUsage`) does not include the children's requests (separate worker processes, own sessions) — no double counting. A real provider's usage was not observed | New `NativePiUsage` beside `host/…/HarnessUsage.scala`; `AttemptSettlement.collect`; `Attempt.collector` names `pi-native/ponygirls-subagents@<revision>` |
| 7 | **Cancellation**: `Cancel` stops the whole unit; guardian: SIGTERM, `graceMillis`, repeated kill to `killMillis`, `Uncertain` when termination is unproven (`docs/design/process-guardian.md`) | **Changes.** `interrupt_agent` (then, for a child that will not be used again, `close_agent`) returns *accepted*, not stopped; the host then polls `read_agent status` until `observed: settled` and records `Uncertain` when the extension reports `uncertain` or the poll runs past the bound. There is no SIGTERM/grace/kill ladder for the worker, and a host-isolated `bash` of a dying Pi cannot be killed (*"recovery treats their effects as uncertain"*) | `DispatchController` cancel path → `NativeCancel` (executeTool `interrupt_agent` inside a `cq_dispatch Cancel` call); `JobSupervisor` records the native job as `Stopping` until settled |
| 8 | **Recovery**: durable `JobRepository` records, `cq job upload --session`, startup `WorkspaceCleanup.recover`, `Uncertain` for jobs without confirmed termination | **Changes.** The extension recovers only on re-attach of the same Pi session id. The host cannot rely on it: if the operator starts a new session, the old root stays unsettled. The host therefore records each native attempt as a durable job (extension root path, agent id, task-run id, worktree, git dirs) and its startup recovery **reads the extension's journal read-only** (`journal.log`, `STORE_VERSION 1`, framed records) to settle: a `task.terminal` found → the result is read as for a live attempt; none → the attempt is `Uncertain`, its workspace quarantined and retained; nothing is replayed. This ties CQ to a non-public file format | `JobRepository` gains a native record; `WorkspaceCleanup.recover`, `SessionDelivery.interrupt`; `docs/design/local-jobs.md`, `workspaces.md` |
| 9 | **Unit, seat and abstention semantics**: `AgentsAction.Resolve` → seats; `UnitProgress` decides what is launched; a candidate **abstains** when no model ran for a reason that is none of the work's (`AbstentionClassifier`, reasons `Unconfigured Launch Credential Quota RateLimit Unavailable`); everything else is a seat failure | **Kept for units and seats**, native only changes *how* one candidate runs. **Abstention: partly.** A refusal that arrives before the extension accepted the spawn (`POLICY_DENIED` model not allowlisted, `SANDBOX_UNAVAILABLE`, `WORKSPACE_UNAVAILABLE`, `CONFLICT` dirty checkout, `CAPACITY_EXCEEDED`, `MODEL_UNAVAILABLE`, `INVALID`) means no model ran: the host **falls back to a host-launched child for the same candidate** ([selection rule](#selection-rule)), and records the refusal in the attempt's gap text. A failure of an accepted child is a seat failure; the classifier's patterns were captured from `--mode json` streams and cover no native text, so a provider refusal inside a native child is **not** recognised as an abstention in phase 1 (what the child's `detail` looks like for a real provider refusal is not observed) | `DispatchUnits`, `UnitProgress` (no change), `AbstentionClassifier` (no change in phase 1), new `NativeSelection` |
| 10 | **Route fields on the attempt** (`Attempt.harness/provider/model/effort/collector`; the host verifies the profile with `SupervisorConfig.verifyProfile` before launch) | **Kept, with a check.** `spawn_agent.model = {provider, id, thinkingLevel}` takes the route's provider and model; `effort` maps to `thinkingLevel` (same Pi level names, `AgentResolution.efforts`); the reply's `list_agents.model` (`provider/id`, observed `openai/gpt-5.5`) is compared with the route and a mismatch fails the attempt. Two limits: the model must be in the policy allowlist (or the allowlist `null`), a **static** file loaded at session binding, while the agent configuration is read at each unit start; and a model provided only by a Pi *extension* is unavailable to children (`MODEL_UNAVAILABLE`; `P/docs/ponygirls-subagents.md`), so a route whose settings entry has `providerExtensions` (`HarnessProfile`) is not eligible. `PiAdapter.AmbiguousModel` (a model name Pi would read a thinking level from) is checked by the selection too, because a colon in `id` was not probed | `HarnessProfile`, `NativeSelection`, `DispatchUnits`; `Attempt` unchanged except the `collector` string |

Fixed by the extension and different from a host-launched Worker, to be recorded in `docs/design/local-dispatch.md` when implemented: `bash` is capped at 600 s per command (a host-launched Pi Worker has no such cap in `PiAdapter`; a long focused test run may need to be split); the Worker's system prompt is Pi's default and CQ's role instructions are task text; the task text is ≤ 64 KiB; and `maxAgentsCreated` is **32 agents per governing session** (`P/src/scheduler.ts` `DEFAULT_LIMITS`), while an attached session starts an unbounded number of children over its lifetime (`docs/design/local-dispatch.md`) — the 33rd native agent is refused with `CAPACITY_EXCEEDED` and falls back to the host (a later Pi session starts a fresh root).

## Independent review of a natively dispatched Reviewer

Plan and Candidate review today (`ChildRunner`, `docs/design/reviewer-checks.md`): a **separate process** with a fresh session, its own scoped domain and local tokens, read-only tool policy, optional `Check` of declared checks through the local `workspace` tool, and a route that the agent configuration may place on **another harness** than the Governor's and the Worker's (`fallback` over the other harnesses' frontier tiers by default, `AgentStarter`).

| Point | Native Reviewer (a `reader` child, or the extension's gate reviewer) | Mechanism and source | Weaker than host-launched? |
| --- | --- | --- | --- |
| Model | Any model that Pi's built-in providers or `models.json` supply and the policy allows (`allowedModels`); may differ from the Governor's and the Worker's. For a `reader` child: `spawn_agent.model`; for the gate reviewer: `gate.model`. **Always a Pi provider**: the extension cannot run Claude Code or Codex. | `P/index.ts`, `P/src/gate.ts` (`gate.model` allowlist), `P/src/supervisor.ts` `resolveChildModel` | **Yes**: no reviewer on another *harness*. The default starter configuration's "other harnesses first" cannot be honoured; only a different provider/model on Pi |
| Fresh context | Yes: a child sees only its task text plus passed context files; the gate reviewer's conversation is in-memory and fresh per evaluation. It sees the Governor's conversation never | `P/src/supervisor.ts` `startReviewerExecution`; `P/README.md` | No |
| Credentials | The extension has **no per-child credentials**: every worker opens the host's `auth.json` live (`PI_SUBAGENTS_HOST_AGENT_DIR`; *"auth.json is never copied"*), and under `worktree` isolation a reader can `read` that very file. There are no CQ scoped tokens: no domain read, no claim awareness, and no way to be denied individually | `P/README.md` *Configure*, `P/docs/ponygirls-subagents.md` *Genuine limitations* | **Yes**: host-launched reviewers get a token scoped to read-only domain tools and a `workspace` capability that ends with the attempt (`LocalAccess`) |
| Tools | `read grep find ls` plus the gate decision tool; no `search/read/usage` of CQ, **no `Check`**. A natively dispatched Candidate Reviewer cannot request declared checks; it may only be shown the output of checks the host (or the gate) ran beforehand | `P/src/policy.ts`, `ChildRunner.workspace` (`WorkspaceCommand.Check`), `ReviewerChecks` | **Yes**: reviewer-chosen checks are lost |
| Output | The gate reviewer's decision is `submit_gate_decision` (approve/revise/blocked with findings); a `reader` child returns ≤ 8,000 characters. Neither is `ChildReport.Review` (per-member verdicts, `next`, evidence the server admits); a `Review` report cannot be carried in 8,000 characters and the reader cannot write a result file | `P/src/gate.ts`, `ChildContracts.report` | **Yes**: no admitted structured review |
| Independence of the governing session | The reviewer is a child of the **same supervisor in the same Pi process**, with the same auth store, started and ended by tool calls of the governing model; the governing model can `manage_gate bypass` (if the policy allows), `interrupt`, `close` or re-ask. The reviewer's task text is written by the Governor's `Start`; the extension's candidate is a fingerprint, not a captured commit. Its decision is *"a recorded model judgment about the submitted evidence, not proof of correctness"* | `P/src/supervisor.ts` `manageGate`, `P/src/gate.ts` | **Yes**: the host-launched reviewer's input is assembled by the host from admitted artifacts, reads the host-captured candidate and publishes under its own attempt |
| Reproducibility | The reviewer's view is the live worktree (readers read in place under `worktree` isolation); external writers during review are only detected by fingerprint comparison, not prevented | `P/docs/ponygirls-subagents.md` | **Yes**: host-launched candidate reviewers read a workspace at the captured commit |

**Assessment.** A natively dispatched Reviewer is a weaker review in every row but "fresh context" and "model may differ". It would be acceptable only as an additional, cheap *pre-review* inside a Worker's own loop ([alternative C](#who-owns-checks-review-and-repair)), never as the review that Integration requires. The design therefore keeps **every Reviewer role (Plan and Candidate) host-launched** and makes native review an [open question](#open-questions-for-the-operator) (question 7) rather than a default.

## Dispatch limits

`DispatchRequest.limits` is `HostLimits {startupMillis, heartbeatMillis, graceMillis, killMillis, retainedOutputBytes}` (`models/cq-api.baboon`); `SupervisorConfig.limits` turns it into `ExecutionLimits` with **no execution deadline** (`None`); the guardian and `JobSupervisor` own drainage, cancellation and termination (`docs/design/process-guardian.md`, *Deadlines that stay and deadlines that went*). For a child of the extension:

| Limit | Host-launched | Native child: what observes or enforces it |
| --- | --- | --- |
| `startupMillis` | the guardian's exec acknowledgement and the guardian's exit (`guardian.c`, `GuardianDriver.monitor`) | **The extension enforces a fixed 30 s worker handshake** (`P/src/worker-launch.ts` `HANDSHAKE_TIMEOUT_MS`) and fails `spawn_agent` when it runs out. CQ's value cannot be passed. The host observes startup as the time from its `spawn_agent` call to the reply and, when that exceeds `startupMillis`, does not fail or replace the attempt but reconciles it with the extension (launch state unknown, see the selection rule); a value below 30 s therefore only bounds the host's wait, not the extension's. A spawn that is refused or errors is synchronous (an `isError` tool result) |
| `heartbeatMillis` | the guardian detects a frozen or dead **owner** | **Nothing observes a frozen worker or a frozen Pi.** The extension has no heartbeat. A dead Pi is visible (its workers died with it, probe R; the attached connection closes), a frozen one is not. The host can supply `DispatchStatus.quietMillis` from `lastActivityAt` of `list_agents` (observed field), which, as today, is evidence for a human and not a trigger |
| `graceMillis` | time between SIGTERM and kill | **Nothing.** The extension's interrupt is a request with a fixed 15 s timeout (`INTERRUPT_TIMEOUT_MS`); the host's own bound for confirmation of `settled` is the only grace and is `graceMillis + killMillis` of the request (a CQ-side poll limit; it cannot kill) |
| `killMillis` | repeated kill until reaped, then `Uncertain` | **Nothing.** The extension kills a host `bash` process group when its job ends or is cancelled and the worker with `dispose`; there is no kill ladder. A child that does not settle by the host's bound is `Uncertain` and its workspace stays quarantined |
| `retainedOutputBytes` | bounds what the host *publishes* of stdout/stderr; the 1 GiB disk-safety ceiling stops a runaway writer (`ExecutionLimits.OutputCeilingBytes`) | **Nothing is streamed**; there is no stdout. The extension truncates its own returns (8,000 characters of result, 24,000 of tool result). The host applies `retainedOutputBytes` to the one thing it publishes, the child's native session file, with the same head/tail cut and marker as `NativeTranscript.retained`. **No disk-safety ceiling exists** for the session file, a worktree or `bash` output |
| Execution deadline | none | **None imposed by the extension**: no wall-clock, heartbeat or run-time limit was found in the source. What does bound things are per-operation limits (a tool request 15 min, `bash` 600 s per command, a question 15 min, one `wait_agent` 300 s). A native child therefore stays **without an execution deadline**, as a host-launched one, and the "residual: nothing bounds a hung child" of `process-guardian.md` applies unchanged |

The 4-active-children bound and the claim lease (`ClaimRenewal`) are host-side and unchanged; the extension's own `maxRunnable` 4 and `maxResidentWorkers` 8 (`P/src/scheduler.ts`) are consistent with the first.

## Selection rule

Decision 13 as conditions a test can assert. Let a *candidate* be one launch of a unit (`UnitProgress`). The attempt of the candidate runs **through the extension if and only if ALL of the following hold**; otherwise the host launches the process as today. The rule is a pure function `NativeSelection.choose(context, candidate): Native | HostLaunch(reason)` over data the host already holds or is told, so that `*Dummy` suites assert it row by row.

| # | Condition | Where it is read |
| --- | --- | --- |
| N1 | The governing harness is **Pi** and the governing session is **attached** (an interactive Pi session with `cq/pi-attached.mjs` loaded). A *managed* Governor (`cq run`) is host-launched by `PiAdapter` with `--no-extensions` and an environment filtered by `HarnessEnvironment.isolated` (no `PI_SUBAGENTS_SDK_ROOT`), so it never has the extension; phase 1 does not change that | session kind of the activation (`AttachedWorkflow`, `SupervisorConfig`) |
| N2 | The candidate's route (`ModelRoute.harness`) is **Pi**. A route naming Claude or Codex is host-launched (Decision 13: "explicitly configured for a role") | `ResolvedAssignment` of the unit (`DispatchUnits`) |
| N3 | The work is in the native-eligible set: phase 1 = `Worker(Implement)` (`DispatchWork`, `WorkerMode` in `models/cq-api.baboon` has `Implement`, `Probe`, `ResolveConflict`; a correction round is an `Implement` request whose `previous` is the earlier result; no `Correct` mode exists and none is proposed); every Reviewer, Explorer, Planner, `Worker(ResolveConflict)` (needs the merge report and `MergePreparation`) and the Governor's own work are host-launched | `DispatchWork` of the request |
| N4 | **The extension is available to this session**, determined by the CQ attached extension at attach and reported to the host in its handshake: (a) `pi.getAllTools()` contains `spawn_agent`, `read_agent`, `wait_agent`, `list_agents` and `interrupt_agent`, each with `sourceInfo.path` inside the **pinned extension directory** (the store path of the flake input, [step 1](#implementation-steps)) or, if none is pinned, a directory whose `package.json` has `name: "ponygirls-subagents"` and a `version` the host lists; (b) `typeof ctx.executeTool === "function"` in the `cq_dispatch` tool context; (c) `PI_SUBAGENTS_SDK_ROOT` is set in Pi's environment and equals the root of the running Pi's installation; (d) the running Pi version is one the host lists as verified for native dispatch ([question 4](#open-questions-for-the-operator)); (e) `git` is on `PATH`. A tool of that name from another path is not the extension | new capability record in `cq/pi-attached.mjs` (`PiAssets`), received by `AttachedProgram` |
| N5 | The route is **expressible**: no `providerExtensions` in the settings entry; `PiAdapter.AmbiguousModel` does not apply; the model is accepted by the extension's policy (allowlist `null`, or listing `provider/id`) — the host learns the policy by a probe call at attach, or learns it from the first refusal | `HarnessProfile`, capability record |
| N6 | The **workspace is expressible**: the Pi session's cwd is the **top-level of `config.run.repository`'s checkout** (so the child's `workdir` is the worktree root and `.work/evidence` works); the base commit resolves in that repository (`candidates.fresh()`, a captured candidate, or the combination base); the checkout may be dirty because the host always passes `base_commit` | `SupervisorConfig.run.repository`, `CandidateWorkspace.verifyBase`, capability record (cwd) |
| N7 | The assembled input fits: the rendered task text (role instructions + `ChildExecutionInput` + the result-file instruction) is ≤ **60 KiB** (below the extension's 64 KiB with margin for the task header, `taskHeader` in `P/src/protocol.ts`) | `NativePrompt` after `InputAssembler` |
| N8 | The operator has enabled it for this role key of the agent configuration, if [question 1](#open-questions-for-the-operator) is decided as opt-in; otherwise this row is true | `AgentsAction.Resolve` reply (`RoleKey`) |
| N9 | The session has not exhausted the extension's capacity (fewer than 32 agents created this session, as counted by the host from its own native attempts) and the capability record is not marked `broken` by an earlier failure of the same kind | host state |

**When the extension is present but refuses or fails.** The host sends `spawn_agent` and waits for the reply:

- **Refusal or error before the spawn is accepted** (an `isError` reply with one of `POLICY_DENIED`, `SANDBOX_UNAVAILABLE`, `WORKSPACE_UNAVAILABLE`, `CONFLICT`, `CAPACITY_EXCEEDED`, `MODEL_UNAVAILABLE`, `INVALID`, `PAYLOAD_TOO_LARGE`): the reply is proof that no model ran for this candidate. The host records the code and text in the attempt's gaps, marks the capability for that cause (`policy`, `capacity`, `workspace`) so that N5/N9 do not retry it in this session, and **launches the same candidate as a host-launched child under a new attempt** (the first attempt ends as a launch refusal, not as an abstention of the seat; `UnitProgress` is not told). Each such fallback leaves the adopted worktree, if any, to be removed.
- **No reply within `startupMillis`, or a lost or malformed reply** is *not* proof: the launch state is unknown and a native writer may already be running. The host does **not** replace the attempt automatically. It first reconciles: it asks the extension (`list_agents` / `read_agent` for the `task_name` it chose, which carries the attempt id) and, if the extension answers, treats a found agent as accepted (next bullet) and a definitively absent one as a refusal. If the extension cannot answer, the attempt is `Uncertain` (its workspace quarantined and the extension's journal consulted as in row 8); no host-launched replacement is started until the operator or recovery settles it. Fixture: a delayed reply that arrives after `startupMillis` and a lost reply (see implementation step 7).
- **After acceptance** (the reply carried an `agentId`): everything that follows is the candidate's own result. `failed`, `interrupted`, `uncertain`, a missing or invalid result file, or a worktree that fails adoption is a **seat failure** exactly as for a host-launched child; there is **no automatic re-run elsewhere** (the effects of a possibly started writer are uncertain, and the extension itself never auto-replays uncertain effects).
- **The extension disappears mid-run** (the Pi session ends, the connection closes): the attempt is `Uncertain` and recovered from the extension's journal as in [row 8](#guarantees-of-a-host-launched-child).

Testable consequences: with all of N1 to N9 true the first launch of an eligible Worker candidate is a `spawn_agent` call and no `JobCommand` is created; with any false, the attempt is the unchanged host-launched one and its recorded route and `collector` are unchanged; a stub extension that refuses with each listed code yields exactly one host-launched replacement attempt and no second native call; a stub that accepts and then reports `failed` yields a failed seat and no replacement.

## Who owns checks, review and repair

Three alternatives for a natively dispatched Worker. Integration preconditions are those of `IntegrationService.reserve` (`docs/design/git-integration.md`): *"accepted worker/reviewer admissions, exact candidate, applicable validation"*, and a self-reviewed integration additionally needs a configured check or the operator's exemption.

| | A. **CQ owns all** (recommended) | B. **The extension's gate owns all** | C. **Gate as a pre-review loop, CQ re-does everything** |
| --- | --- | --- | --- |
| Checks | the host's configured checks on the captured candidate, `HostValidation` (`AttemptSettlement.checked`), as for any Worker | the gate's `checks[]` (arbitrary commands in the writer's worktree, host-isolated, which "can modify sources") | gate `checks[]` for the loop, **and** the host's configured checks on the captured candidate |
| Review | a host-launched Reviewer (Candidate) on another harness, admitted by the server | the extension's reviewer, its decision recorded as `passed` | gate reviewer inside the loop, **and** the host-launched Candidate Reviewer |
| Repair rounds | the Governor's `Start` with `previous` (Correction) after a `ChangesRequested` verdict: a new Worker attempt | the gate's up to `maxRounds` automatic repairs inside one child | gate rounds first (cheap model), then CQ's correction loop |
| Integration preconditions | **unchanged and met**: admitted worker and reviewer results, host-captured candidate, host checks `Passed` | **not met**: the server admits no `gate passed` as a review or as validation; `IntegrationService.reserve` would refuse. Meeting them means changing server admission to accept a model verdict from a process whose input and tools the host did not control, which weakens the very property reviews exist for | **unchanged and met** (the gate is only evidence the Worker's loop used, not trusted by the server) |
| Cost | one Worker round plus CQ's loop | cheapest | the most: gate reviews plus CQ's; duplicate checks |
| Consequence | native adds only the worktree/model facility; `docs/design/reviewer-checks.md` and `git-integration.md` need no change | CQ would give up independent review for natively dispatched Workers; **not recommended** | adds a rubric and check list the host must assemble for the gate; two review verdicts to reconcile; gate fixed by `gateMaxRoundsCeiling` |

The recommendation is **A**; **C** can be added later as an optimisation without changing integration. **B** is listed so that the operator can reject it explicitly ([question 6](#open-questions-for-the-operator)). In all alternatives the gate is **switched off by omission**: `gate` is a per-spawn parameter and the policy file cannot force it, so a Worker spawned without `gate` has no gate (probe scenario A).

## The six tensions of Idea 36

| Tension | Resolution in this design |
| --- | --- |
| The extension's children load no extensions, so they cannot call CQ's scoped tools | Resolved by **prompt-complete input** and a **result file**, and by restricting native dispatch to the Worker, whose host-assembled input is already complete (rows 4 and 5). The Reviewer, which needs `Check`, stays host-launched. Not resolvable inside the extension; an upstream change is [question 3](#open-questions-for-the-operator) |
| The extension's worktree is not the host's workspace and the host must capture the candidate | Resolved by **adoption** of the worktree and `base_commit` pinned by the host (rows 1 and 2). Residual: not locked, registered in the governing repository, release by the host |
| The gate duplicates CQ's checks, review and correction loop | Resolved by **not using the gate** in phase 1 (alternative A); C is optional later |
| A reviewer that is a subagent of the Governor's own session is less independent than a separate process on another harness | **Not resolved; avoided.** All Reviewers stay host-launched ([assessment](#independent-review-of-a-natively-dispatched-reviewer)) |
| A notice to an idle governing session waits for the next user turn, which matters to the auto-driver | Observed (probe B): the extension's notices never wake an idle session. The design does **not** use them. The host learns the end of a native attempt itself (by polling the extension's journal or `list_agents` inside its own `Status` calls) and ends the attempt on its side; the attached extension's existing waiter (`cq wait` → `sendMessage … triggerTurn: true`, [Pi 1.0.0 record](../validation/pi-1.0.0-20261006.md)) wakes the idle session, and the auto-driver (`docs/auto-driver.md`) sees an ordinary attempt end. The extension's own `[subagents]` notices still appear at the next turn as duplicate information; they cannot be switched off (`drainNotices` is unconditional) |
| The extension's sandbox mode needs bubblewrap with user namespaces, which may not work inside the operator's sandboxed launch | Phase 1 uses **`worktree` isolation only**. `sandbox` also needs a static registered repository per project in the policy file, which cannot follow CQ's per-attempt bases. That bubblewrap works in this worker's launch (probe D) says nothing about the operator's launch; it stays [open question 9](#open-questions-for-the-operator) and is not required by the design |
