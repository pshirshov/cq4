# Auto-driver core

The driver core is the harness-neutral part of the operator-toggled auto-driver. It decides, per harness session, whether the session should keep advancing a frozen workset, hands the session the exact advance invocation to submit, and confines every ledger write of a driven session to the cycle it belongs to. The shared Claude Code/Codex hook commands and the Pi extension are thin callers; none of them builds a directive or holds driver state. The harness sections below describe those callers; the operator documentation is [auto-driver.md](../auto-driver.md).

The core is `DriverService` (state machine), `DriverBoundary` (write-time admission) and `DriverPolicy` (pure decisions and texts) in `core`, with `DriverRegistry` holding the state. `LedgerMutation` calls the boundary for every ledger write. `DriverEntry`, `DriverArguments` and `DriverSessionClient` in `host` are the callers' typed entry points.

## State and its lifetime

The server holds one record per project, harness and session key: the state (`Binding`, `On` or `Off`), the bound attached session, the stored workset ID if one was used, the frozen targets and through phase, the latest cycle, the number of directives issued and the last stop reason.

The records live in the server process, not in PostgreSQL. A status read (`Status` from a control origin or from an attached session) reads them directly and takes no project transaction, so status-line polling never waits for a ledger write; every other driver operation runs inside one project transaction. They persist across the turns of a harness session, but a server restart turns every driver off: the next continuation query then returns stop with reason `Off` and the session's writes behave as they do without a driver. No ledger schema change accompanies the driver.

A project holds at most 64 records. At capacity, drive-start displaces the least recently touched record that is off or has been silent for eight hours; if every record is live, drive-start fails with `Limit`. Silence is measured from the record's last driver operation or attributed write, so a driver that is on but idle for eight hours (a session left open overnight, a child that runs longer) is displaced like an abandoned one. Its record is removed without a stop reason: the session's next continuation query returns `Off`, and from the moment of displacement its writes are no longer confined. Displacement happens only at capacity.

## Session trust

State-changing entry points are keyed by the session key the harness supplies: the hook-stdin `session_id` for Claude Code and Codex, and the extension's own session identity for Pi. The key is validated for shape (1–200 characters of letters, digits, `.`, `_`, `:` or `-`) and is otherwise trusted, not authenticated (Decision 2). A missing or malformed key, an unknown harness identifier and an unknown hook event are rejected with `Invalid` and change no state; no call falls back to a default session.

Two sessions that each supply their own key never change each other's record. A same-user process that supplies another session's key does change that session's record. This is the documented limit of the isolation guarantee and a contract test asserts it.

The same limit applies to the driven model itself. The hook commands run in the harness environment, which carries the operator token file, and the harness exposes the session's own key to the model's shell tool. A model with shell access can therefore run `cq hook <harness> UserPromptSubmit` with a drive or park prompt on stdin, or use the token file directly, and start, park or re-scope its own driver. The control surface is separated from the model-facing tools, not from a model that can execute commands as the operator.

Authority separates the two surfaces:

- **Control** (`DriverRequest.Control`: `Start`, `Park`, `Continue`, `Status`) requires the operator credential, which only the CQ hook commands and the Pi extension's attached host hold. A governor credential is `Denied`. The declared origin is checked: Pi drives from `Extension`, the other harnesses from hooks; `Start` and `Park` belong to `UserPromptSubmit`, `Continue` to `Stop`, and `Status` to any origin including `StatusLine`.
- **Session** (`DriverRequest.Session`) runs under an attached session's own governor credential. The model-facing `session` tool exposes only `Bind` (gated by the hook-minted token) and `Driver` (read-only status). Neither starts nor parks a driver. Activation, lineage registration and the read of what may be settled under a pending start directive (`DriverSession.Settleable`) are called by the attached host, not offered as tools. Cycle-attributed changes (`DriverSession.Change`) are a server operation that no CQ client calls yet (see [Cycle lineage](#cycle-lineage)).

No MCP domain tool carries a driver command.

## Drive-start, binding and park

Drive-start takes the key and either a stored workset ID or inline non-empty targets plus a through phase. It evaluates the workset again and returns the same preview `Command.Workset` `Preview` returns. Empty targets, an unknown item, a missing workset, a cross-project target and an invalid key are rejected and leave the driver off. `DriverArguments` parses the command text `<target IDs> through=<phase>` or `workset=<id>` and rejects unknown item references and unknown phases before the server is called.

The targets and the phase are frozen. Drive-start on a driver that is binding or on fails with `Conflict`; changing targets or phase requires parking and driving again.

A driver turns on only when it is bound to exactly one CQ attached session:

- **Claude Code and Codex:** drive-start leaves the driver `Binding` and mints a single-use bind token valid for ten minutes. The token appears only in that drive-start reply, which the hook returns as context for its own session. `Bind` from an attached session presents the token and binds the caller. An unknown, already used or expired token is `Denied`.
- **Pi:** the extension's attached host supplies its attached session at drive-start, so the driver is on immediately and no token is minted.

An attached session is bound to at most one driver, and the binding follows the key that drives now. A harness can issue a new session key while its attached host process lives on; the drive command then arrives under the new key while the attached session is still bound to the old key's driver. Binding it to the new driver (`Bind`, or a Pi drive-start) parks the old key's driver with reason `Parked` and the detail `Its attached session was bound to the CQ driver of session <new key>`, ends its cycle, and turns the new driver on.

If no session binds, the driver never turns on, and the next continuation query stops it with reason `NotBound`, whose detail names it as a failure.

Park turns the driver off, ends any pending or active cycle (its tokens stop working) and releases the binding. The record keeps its frozen workset and a `Parked` stop reason for the status indicator.

## Continuation query

The query takes the key and returns either a directive (`Continue`) or `Stop`.

| Driver state | Result |
| --- | --- |
| No record, or off | `Stop` with reason `Off`; nothing changes |
| Off after a stop no control reply has carried yet | `Stop` with that stop reason, once |
| Binding | `Stop` with `NotBound`; the driver turns off |
| On, cycle issued but not started | `Stop` with `Failure` (directive not started) |
| On, cycle started and its run still active | `Continue` with a resume directive |
| On, cycle started, nothing in flight, work resting on the session | `Continue` with one resume directive for that work, then `Stop` with `Failure` |
| On, no cycle, or the cycle's run is over | a new cycle decision, below |

A cycle's run is still active while a lineage member registered under it is **in flight**: work the attached host is carrying out, which finishes without the session. That is a child attempt that has not reached a terminal phase, an integration that is `Preparing` or `Running`, or a combination that is `Preparing`. Each stop of the session then yields a resume directive.

A member **rests** when it is unsettled but only the session can move it: an integration that is `Ready` (prepared, not applied) or `Pending` (awaiting reconciliation), and a combination whose publication is pending. Resting work does not hold a cycle open indefinitely. When nothing is in flight and some member rests, the query issues one resume directive, so the session can resolve that work inside the cycle that owns it. If the next query finds the same members still resting, the driver stops with `Failure` and the detail `cycle N is held by integration <id>, which only the session can resolve, and a resume directive did not resolve it`. A member the session resumed (it is in flight again) and that comes to rest again earns a new resume directive. A member that reaches a terminal phase is settled and holds nothing.

`Integrate` resumes its integration. The integration is `Running` when the dispatch tool returns, and the attached host reports it as in flight before it returns that reply (see [Cycle lineage](#cycle-lineage)). A session that calls `Integrate` as the last action of its turn therefore gets a resume directive from the query that follows, and from every later query while the integration is still being applied, however long that takes. The stop above is left for an integration that was not applied at all, or that came back to `Pending` and was not applied again.

For a new cycle the query first computes the advanceable set from the frozen targets with `WorksetPlanner.evaluate`. This issue-time snapshot is the only input to the readiness decision, and it is stored with the cycle it creates:

- **Continue:** some advanceable item is ready and is not waiting for a person. The query creates a pending cycle holding a single-use start token, exactly the frozen targets as roots, the frozen phase and the snapshot.
- **Continue after failed attempts:** the snapshot equals the previous cycle's, some item is ready, and the previous cycle left at least one input retryable (see [Attempt outcomes](#attempt-outcomes)). The reply carries the message `CQ driver: cycle 1 changed nothing, and its work on G1 failed without a result; the same input is offered again with the fault`, and the new cycle stores those failed attempts as `retried`. This case is decided before `UserInputRequired`.
- **`UserInputRequired`:** no other item is ready, or the previous cycle changed nothing and left no input retryable, and an open Question or a requested Operator Action is itself ready or blocks an advanceable item. The driver never answers a question or infers an approval.
- **`Quiescent`:** nothing is ready, or the snapshot equals the previous cycle's in members, context and readiness and that cycle left no input retryable, and nothing waits for a person. Either detail names the prerequisites outside the advanceable set that block a member, with the members they block: `No item of the advanceable set is ready to advance; blocked from outside the set: D7 blocks T5,T6`, or `The previous cycle changed nothing in the advanceable set, its context or its readiness; blocked from outside the set: D7 blocks T5`. The second form is the stop of a drive whose root stays ready, such as a Defect or a Goal, once its remaining Tasks are blocked. The drive cannot change those prerequisites. The detail names at most eight of them, in ledger order, and at most eight members for each (`DriverPolicy.MaxBlockersNamed`); it counts the rest (`T5,T6 and 3 more`, `; and 2 more`), so its length does not grow with the workset.
- **`LimitReached`:** the drive has issued its 64 directives. Start and resume directives both count.
- **`Failure`:** the set cannot be computed, an item the previous cycle created is not in the recomputed set, or an input failed without a result in two consecutive cycles that changed nothing else (see [Attempt outcomes](#attempt-outcomes)). Outside the query, the drive stops with `Failure` when the host reports a child attempt that repeated the fault of the attempt before it on the same input.

When the recomputed set differs from the previous cycle's, the reply carries a transcript message naming the added and removed items. Every stop carries its message. A stop turns the driver off and releases the binding.

## Directives, start and resume

A directive is host-generated text the session submits unchanged:

```text
/cq:advance --roots G1,T4 --through work --start-token 3f0c…
$cq-advance --roots G1,T4 --through work --resume-token 91ab…
```

Claude Code and Pi receive `/cq:advance`, Codex `$cq-advance`. The roots are the frozen targets in `(ledger, number)` order and the phase is the frozen one. The advance entry point passes the token as `SessionCommand.Workflow.token`; it is `null` in a session without a driver. The token travels only in that field: the attached host refuses, with `Invalid`, an activation whose `operatorRequirements` text contains its own token, because that text is delivered to Planner, Worker and reviewer children. A directive consists only of workflow flags, so the entry point passes an empty `operatorRequirements` for it and the children of a driven cycle receive no session request. Their requirements section then holds the project's standing requirements alone, and is absent only when the project has none. The refusal comes before the token is presented to the server, so the session can activate again with the token left out of the text.

The attached host asks the server before every new activation (`DriverSession.Activate`). For a start token, or no token, it first checks its own precondition: no child, check, integration or combination of the session is still active. A refusal there (`Settle active child/check/integration/combination work before changing workflow: …`, which names each unsettled piece of work by kind, identity and phase) is made before the token is presented, so the token stays unused and the same activation succeeds once the work has settled. The host retains its last 64 activations only to answer a repeated request; the number of activations of one attached session is not limited.

**Work an earlier drive left unsettled.** A drive can end, for example by a park, while an integration its session prepared is `Ready` or `Pending`. That integration is not terminal, so the next drive's start directive is refused as above until it is settled, and it is settled in the same turn, before the directive is submitted again:

- The session applies it with `Integrate`. The host authorizes that on two conditions. First, an integration is applied only in the workflow activation that prepared it; because the start directive was refused, that activation is still the host's current one. Second, the integration is one the server carries over (see [Bound-session mutation rule](#bound-session-mutation-rule)): before it authorizes an `Integrate` the host asks the server (`DriverSession.Settleable`) whether a start directive is pending for its session and which integrations may be settled before it. Every outcome `Integrate` returns is reachable: `Recorded`, `NotApplied` (Git refused the update; nothing is written to the ledger) and `Pending` (the outcome or its acknowledgement is unconfirmed; `Integrate` is repeated). The drive stays on with its cycle pending in each case. There is no separate discard operation: an integration is left behind only by applying it.
- The completion that `Recorded` writes to the ledger is admitted although no cycle is active (see [Bound-session mutation rule](#bound-session-mutation-rule)).
- Once the integration is `Recorded` or `NotApplied`, the same start directive activates and the cycle starts. If the turn ends before that, the next query stops the drive with `directive not started`, as for any unused start directive.
- Nothing new starts under the pending directive. `PrepareIntegration` with a new ID and `Combine` with a new ID are refused with `Denied` (`The CQ driver's start directive is pending: a new integration waits for the workflow it starts. …`); `Integrate` or `Combine` naming an integration the current activation did not prepare is refused as before.
- No combination is settled under the pending directive. An earlier drive can leave a combination whose publication is pending (its plan is frozen and the upload failed); a `Combine` that repeats it would publish it again. That `Combine` is refused with `Denied` (`The CQ driver's start directive is pending: combination <id> cannot be prepared or published before the workflow the directive starts. …`), whichever integration it names: nothing is uploaded, the combination stays `PublicationPending` and the drive stays on. The source of a combination is an integration that already resolved as `NotApplied`, so it is not work the server carries over, and the refusal does not depend on the carried set. `CombinationStatus` still reads the combination. The start directive stays refused while the publication is pending, so the turn ends with the directive unused and the next query stops the drive with `directive not started`; the session then repeats the `Combine` as an undriven session does.
- An integration the current activation prepared but no drive carried over is not applied either. The earlier drive's activation stays current after that drive ends, so the session can prepare an integration in it between the two drives, and the host then owns an integration that no cycle registered. `Integrate` for it under the pending directive is refused with `Denied` (`The CQ driver's start directive is pending: integration <id> was not left unsettled by an earlier drive of this session, …`) before Git is touched: the target ref does not move, the integration stays `Ready` and the drive stays on. The start directive stays refused while that integration is unsettled, so the turn ends with the directive unused and the next query stops the drive with `directive not started`; the session then applies the integration as an undriven session does. After the start directive has activated, the earlier integration belongs to a previous activation: combining a `NotApplied` one is refused there, and the session prepares it again under a fresh ID, as the governing instructions already require after `NotApplied`.

The quiescence precondition itself is unchanged: no activation, driven or not, starts while an integration is `Ready`, `Pending`, `Preparing` or `Running`.

- **Start token.** A run starts only if the token is the pending cycle's unused start token, the caller is the bound session of an on driver, and the request is `Advance` with exactly the cycle's roots and phase. The cycle becomes active and records the run. A retry with the same activation ID returns the same result.
- **Resume token.** It returns the cycle's existing run and never creates one. It is valid once, for the active cycle, from the bound session, with the same roots and phase. Each resume directive carries a fresh token. If the run the server returns is not the attached host's active workflow, the host holds no record of that run and no resume directive can succeed there: the host reports it (`DriverSession.Fail`), the driver stops with `Failure` and the detail `run <id> of cycle N is not the active workflow of its attached host`, and the activation is refused with that reason.
- **Rejections.** An omitted token, a start token presented as a resume token or the reverse, an unknown or reused token, altered roots or phase, another workflow (begin, review or upstream) and a caller other than the bound session are all rejected. No run starts, and the driver stops with reason `Failure`.

A session whose driver is off, or that has none, activates exactly as before and receives no cycle.

## Bound-session mutation rule

While a driver is on, every ledger mutation from its bound attached session is attributed to that driver's active cycle, whether or not the call names a cycle: direct `change` calls, Reference changes, proposal applications and integration completions. If no cycle is active — before the first directive, between cycles, or before the start directive is accepted — the mutation is rejected and the driver stops with reason `Failure` (untracked mutation). The same holds for an activation without a valid token.

**The carried-over integration.** One write is admitted without an active cycle: the completion of an integration that an earlier drive of the bound session left unsettled, while the driver's cycle is pending (its start directive is issued and not yet accepted). The write is the reserved completion of that integration and nothing else; it is not attributed to any cycle, and the pending cycle's boundary is not applied to it.

The server derives which integrations are carried over, from its own records. When a drive starts, it takes over the unsettled `Integration` lineage members of the last cycle of the earlier drive under the same session key, together with what that drive had itself carried; when a driver binds an attached session, it also takes over those of that session's drives under other session keys. They are kept by attached session, so a different attached session that later binds the same key completes none of them. An integration is in that lineage because the attached host registered it when it was prepared under a driven cycle. An integration prepared outside a drive is not carried: its completion under a pending cycle is an untracked mutation. The attached host does not let it come to that. `DriverSession.Settleable` returns, to the bound session of an on driver whose cycle is pending, `pending` and the integrations carried over for that session, and to every other caller `pending = false` and no integrations. It is a read: it takes no ledger transaction and changes nothing. It gives the same answer the boundary gives the completion write, so the host refuses an `Integrate` the boundary would reject before the integration is applied in Git (see [Directives, start and resume](#directives-start-and-resume)).

Everything else is unchanged while the cycle is pending: any other ledger write of the bound session, the completion of any other integration, and the carried-over completion itself before the first directive is issued, are rejected and stop the drive as untracked mutations. Once the cycle is active nothing is carried: a completion then meets the boundary of the active cycle like any other write. A `NotApplied` observation writes nothing to the ledger and never meets the boundary.

An exact retry of an already committed request returns its acknowledgement without writing and is not checked. `previewWorksetAfter` evaluates a hypothetical change in a transaction that always rolls back and is not a write.

Sessions that are not bound to an on driver are unaffected. A park, a stop or a server restart returns the bound session to that behaviour.

## Write-time boundary

The boundary runs inside the writing transaction, so a rejection leaves the ledger unchanged. What an admitted write adds to its cycle (created items, lineage members, the claim it acquired) is recorded only after that transaction has committed; a transaction that fails leaves the cycle as it was. A stop, by contrast, is recorded at once and survives the rollback of the write that caused it. The boundary applies to every attributed write:

1. **Before the write:** every existing item the request names must be in the cycle's stored snapshot or have been created by the cycle. A Reference names both endpoints; Produce names the producer; Archive, Terminate and Restore name their members, roots and neighbours.
2. **After the write, before commit:** every item the write actually changed must satisfy the same rule, and every item it created must be selected by roots-bound enumeration of the frozen targets on the resulting ledger state. A plain Create is therefore rejected, except the Defect report below; a Produce under an in-set producer is admitted.
3. **After the cycle:** the next continuation query checks that every item the cycle created is in the recomputed set.

**Milestone assignment.** Work admission requires every Task to belong to a milestone, and workset traversal selects only through `Produces` and `Contains`, so the milestone of a planned Task is context and never a member of the set. A drive therefore assigns and reassigns Tasks under these exceptions to rules 1 and 2:

- A `Produce` from an in-set producer may name an existing milestone outside the set (`MilestoneRef.Existing`), and a `Reference` may add `PartOf` from an in-set Task to one (written either as `PartOf` or as `Contains`). The milestone must be Open. The write adds the membership edge and revises the milestone with an unchanged draft; a batch changes an item once, so no other mutation of that batch can name it.
- A `Reference` may remove `PartOf` from an in-set Task to a milestone outside the set that is Complete or Cancelled (written either as `PartOf` or as `Contains`, `present` false). The write removes the membership edge and revises the Task and the milestone; the milestone keeps its draft and its status. This is the recovery of a Task that [work admission](cohorts.md) refuses with `ClosedMilestone` when the drive does not select its milestone, as in a drive rooted at the Task: the removal, then an assignment to an Open milestone in a second request, because a batch changes the Task once. A request that carries both is refused by the ledger with `Invalid` "An item may be changed only once in a batch", as for an undriven session; that is not a boundary violation and the driver stays on. After the two requests the next continuation issues a new cycle that contains the Task.
- A Milestone created in the same batch that an in-set `Produce` names with `MilestoneRef.Created` is an admitted creation: after the write it must contain a Task that write produced. It joins the cycle's created items, so the cycle that created it may change it. Rule 3 accepts a created Milestone while it is context of the recomputed set.

Everything else that names or changes a milestone outside the set is rejected as an out-of-set change: replacing its draft, including to reopen it, archiving, restoring or terminating it, removing a membership in an Open milestone, removing the membership of a Task that is outside the set, restoring a Task so that its membership changes, any other relation, and an assignment to a milestone that is not Open. A Milestone created without such a `Produce` is a non-selected creation.

**Defect report.** A drive can meet a defect it must not work: a host or tooling defect that blocks its workers. The governor records it and links the items it blocks, so that those items leave the ready set and the drive continues with the rest. Two exceptions to rules 1 and 2 admit this, for the bound session only:

- A plain `Create` of a Defect is an admitted creation. It does not join the cycle's created items, so rule 3 does not apply to it, no later cycle's boundary contains it, and it is never selected: workset traversal selects only through `Produces` and `Contains`.
- A `Reference` may add `BlockedBy` from an in-set item to a Defect outside the set that is Open (written either as `BlockedBy` or as `Blocks`). The write adds the edge and revises the Defect with an unchanged draft; a batch changes an item once, so no other mutation of that batch can name it. The Defect need not be one the drive created. The ledger treats the write as any `Reference`: both expected revisions, and the fence of an endpoint that has an active claim, which only the claim's owner can supply.

Everything else that names such a Defect is rejected as an out-of-set change: replacing its draft, including by the cycle that created it, restoring, archiving or terminating it, removing the blocking link, any other relation, a link whose blocked item is outside the set, and a link to a Defect that is not Open. A blocking link to an item of another ledger outside the set is rejected as before. A session the cycle delegated to has neither exception: its plain `Create` of a Defect is a non-selected creation. The linked items are not ready while the Defect does not satisfy the dependency, so the continuation decision needs no rule of its own: the drive continues while other work is ready and stops `Quiescent`, naming the Defect, when everything left is blocked. Once the Defect is Resolved the items are ready again. Only `Resolved` satisfies the dependency ([dependencies](dependencies.md)): a Defect closed as `NotReproducible`, `Rejected` or `Withdrawn` keeps the linked items blocked, and no drive can remove the link, since removing a blocking link to a Defect outside the set is an out-of-set change. The operator removes it: in the browser's relationships of the blocked item, or with a `change` of `Reference(item, BlockedBy, Defect, present false)` and both current revisions from a session that has no driver on.

A milestone inside the set, as in a drive rooted at it, is an ordinary member: the bound session reopens it by `Replace` or `Restore` and the next cycle contains the milestone and its Tasks. Removing a Task's membership there takes the Task out of the set, so reopening is the remedy in that drive.

Closing a milestone inside the set is an ordinary ledger write: the [closure gate](ledgers.md#references) refuses a `Replace` or `Terminate` that would close it over a Ready or Active Task with the same `Invalid` fault an undriven write receives, nothing is committed, and the driver stays on because the refusal is not a boundary violation.

The snapshot is never recomputed at activation or at write time. An item attached to the targets after the directive was issued is outside that cycle and becomes advanceable in the next one. A descendant created in cycle N is in the snapshot issued for cycle N+1.

Any such rejection stops the driver with reason `Failure` and a detail naming the items.

**Questions.** Only a person settles a Question, by answering or by withdrawing it. An attributed write that leaves a Question `Answered` when it was not, or with a different `answer`, is rejected with `Denied`: `The CQ driver never answers Questions: Q3 would be answered by a driven session; park the driver before recording the user's answer`. This holds while a cycle continues on other ready work, and for a Question the write creates. An attributed write that ends a Question's wait for the user without an answer is rejected with `Denied` as well: `The CQ driver never settles Questions: Q3 would be withdrawn by a driven session; park the driver before withdrawing a Question`. The wait is the one `DriverPolicy.awaitsUser` counts, an unarchived `Open` Question, so the rule covers a `Replace` to `Withdrawn`, a `Restore` of a withdrawn revision and a `Cancel` termination that reaches the Question from its roots. No write archives a Question that is still `Open`: the ledger admits archival of terminal or settled items only and rejects it with `Invalid` for any session. Both checks compare the written Question with its previous revision after the write is applied and before it commits, so nothing is written. Unlike the rejections above they leave the driver on: the session has not left its set, and the operator parks, has the Question settled and drives again. Any other change of an in-set Question, such as a new title, is admitted.

**Operator Actions.** Only a person ends an Operator Action's wait for the operator. An attributed write after which an Operator Action that was unarchived and `Requested` is no longer so is rejected with `Denied`: `The CQ driver never settles Operator Actions: OA2 would be taken out of Requested by a driven session; park the driver before settling an Operator Action`. The wait is again the one `DriverPolicy.awaitsUser` counts, and the boundary evaluates that same predicate on the written action and on its previous revision, so one rule covers every exit: a `Replace` to `Cancelled`, `Failed`, `Observed` or `Confirmed` (the ledger itself restricts only confirmation text from a non-human session, not the status), a `Restore` of a revision that was not `Requested`, and a `Cancel` termination rooted at the action or at an in-set item that reaches it through `Produces` or `Contains`. The ledger has no status-transition rule for Operator Actions and already rejects archival of a `Requested` action for every session, so this check is the only place the rule lives. It applies to every write attributed to the cycle, whatever the role of the session, including a delegated session with the `Human` role. Like the Question checks it runs after the write is applied and before it commits, writes nothing and leaves the driver on: the operator parks the driver, settles the action by hand and starts the drive again. Three kinds of write stay admitted: a change that leaves the action `Requested`, such as a new title; the creation of an Operator Action in any status, since a new action never waited; and a move of an action that is already `Confirmed` to `Observed` or `Failed`, since `Confirmed` is not a wait for the user.

## Cycle lineage

The accepted cycle ID is stamped on the advance run: the server records the run in the cycle, and the attached host writes it into the `WorkflowActivation` it stores. A cycle's lineage lists everything that inherits the ID, each entry with its parent and whether it has settled:

- the server adds the Change request, Claim, Proposal and Integration of every attributed write and of every claim the bound session acquires during the cycle;
- the attached host registers each dispatch Request and child Attempt, each prepared Integration and each Combination when the dispatch tool returns. It then follows the member: it reports it as resting (`DriverSession.Rest`) when it comes to rest, registers it again when the host works on it again, and settles it when it reaches a terminal phase. A child Attempt is settled with its outcome (`DriverSession.Conclude`, see [Attempt outcomes](#attempt-outcomes)).

A cycle holds at most 1,024 lineage members (`DriverPolicy.MaxLineage`). The count is needed, though its value is not derived: `DriverStatus` carries the whole lineage of the latest cycle in every driver reply (`Started`, `Bound`, `Continue`, `Stop`, `Status`, `Parked`), and the host's client refuses a reply above 2 MiB (`ServerApi`). One entry encodes to about 165 bytes of JSON, so past some 12,000 members every reply of that driver, the continuation query and park included, would be unreadable; at the bound the lineage takes about 165 KiB. A registration beyond the bound is refused with `Limit`, and an attributed write beyond it stops the drive with `Failure`; the next drive starts a cycle with an empty lineage. Removing the bound requires a status that no longer carries settled members.

The host follows a member by reading its state: a read waits up to 20 seconds for the member's current operation to finish, and the follower pauses one second between reads that show no change. A successful `Integrate` is therefore reported directly: before the dispatch reply is returned, the host registers the integration again (`DriverSession.Inherit`), which clears its resting state on the server. That report and the follower's resting reports are made one at a time, and the follower drops a resting state it read before the `Integrate`, so a late report cannot mark a running integration as resting. If the cycle the integration was prepared under has ended, the server refuses that report and nothing is held; this is the case for an integration carried over to the next drive.

**Implemented and reserved.** The three kinds of entry above are what a real drive produces. Only the bound attached session writes under a cycle: children report results and do not change the ledger themselves, and the attached host makes no ledger write of its own under a cycle ID.

The server core also implements delegation, which nothing in the attached host, the hook commands, the Pi extension or the MCP tools uses: a `LineageMember.Session` entry for a session delegated under the cycle, which may register members beneath itself and holds the run open while unsettled, and `DriverSession.Change`, a write by such a session that carries the cycle ID and meets the same boundary. A write that names an unknown cycle, an ended cycle or a cycle the caller is not part of is rejected; when the cycle's driver is on it stops with reason `Failure`. `DriverContractTest` exercises these paths; no production code constructs a `Session` member or a `DriverSession.Change`, so they are reserved for a future delegating client and carry no guarantee about one.

**Claims are stamped, not confined.** A claim the bound session acquires during an active cycle is added to the lineage, and that is all the boundary does with claims. Acquiring, renewing and releasing a claim are not ledger mutations: the bound session may claim an item outside the cycle's set, and may claim while no cycle is active, without a rejection or a stop. The claim confers no write: a mutation of that item still meets the boundary.

The host's lineage calls are made reliable rather than best-effort. A call lost in transit is repeated up to six times with a doubling pause (250 ms at first); a fault the server returns is its answer and is not repeated. If a member cannot be registered, its state on the host cannot be read, or it cannot be settled, the host reports it with `DriverSession.Fail` and the driver stops with `Failure` and a detail naming the member: `attempt <id> of cycle N could not be registered: <cause>` or `… could not be settled: <cause>`. If that report cannot be delivered either, the host logs it; the drive is then bounded only by its directive limit.

### Attempt outcomes

The attached host is the source of what happened to a child attempt. When an attempt ends, the host settles its lineage member with `DriverSession.Conclude`, which carries a `ChildOutcome`: the attempt ID, the items of the attempt, the operative-input fingerprint of its group when the attempt was started from a selection (see [cohorts](cohorts.md#adaptation-and-progress); a direct `Start` has none), the fault text when it failed, and one of six ends:

| End | Meaning | Input afterwards |
| --- | --- | --- |
| `Admitted` | The attempt left an admitted result, whatever it reports. | Deferred until an operative input changes. |
| `Retryable` | The attempt failed without a result and the host published its fault. | Offered again by the next Select, with the fault as context. |
| `Repeated` | The attempt failed without a result in the same fault text as the attempt before it on the same input. | Deferred. |
| `Failed` | The attempt failed without a result and the host does not offer its input again: it was not started from a selection, its receipt does not advise a retry, or its fault could not be published. | Deferred. |
| `Cancelled` | The Governor or the host's shutdown cancelled it. | Deferred. |
| `Unknown` | The outcome is unknown or the publication is pending. | Deferred. |

The server stores the outcomes in the cycle (`CycleRecord.outcomes`, one per attempt; a repeated report replaces the earlier one), so they are part of the durable driver record and of a project archive. `DriverRequest.Snapshot` returns them with the cycle's frozen snapshot. They are not part of `DriverStatus`. The server refuses with `Invalid` an outcome without items, a `Retryable` or `Repeated` outcome without fingerprint or fault, and a fault or fingerprint above 512 characters; the attempt must be a registered member of the cycle.

Three rules read them. None has a count or a timeout to configure.

1. **Repeated fault (D145).** A `Repeated` outcome reported for the active cycle of an on driver stops the drive at once with `Failure` and the detail `attempt <id> of cycle N failed on G1 with the same fault as the attempt before it on the same input: <fault>`. "The same fault" is equality of fault text, compared by the host.
2. **A cycle that only failed continues (Q53).** An input is *left retryable* by a cycle when every attempt the cycle made on it ended `Retryable`. An input that failed and was then attempted again in the same cycle with any other end is not, because the host keeps it deferred. When the next query finds the snapshot unchanged, a ready item and at least one input left retryable, the drive is not quiescent: the query issues the next start directive.
3. **The same input fails in two consecutive such cycles (Q53).** The cycle issued under rule 2 stores the retryable attempts of the cycle before it (`CycleRecord.retried`). If that cycle also ends with an unchanged snapshot and leaves retryable an input with the same fingerprint as one in `retried`, the drive stops with `Failure`, whatever the two fault texts are: `G1 failed without a result in two consecutive cycles on the same input while nothing else changed: attempt <id> of cycle 1: <fault>; attempt <id> of cycle 2: <fault>`. Parse faults carry positions that differ between attempts, so rule 1 alone would let differently malformed outputs continue a drive cycle after cycle; rule 3 ends that sequence after the second cycle. A cycle that changed the snapshot is not such a cycle: the cycle after it stores no `retried`, and a failed input is counted again from its first unchanged cycle.

Rule 3 compares cycles, not attempts. Within one cycle the Governor may select a failed input again as long as each fault text differs from the one before it; the host ends that only by rule 1. A cycle with no attempts, or whose attempts all ended otherwise, and an unchanged snapshot stops `Quiescent` as before.

## Status

`DriverStatus` carries the key, state, bound session, frozen workset, the latest cycle with its lineage, the active child count, the directive count, the last stop reason and one host-generated indicator line:

```text
CQ driver binding: G1 through work
CQ driver on: G1 through work; 2 active children
CQ driver off: G1 through work; stopped (quiescent): No item of the advanceable set is ready to advance
```

Every state change and stop also returns a transcript message in its reply.

## Pi extension

The generated Pi extension (`.pi/extensions/cq-host.js`) is Pi's caller of the driver. It keeps only what the last control reply reported and the drive input last accepted, and it builds no directive.

- **Commands.** `/cq:drive <target IDs> through=<phase>` or `/cq:drive workset=<id>` sends its argument text unchanged to `Start`. It posts the host message with the preview in three groups (advanceable, context only, readiness) and, when Pi is idle, asks for the first continuation at once. `/cq:park` sends `Park`. A rejection is posted as an error and changes nothing. Both are extension commands; the four workflow prompt templates are unchanged.
- **Session key.** `ctx.sessionManager.getSessionId()`: Pi's session identifier, a UUIDv7 unless the operator chose `--session-id`, and the value the native usage records already carry. On Pi 0.99.1 it was observed stable across the turns of a session and distinct between two concurrent sessions.
- **Toggle key.** `ctrl+alt+a`, which no default Pi keybinding uses. With the driver on it parks. With the driver off it drives again with the input last accepted in this Pi session. That text lives only in the extension's memory, so a new, resumed, forked or reloaded session has none; the key then starts nothing and posts a notice asking for `/cq:drive` with targets and a through phase.
- **Continuation.** On `agent_settled` with the driver on, the extension sends `Continue`. It submits a directive with `sendUserMessage(text, { deliverAs: "followUp", expandPromptTemplates: true })`, which Pi expands through the `/cq:advance` prompt template; a stop is shown and nothing is sent. A turn whose `turn_end` outcome is `aborted` or `error` parks the driver instead of continuing, so `escape` ends a drive. With the driver off the extension makes no request.
- **Indicators.** The footer status `cq-driver` shows `DriverStatus.line` from every control reply and is refreshed by a `Status` query at each `turn_end` while the driver is on; before any drive it reads `CQ driver off`. That refresh is an indicator only: it is given up after five seconds without closing the host connection (a late reply is dropped), and a failed refresh is shown as `CQ driver status unavailable: <cause>` and does not end the drive. Item titles in the preview are shown on one line, without control characters and cut to 80 characters. Every state change, set-change message and stop reason is posted with `ctx.ui.notify`, failure and not-bound stops as errors.
- **Session end.** `session_shutdown` parks a driver that is on, because the attached session it is bound to ends with the host process.

## Claude Code and Codex hooks

Claude Code and Codex share one hook program, `cq hook HARNESS EVENT` (`DriverHook`), which `cq configure` installs as project hooks. It reads the hook's JSON on stdin, calls `DriverEntry` with the operator credential and the saved project configuration, and writes the hook's JSON reply. It holds no state and never builds or edits a directive.

- **Session key.** The `session_id` on the hook's stdin. On Claude Code 2.1.285 and Codex 0.159.2 the UserPromptSubmit and Stop hooks of one session received the same id on every turn, and two concurrent sessions received different ids. The Claude statusLine input carries the same id.
- **UserPromptSubmit.** A prompt whose first word is `/cq:drive` (Codex: `$cq-drive`) sends the rest of the prompt unchanged to drive-start; `/cq:park` (`$cq-park`) parks. The reply goes back as `hookSpecificOutput.additionalContext` for that session's turn and as a `systemMessage` in the transcript: the host message, the status line, the single-use bind token with the exact `session` `Bind` request, and the preview as two headed lists with readiness shown inline (rendered by `DriverHook`, the host-side renderer for both harnesses). A host rejection is reported the same way with `Nothing changed for this session's driver and no bind token was issued.` Any other failure, such as a reply that did not arrive before the client deadline, leaves the outcome unknown, because the server may have committed the request: the hook then says that the driver may have changed and tells the session to read the driver status or park before driving again. Every other prompt produces no output and no host call.
- **Command bodies.** `/cq:drive`, `/cq:park` and the `cq-drive`, `cq-park` skills only present that bind token to `session` `Bind` and show the status. They start and park nothing; a session that skips the bind gets the `NotBound` stop at its next stop.
- **Stop.** The hook queries the continuation. `Continue` becomes `{"decision":"block","reason":…}`: any set-change messages, one instruction line, and the host directive, unchanged, as the last line. Anything else allows the stop, with the stop message as `systemMessage`; with the driver off the hook prints nothing.
- **Status line.** Claude Code only: `cq hook claude StatusLine` prints `DriverStatus.line`, or `CQ driver off` before any drive. Codex shows no custom status-line text, so its indicator is the transcript messages.
- **Errors.** Malformed input, a missing or malformed `session_id`, an event other than the one the command was installed for and an unknown harness are rejected before any host call, with an explicit message and no default session. The program always exits 0 and never blocks the harness on a CQ error: the Stop hook then allows the stop and the prompt is passed on, with the error as `systemMessage` (as the status-line text for `StatusLine`).
- **Parking a running drive.** Codex delivers a `$cq-park` typed during a driven turn to the hook at once. Claude Code queues a prompt typed during a turn until the turn ends, and a blocked stop continues the same turn, so in Claude Code the operator interrupts the turn first (Stop hooks do not fire on an interrupt) and then enters `/cq:park`.

`cq configure` writes, for Claude Code, `.claude/commands/cq/drive.md` and `park.md` and, in `.claude/settings.local.json`, one hook group for each of `UserPromptSubmit` and `Stop` plus a `statusLine`; for Codex, the `.agents/skills/cq-drive` and `cq-park` skills and the two hook groups in `.codex/hooks.json`. An entry is CQ's when its whole command, after whitespace is normalised, is the command CQ generates: one executable (as CQ quotes it) followed by `hook <harness> <event>`. Such entries are replaced, also when they name another CQ executable, and every other hook group, handler and event is kept. A command that wraps the CQ hook (`timeout 5 cq hook claude Stop`, `sh -c '…'`) or merely ends like one is the user's: it is kept, and CQ adds its own group beside it. A `statusLine` that is not CQ's is refused until the operator passes `--replace-statusline`; `--replace` alone does not replace it. The flag is refused for Codex and Pi, which get no status line. A file CQ replaces or merges into is written to a temporary file and renamed over the original, keeping its permissions.

## Interfaces

HTTP and WebSocket carry `Command.Driver` and `Result.Driver`. The attached host's `session` tool adds `Bind` and `Driver`. A Pi attached host additionally serves the JSON-RPC method `cq/driver`, taking an `ExtensionDriver` (`Start`, `Park`, `Continue` or `Status` with the extension's session key) and returning a `DriverReply` or `{"Failed":{"fault":…}}`; other harnesses answer it with method-not-found. The CLI has one driver entry point, `cq hook`, and there is no MCP domain tool.
