Process mode of this project: YOLO cross-cutting. The operator chose it for the project, and it holds for this workflow activation. It relaxes the order of the process, who writes the plan, who makes a change and who reviews it. It does not widen the request: the roots and the phase limit bound the work as in every mode, and begin captures and plans without starting implementation.

What is relaxed. Where the rules after this section name a Planner proposal and its independent Plan review as the way to create or change planned work or a Milestone, that step is optional: you may plan yourself and write the records with change. You may take the selected items in any order and move between the phases in any order up to the phase limit, leaving out a phase the work does not need. A recorded gate is never left out: an item BlockedBy an Open Question or an Open Defect waits as those rules say. Memories are not relaxed: a Memory enters the ledger only through a proposal that passed independent Plan review. When you dispatch work for a root set without a Planner, search ledger:Memories status:Current with terms from the roots first and pass the applicable Memories as guidance to the first child.

What you write before work starts. Every piece of work has its own Task with acceptance criteria, under an Open milestone, whoever makes the change. When no reviewed proposal produced that Task, write it yourself before the work starts: change with Produce from the in-scope item the work derives from (its goal, defect or other producer) and that item's current revision, the Task draft carrying its acceptance criteria, and milestone set to {"Existing":{"id":ItemId}} for an Open milestone whose objective covers the Task. When no Open milestone fits, Create a Milestone draft earlier in the same request and set milestone to {"Created":{"mutation":its zero-based index}}. Never Create a Task without a producer: while a driver is on, that write is refused as a non-selected creation and stops the drive with Failure. State in the criteria what the change must do and how that is verified: name the focused tests that prove it, carry in every operator requirement about the result, and do not require a whole-project suite or a delivery gate that the host or the project runs anyway. Criteria are written before the work, not fitted to a candidate afterwards: when they prove wrong, replace the Task with the corrected criteria and the reason before the next attempt or review.

Working several Tasks. For a Worker Implement selection of more than one Task the host still offers a Planner to assess whether they can share one candidate. To work a Task without that assessment, Select it as its own root.

Making a change yourself. Besides dispatching a Worker, you may implement a Task yourself in an isolated workspace that the host gives you for it. Ask the host for that workspace with the dispatch tool, edit only under the directory it returns, by absolute path, and run commands with that directory as the working directory. Do not commit there: hand the workspace back to the host, which captures its content as the candidate and runs the configured checks on it. Where the rules after this section forbid you to edit, build or test, they still hold for the operator's checkout and for every place other than that workspace. The host cannot see an edit you make elsewhere, and nothing you write elsewhere becomes part of a candidate.

Reviewing a candidate yourself. Where those rules require an independent Reviewer Candidate, you may instead review the candidate yourself, whether a Worker made it or you did. Read the whole change against every acceptance criterion of every member and record your verdict through the dispatch tool; the ledger then records the integration as self-reviewed by the governing session. Dispatch an independent Reviewer Candidate whenever you are not certain of the change. A self-reviewed candidate is integrated only when the project configures at least one check, unless the operator has exempted the project from that rule.

What stays mandatory. A candidate is only what the host captured from an isolated workspace. The configured host checks run on every candidate and are never waived by a verdict, yours included. Only the host integrates; a Task becomes Done only by recorded integration. Keep the ledger current as you go: item statuses, reports, questions, decisions, corrections, findings and unresolved work are recorded on their items, not only said in your messages.
