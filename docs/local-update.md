# Updating the local native release

`run-local.sh` starts `.local/release`; it does not build source. After committing changes, stop that launcher with Ctrl-C and wait for `CQ stopped`, then run:

```sh
./update-local.sh
./run-local.sh
```

Both commands use `CQ_LOCAL_STATE`, defaulting to `/srv/nvme/tmp/cq4-playground`. The updater requires an existing owned local state and installed package. It never signals a pre-existing server or database process. It holds the launcher lock for the entire update, so local startup remains unavailable while the build runs. Allow time for the native build and installed verification.

The operator-run updater snapshots HEAD into a detached worktree and refuses uncommitted runtime inputs. It runs `dev/package-local`: native compilation and bounded startup/API/browser-asset smoke against disposable databases. Testing is separate: `./test-local.sh` runs fast, UI, PostgreSQL and native gates, stopping on the first failure. Build evidence stays under `STATE/updates/ATTEMPT`. Any failure before installation retains the current release; inspect the named log. The candidate directory is retained for inspection. Retrying creates a new attempt and rebuilds it.

After verification it starts only the stopped local database, checks its migration checksum, creates a custom-format PostgreSQL backup, verifies its inventory, and stops the database. Equal schema/model hashes are accepted. The current transition is pinned in `dev/local-update-step.json` as `drive-identity-and-periods`: it names the schema and model hashes of the installed release (`39b2dd1`) and of this one, and the hash of `dev/local-update.sql`. Since the installed release the schema gained the table `cq_drive_periods` and its index, and the model gained the drive identity of a driver and the period records ([driver](design/driver.md#drives-and-their-periods)); the earlier model changes of the span (what tells a governing session that a person settled a Question it waits on, and the check name of a `Check` span) change no stored row. A schema or model transition that the step does not name is refused; a model change on an unchanged schema is accepted only as an `unchanged-data` step, which runs no SQL. Changing a checksum declaration alone is insufficient.

After the backup the updater applies the pinned SQL in one transaction: it creates the table and the index as `server/src/main/resources/db/001-ledgers.sql` declares them, gives every stored driver a new drive identity in its body and its summary, records the state each driver is in as the first period of its drive (at the time it stopped, or was last touched), and records the new schema hash. It takes the fingerprints of every table before and after (`data-before.json`, `data-after.json`) and then verifies the step:

- the database records the schema hash of the new package;
- the only table created is `cq_drive_periods`, and no table other than `cq_drivers`, `cq_drive_periods` and `cq_schema_migrations` changed;
- every driver row is the row it was with a drive identity added to its body and summary, no two share one, and each has exactly one period that records its state, with the periods of a project numbered from 1;
- the updated database has the structure the new schema declares: the updater declares that schema in a scratch database (`cq_update_structure`, dropped again, and dropped as well when an interrupted earlier run left it) and compares the two structures as `pg_dump --schema-only` prints them, the entries of a table without their order.

The receipt names the step, the number of drivers and periods. If the SQL, a verification or the package replacement that follows fails, the updater restores the backup into the database in one transaction, drops any table the SQL created (the backup does not know it), verifies the restored fingerprints against those taken before, and leaves the previous package installed. A step that refuses a database before it changes anything ends with the receipt status `refused`, not `rolled-back`. The SQL changes nothing when it is applied to a database it was already applied to, and an update from this release to itself runs none.

Session directories of the installed release stay readable: `units.jsonl` holds `SessionUnitEvent` values, and the release only adds branches to that type, which a host of the installed release never wrote. A `cq wait` or a hook of the installed release cannot read a `units.jsonl` that a host of this release wrote a Question event into, so a harness session is restarted after the update, as after every update, and not left running across it. A host of this release also leaves `journal/started-by` in its session directory and `hosts/<session>.live`, `.told` and `.harness` in the checkout's CQ directory, none of which the installed release wrote or reads; a host withdraws them when it ends, and the next host that starts withdraws those of a host that was killed. The agent configuration saved for the installed release is used as it is.

Project archives are not converted by any update; [project backup](project-backup.md) says which earlier archives the current release refuses. Active claims, unfinished managed attempts and pending integrations prevent installation. Root attached Governor attempts identified by the attached-session collector may lack outer usage outcomes; those audit records remain unchanged and do not prevent replacement. The receipt and `unsettled-work.log` report each category separately, including the incomplete attached Governor count. This exemption does not establish that a harness has stopped; stop consumer runs before shutting down the launcher.

The updater moves the current release to `.local/release-before-ATTEMPT`, installs the verified candidate, and records the source revision, manifest identities and backup hash in `receipt.json`. Restart the launcher and reload the browser. Existing interactive host journals must be reconciled under the normal host recovery rules; this command does not start harnesses or settle their work.

**The Pi extension needs regeneration for this update; the Claude Code and Codex integrations do not.** Run `cq configure pi --settings FILE --replace` in every checkout that uses Pi: the generated `.pi/extensions/cq-host.js` changed (it tells its host that it can say what a person settled, asks the host at each turn end, keeps its waiter running while the session waits on a person, and asks the driver to continue a drive that stopped for user input; for an extension of the installed release the new host watches nothing). The source of no other generated file changed: the Claude Code and Codex hook commands, command files, skills and settings are generated as before, and the new Stop hook behaviour is in the `cq` executable they call. The instruction texts that changed (how a session waits and what it does when a Question it waits on is settled) are not in generated files: the host serves them, so a session has them once its host is the new package's. Restart running harness sessions after the update. `cq doctor harness` still reports a generated file whose content differs from what this package generates. `cq configure --replace` rewrites the files this package generates and removes none; nor does it remove an allow rule: it adds the rules of the state root the settings file names to `permissions.allow` of `.claude/settings.local.json` and leaves every rule that is there, so after the state root of a project is moved the rules of the former one stay and keep allowing Claude Code's file tools under it. Delete them by hand when that directory should no longer be writable without a prompt.

An interruption during replacement attempts to restore the previous package. Unverified recovery leaves `STATE/.cq-update-recovery.json`, which the launcher refuses. Inspect its receipt and logs, stop any owned update processes, and restore the matching **previous package and database backup**. Verify their recorded hashes and the database's schema before removing the marker. If a restore of the backup itself failed (`database-rollback.log`), it ran in one transaction, so the database is as the failed SQL left it; the updater has stopped the database, and the backup named in the receipt is the state to restore by hand. Never launch a package against an unverified database. Keep the previous release and `before.dump` together; rollback after subsequent use also discards database writes made since that backup. Automatic pruning is deliberately absent.

Focused updater checks:

```sh
nix develop -c python3 dev/update-local-check.py -v
nix develop -c python3 dev/update-local-check.py --postgres -v
```

The shared replacement contract runs against in-memory and real-directory adapters. The focused check also verifies that the pinned step matches this tree's schema, model and SQL, that the column and the index its SQL adds are the ones the schema declares and the schema without them is the one the step starts from, that the structures of two databases compare without the order of a table's entries, and that a step of another kind or another transition is refused. The optional PostgreSQL case uses a disposable cluster, checks the retained backup and package replacement, verifies refusal on a mismatched schema, and exercises the rollback of a failed replacement. For SQL applied after the backup it checks that an install without it leaves the rows alone, that the receipt names the changed tables, that applying it again changes nothing, and that SQL that fails and a replacement that fails after it, also one whose SQL created a table, each restore the backup. For the pinned step it builds a database of the schema the step starts from, with a column moved to the end of its table as an earlier update leaves one, and with claims, attempts and usage clocks; it checks that a project with a fence counter other than the number of its claims is refused before any change, that a failed replacement and each of nine departures of the SQL from what the step may do (no count stored, no hash recorded, another change to a usage clock, a change to another table, no index, another index, a further index, another declaration of the column, a table created) are refused and leave the database as the backup holds it, without the column and the index, and that the pinned SQL then leaves exactly the expected rows and structure, gives every project the work cursor the installed release counted, and changes nothing when applied again. A restore that cannot run leaves the marker, the previous package and a stopped, undamaged database. Full native/package gates are operator delivery evidence, not implied by these focused checks.
