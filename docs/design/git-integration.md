## Required behavior

The governor chooses whether to integrate a reviewed candidate. The local host owns Git execution; the server owns claims, revisions and domain changes. Successful worker/reviewer results do not themselves update a branch or accept a task.

Integration uses a separate workspace and an explicit configured target branch. The host must verify the repository identity, full expected target object ID, exact candidate, accepted result handles, applicable checks/review, and current claim/revision admission. Never use the governing checkout's index. A target checked out in another worktree needs an explicit safe policy before support; the initial implementation should reject it rather than leave its HEAD, index and files inconsistent.

Two sessions with disjoint item claims can still conflict on the target. The effect must use Git's conditional ref update with the complete expected old object ID. A failed comparison cannot be converted to an unconditional update. A stale candidate must not overwrite another session's work.

If the target advances and the reviewed candidate merges onto the current head without conflict, the host builds that merge itself, reruns every configured check on exactly the merged commit and integrates it ([host rebase](#host-rebase-onto-an-advanced-target)). Otherwise preserve the first candidate and its evidence, construct the combined candidate in isolation, and perform applicable validation and independent review on that exact candidate. Earlier approval does not transfer to bytes a model writes after the review: any change beyond the host's own conflict-free merge needs the existing worker conflict-resolution mode, fresh validation and a fresh independent review. The governor continues to pass handles.

## First implementation boundary

Introduce a narrow Git integration service with injected repository/command dependencies and a shared behavioral suite for a manual dummy and real scratch Git repositories. Its immutable operation intent binds identity, canonical repository/target, expected target, candidate and evidence references. Persist and force the intent before attempting the ref update. Track the observed Git outcome separately from delivery of the associated domain acknowledgement.

The mechanical proof must cover competing expected-target updates, separate indexes, unchanged unrelated checkout files, target advancement and recovery after a successful update loses its caller acknowledgement. It does not close claim authorization, combined-candidate review or the connected supervisor workflow by itself.

Do not treat a second Git receipt ref as an atomic transaction with the target across crashes. The installed Git 2.55.0 `git-update-ref` documentation promises individual ref atomicity and explicitly permits concurrent readers to observe a subset of a multi-ref update. A stronger crash guarantee has not been established here.

Recovery first inspects the retained operation and Git state. A matching candidate at the target, or verified containment of the candidate in a later target, can establish the retained effect. Preserve operation identity and replay the original idempotent domain request when its acknowledgement is missing. Never repeat Git merely because that acknowledgement is missing. Ambiguous Git outcomes, external history rewrites and missing retained evidence must remain explicit unresolved cases; they cannot trigger an unconditional retry.

## Reservation and exact domain request

Preserve the approved fencing semantics: an irrevocable grant that silently survives successful takeover is not the selected design. A small server reservation instead blocks overlapping changes until the exact Git operation is settled. An unreachable host can therefore block those items indefinitely. Unrelated items remain available. Lease expiry alone, timeout, or an operator's desire to take over cannot prove that an old executor will never perform its CAS.

Use one `IntegrationIntent` binding operation ID, project/owner, repository/target, expected target, candidate, worker/reviewer result handles, fence/member revisions and the exact prospective `ChangeRequest`. Its server record has a resolution of `Pending`, `NotApplied(reason)`, or `Recorded(ChangeAck)`. The intent and resolution are operational coordination records outside the fourteen ledgers and the usage audit.

`IntegrationService.reserve` validates the full active claim and revisions, accepted worker/reviewer admissions, exact candidate, applicable validation and narrow intended domain changes, then inserts the reservation under the same project transaction as claim changes. Pending reservations block competing domain edits, release, acquisition/replacement, takeover and termination over their affected items. Expose the blocking operation ID. Expiry must not allow acquisition to bypass a reservation, and same-owner ordinary changes must not bypass it either. No database transaction remains open across Git execution.

After ordinary claim expiry, the reservation authorizes only its already frozen effect and domain request. It does not revive the lease or authorize fresh work or result admission. Keep the existing claim operations and add a typed pending-integration conflict plus reservation entries in claim/takeover previews. Renewal may continue. Replaying an already committed ordinary ledger acknowledgement remains valid because it creates no new mutation.

The first connected path integrates a completely reviewed task cohort. The governor confirms a compact preview. Host code loads current drafts, preserves narratives, and constructs the exact bounded task-completion request and evidence citations. The server independently checks those permitted changes against the frozen candidate/review evidence. Do not accept arbitrary host-authored mutations through this capability. Probe results cannot integrate; every selected task needs candidate-ready and accepted per-member outcomes, plus successful applicable checks on the exact candidate.

Extract transaction-local ledger mutation application so `recordApplied` can apply the stored request, retain its ordinary idempotency acknowledgement and resolve the reservation to `Recorded` in one transaction. This path uses the exact reservation authority; it cannot reconstruct a new request against current drafts. Repeating it returns the same acknowledgement. A domain-recording failure after Git success leaves the reservation pending and reports that distinction explicitly.

`NotApplied` requires evidence of definitive failure and a settled executor that cannot later update the target. Hold exclusive coordinator/journal ownership through settlement and durable terminal-observation sealing before releasing the server reservation; a delayed concurrent replay must not subsequently execute CAS. Recovery with unsettled execution, missing journal or ambiguous Git state remains pending. Recovery may record verified candidate incorporation without asserting that this operation caused it. Arbitrary external history rewrites are unsupported; the absence of the candidate is not sufficient evidence to repeat or abandon an uncertain effect.

## Connected host path

Keep four service boundaries in the existing supervisor graph: server `IntegrationService`, local `GitIntegration`, local `IntegrationJournal`, and `IntegrationCoordinator`. The journal seals the complete server-approved intent before CAS, then forces its observed Git result before domain recording. A recorded server operation or durable local applied observation goes directly to acknowledgement replay, never to another Git update.

The mutating Git executor needs the same supervisor-owned process-lifetime discipline as child jobs. Loss of a JVM file lock alone does not prove a descendant Git process has settled. Reuse guardian supervision for that effect and retain an unresolved reservation when cleanup cannot be confirmed.

For target advancement, a host-generated `CombinationPlan` handle binds repository/target, observed target commit and original worker result. Only `Worker(ResolveConflict)` may consume it. Host preparation uses that frozen target as the isolated workspace base, applies/merges the original candidate, and supplies conflict state by handle. Capture a new candidate descending from the frozen target, rerun configured checks, and obtain a fresh independent reviewer result. `ChildRunner` base selection is: the frozen combination target, else the previous candidate, else the current integration target head (the session base without a configured target). A further target advance requires a new operation: its preparation rebases the combined candidate when that merges cleanly and passes the configured checks, and another combination/review round is needed otherwise.

`refs/cq/candidates/*` is the trust boundary for child bases. `CandidateWorkspace.verifyBase` accepts a base only when it is the current target head, the session base or a commit that a host-captured candidate ref points at; any other commit, including one made by hand in the operator's checkout, is refused. It does not refuse work while the operator's checkout has uncommitted changes: a governor must not edit that checkout (D91), but staged and unstaged operator work there is preserved across integration and never blocks dispatch.

The initial target is an explicitly configured branch not checked out in any worktree. Reject checked-out targets before attempting an update. This requires cooperating Git writers: a preflight worktree check does not fence an arbitrary external checkout performed concurrently. CQ never updates shared checkout files or indexes.

### Governor operations and recovery ownership

Supervisor settings carry an optional explicit full `integrationTarget`; `null` leaves candidate-only operation. The existing local `dispatch` tool exposes prepare/apply/status actions exclusively to the governor. Preparation takes an operation identity and admitted reviewer handle, resolves the original worker and exact member revisions, renews the full claim, and freezes the completion request behind a compact preview. Reusing that identity with another reviewer conflicts. Preparation never moves the target and never touches a checkout or index; a host rebase writes one merge commit and its `refs/cq/candidates/<integration id>` ref. The governor applies the frozen identity explicitly. The frozen expected target is the current target head observed at preparation when the candidate strictly descends from it, so a continuation or a revision of a combined candidate integrates without `NotApplied` while the target is unmoved. When the head has diverged from the candidate and the host rebase applies, the expected target is that head and the candidate is the rebased commit. Otherwise it is the worker's recorded base, and the conditional update settles `NotApplied` (combinable) only when the target really advanced past the candidate's base. The server does not compare the expected target with the worker's base; ancestry is a host Git observation.

### Host rebase onto an advanced target

Before I18 every advance of the target sent each reviewed candidate through `NotApplied` → `Combine` → a `ResolveConflict` worker → host validation → a fresh review, even when the merge was textually clean. Preparation now does that merge itself.

When the target head H has diverged from the reviewed candidate C (H is neither C, an ancestor of C nor a descendant of C), `PrepareIntegration`:

1. runs `git merge-tree --write-tree H C` in the governing repository with the host's isolated Git environment (no system or global configuration, hooks disabled). The command writes objects only; it reads no index and no working tree. Attributes come from H's committed tree only. `--attr-source=H` replaces the `.gitattributes` files of the operator's checkout and nothing else: Git 2.55 still reads `$GIT_DIR/info/attributes`, the user's attributes file (`core.attributesFile`, by default `$XDG_CONFIG_HOME/git/attributes` or `$HOME/.config/git/attributes`, which `GIT_CONFIG_GLOBAL=/dev/null` does not disable) and the system file (`git var GIT_ATTR_SYSTEM`), and `merge.default` names the driver of every path without a `merge` attribute. Any of the four selecting `union` turns a textual conflict into exit 0. The user's file is disabled by `-c core.attributesFile=/dev/null` and the system file by `GIT_ATTR_NOSYSTEM=1` in the isolated environment; `$GIT_DIR/info/attributes` cannot be disabled, so a non-empty one is refused, as are repository-local `merge.default` and `core.attributesFile` (see below). `merge.directoryRenames=conflict` and `merge.renormalize=false` are fixed on the command line, so repository configuration can neither move a file into a renamed directory silently nor run content filters;
2. on exit 0 writes the commit M with ordered parents `[H, C]`, C's subject and a `CQ-Integration` trailer, and pins it at `refs/cq/candidates/<integration id>`;
3. runs every configured check on M as guardian-supervised jobs in disposable workspaces based on M, registered with the integration's job admission (cancelled on shutdown; each workspace is removed when its job settles), renewing the claim every 20 seconds; the 60-second preparation bound covers the server calls of each step, not the checks;
4. publishes each `ValidationObservation` with its output under the governing attempt, then freezes an intent with `expected = H`, `candidate = M` and `rebase = { reviewed: C, author: governing attempt, validation }`.

The preview's `rebase` field reports the outcome: `Unneeded`, `Applied { reviewed }`, `Conflicted { target }`, `ChecksFailed { target, validation }` or `Refused { target, reason }`. For the last three the frozen intent is the ordinary one for C (expected = the worker's base), the status carries the blocker `Target advanced to <H>; <cause>; Integrate records NotApplied, then Combine`, and `Integrate` settles `NotApplied` without launching Git, which is the source `Combine` requires. The rebase is refused, not attempted, when no check is configured (nothing would verify M), when the repository configuration defines a merge driver (`merge.<name>.driver` would run an arbitrary program during the merge), and when the repository selects merge behaviour outside H's tree: `merge.default`, `core.attributesFile` or a non-empty `$GIT_DIR/info/attributes`. Those settings are honoured by the merge a `ResolveConflict` worker gets in its workspace, which is where a refusal leads. No child attempt is created in any of these cases.

**Failed checks are bounded.** Every `PrepareIntegration` of C onto H writes a new merge commit and reruns every check, so repeating one after `ChecksFailed` with a fresh identity would rerun a failing check without limit. It is bounded like a [governor-requested revalidation](reviewer-checks.md#governor-requested-revalidation): after a check first fails on a rebase of C onto H, at most `revalidations` further preparations of that pair may rerun it, and `0` sends the first failure straight to Combine. Past the bound the preparation fails before it writes a merge commit or runs a check, with `Limit: Rebase check limit reached; Integrate <id> to record NotApplied, then Combine: check NAME has used its N revalidation rounds on <C> at target <H>`, where `<id>` is the last preparation whose checks failed. A preparation that ends otherwise (conflict, refusal, shutdown, claim loss, a check whose cleanup is unconfirmed) is not counted. The count is kept in the host's memory for the session (`RebasePreparation`); the server keeps none. It need not survive the session: worker and reviewer results are admitted to their governing session, host preparation and server reservation both refuse evidence of another session, and a host process is exactly one session, so no other session can prepare the pair (C, H) — it needs its own worker and reviewer, hence another C. A new head H′ starts a new count; reaching it takes an actual advance of the target.

**Revalidated candidates.** The worker checks that must have passed for C are C's *effective* checks: the admitted evidence with each check replaced by its latest [governor-requested revalidation round](reviewer-checks.md#governor-requested-revalidation). Preparation and reservation derive them from the unchanged worker result and its published `ValidationAmendment` rounds, apply the same bound and authorship rule, and cite every round and the replaced admission evidence in the Task evidence. The checks of M are always run afresh.

**Why M may land without a new review.** M's tree is produced by the host's deterministic three-way merge exiting without conflict: every change between H and M comes from the reviewed difference between the merge base and C, and no model authored any byte of M. The independent review covered C, not M; it is not transferred. What covers the interaction of C with the newer target is only the configured checks, rerun by the host on exactly M. A semantic conflict that no configured check detects is therefore not caught; that residual risk is accepted for a conflict-free merge and is the reason a repository without configured checks never rebases. Built-in merge drivers selected by attributes committed at H (for example `merge=union`) apply as they would to a merge in a workspace at H.

**What is recorded.** The server admits a rebased intent only when worker and reviewer cover `rebase.reviewed`, and `rebase.validation` names every configured check, at least one, each `Passed`, each backed by an observation published by the governing session's collector under `rebase.author` whose candidate and job workspace base are M and whose job settled successfully; otherwise `Rebased integration requires passing host checks on the exact rebased commit`. `rebase.failed` lists the earlier preparations of C onto H whose checks failed, each as `{ commit, validation }` for its own merge commit. The server admits them only when the commits are distinct and none is M, each names every configured check with at least one `Failed` and none `Unknown`, the list is within the bound above, and every failed run is an unsuccessful settled job on that commit published like the observations of M (`Rebased integration cites earlier rebase attempts that are not bounded failed runs of the configured checks on other commits`). That those commits have the parents `[H, C]`, and that the host listed every failed preparation, is the host's word. The Task evidence cites `Commit(M)`, `Commit(C)`, the worker and reviewer results, their validation and the observations of M, a second entry cites the failed runs (those before a passing rerun on M and those on the earlier merge commits), and the appended result reads `Integrated <M> into <target> (host rebase of reviewed candidate <C>)`. The server cannot observe Git: that M's parents are `[H, C]` and that its tree is the conflict-free merge is established by the host that created it, the same trust the server places in candidate capture.

**Further advance.** The conditional update still compares the complete expected head. If the target moves between `Ready` and `Integrate`, the rebased intent settles `NotApplied`; a new `PrepareIntegration` identity rebases C onto the newer head. `Combine` takes an un-rebased `NotApplied` integration as its source, which is what a conflicting, check-failing or refused preparation leaves behind.

Verification: `CandidateWorkspaceLocal` (merge primitive, conflicts, attribute and configuration isolation with one case per attribute source, merge-driver refusal; the system attributes file is provided in a bubblewrap mount namespace and, where bubblewrap is absent, only `GIT_ATTR_NOSYSTEM=1` is asserted), `IntegrationContractDummy`/`Postgres` (server contract), `IntegrationRebaseProcess` (real Git, guardian jobs, in-process server: applied, second advance, conflict, failing check, the bound on preparations that rerun a failed check and the citation of their failed runs, refusals, claim renewal, claim loss, shutdown) and `dev/combination-check.py` (two governors: clean rebase without a worker, conflict and failing check through combination, rebase of a combined candidate onto a further advance with SIGKILL recovery).

A session is not limited in how many integrations or combinations it prepares; one integration operation and one combination preparation run at a time, and each retained request and journal record is bounded in bytes. Background operations publish their compact request ticket before acknowledgement; status polling is bounded to 20 seconds. Shutdown closes execution admission, cancels registered Git jobs and joins outstanding coordination under the existing process watchdog. A dedicated closed-admission rejection proves that no job registration occurred and is sealed as `NotApplied`. Other launch errors do not establish that fact.

**Refused reservation (D144).** `Integrate` asks the server for the reservation before it touches Git. When the server refuses it (the claim the intent was frozen with was released or replaced, a member was revised, another integration holds the members), no reservation exists and no execution was admitted, so nothing can have been applied. The coordinator verifies that the server holds no record of the integration, seals `NotApplied` with the refusal in the host journal and the integration is `NotApplied` for the session: terminal, so it no longer holds the workflow or a drive, and a later `Integrate` of the same ID neither reserves nor launches. The server keeps no record of such an integration, because it never admitted one: `read` with `Integration {id}` answers `Missing` while `IntegrationStatus` answers `NotApplied` with the refusal as its blocker, and `Combine` cannot take it as a source. The session prepares again under a fresh ID. A reservation request that got no answer proves nothing about the server's state; it leaves the integration `Pending`, and repeating `Integrate` asks again. A refusal after execution was admitted, or while the server holds the reservation, also leaves it `Pending`.

`Ready` and `Pending` are not terminal: the session settles a prepared integration by `Integrate`, which either applies it or records `NotApplied`. There is no command that abandons a prepared integration that is still valid without applying it.

The existing `job upload` command acquires exclusive session job ownership and runs a separate reconcile-only operation. Its retained-job adapter rejects execution. It never creates a reservation, rebuilds the completion request or renews an expired ordinary claim. With an existing reservation, an unattempted local intent can be sealed as not applied; an attempted one can only inspect retained execution/incorporation or replay an observation. A missing server record means preparation only, or a reservation the server refused, when no local execution was admitted and the journal holds no observation other than that refusal. Missing counterpart evidence after admission is unresolved.

### Local execution and reconciliation

The host journal holds one coordinator lock per session; its inventory grows with the session's integrations and is read whole by recovery. It forces the intent before server reservation and an execution-admission marker before starting a guardian-owned Git job in a detached workspace. A missing local journal cannot be reconstructed when a server integration already exists. If execution was admitted, recovery only inspects retained execution and target evidence; it never launches that effect again. A crash between admission persistence and process launch can therefore leave an explicit unresolved operation.

The job sends one direct-branch update with full expected/candidate object IDs through Git's `start`, `prepare`, `commit` protocol. Git documents that preparation locks the queued references and aborts when a lock cannot be acquired; commit performs the updates. [Git update-ref manual](https://git-scm.com/docs/git-update-ref).

The observed Git 2.55 implementation prints and flushes an acknowledgement for each successful phase and exits from a failed preparation before reaching commit. CQ classifies a refusal only with settled, fully retained output, a nonzero ordinary exit, exactly the start acknowledgement and the explicit preparation-failure diagnostic. A commit-stage failure stays unresolved unless target incorporation is observed. This classification follows the inspected implementation and is checked against real Git; it is not inferred from a nonzero exit alone. [Git 2.55 implementation](https://github.com/git/git/blob/v2.55.0/builtin/update-ref.c#L555-L614).

After a complete local observation is forced, subsequent runs only deliver or replay server recording. A failed recording and a lost acknowledgement remain distinguishable from an uncertain Git effect. The current checks address process interruption and journal persistence; they do not establish power-loss durability of Git refs and candidate objects. No transaction spans Git and PostgreSQL.

## Combined-candidate implementation contract

The implementation retains the existing roles and local tools. `Combine` requires a source integration resolved `NotApplied`, an explicit combination request identity and the current full claim. Its host-produced artifact binds that request, source integration, owner/project, configured repository/target, frozen observed target, original admitted worker/candidate, exact member revisions and the current fence. Replay must return the same artifact and frozen target; changed input under the request identity conflicts. A pending source integration cannot create this plan.

Same-owner/session claim reacquisition may supply a newer fence when the exact member set and revisions still equal the source intent. Preparation freezes that current fence; later reacquisition requires another plan. Original Worker admission supplies historical provenance, while the active plan claim authorizes new work and result admission. Frozen artifact publication may finish after claim loss, but consumption must reject expired or replaced authority. Reconcile-only recovery may republish already frozen bytes; it cannot renew the claim, refresh the target/fence, create another plan or launch Git. Astra approved this authority distinction; required tests include newer-fence preparation, fence loss after preparation, changed revisions, cross-session consumption, wrong previous Worker and replay after claim loss.

Only `Worker(ResolveConflict)` may consume a validated combination artifact, with the exact original worker as its previous result. Ordinary review corrections in that mode remain supported without a combination artifact. Only the validated plan permits selecting a base outside the existing session-base ancestry check. Both commits must exist in the configured repository and share usable ancestry. A subsequent reviewer receives the new worker handle; it does not resubmit the combination plan as reviewer input.

Prepare the merge and run the harness within one guardian-owned job, in the fresh isolated workspace. A fixed installed shell wrapper supplies fixed Git options and validated IDs, then invokes the harness through positional arguments and `exec`. It must not evaluate constructed command text. Disable hooks, signing, autostash and rerere; isolate Git environment variables inside the preparation subprocess without changing the harness provider environment.

Use `--no-commit` together with `--no-ff`: Git documents that no-commit alone does not prevent a fast-forward from moving HEAD. A conflict can lack individually unmerged index entries, so the file list cannot establish the complete conflict state. [Git merge documentation](https://git-scm.com/docs/git-merge), [Git merge-tree caveats](https://git-scm.com/docs/git-merge-tree#_mistakes_to_avoid).

For the fixed `ort`, non-squash invocation, accept exit 1 only when the workspace began clean without `MERGE_HEAD`, HEAD remains the frozen target, repository/worktree identity is unchanged, and the newly written `MERGE_HEAD` is exactly the original candidate. Pinned Git 2.55 writes that state after selecting a working/conflicted strategy; a strategy failure exits earlier. [Inspected implementation](https://github.com/git/git/blob/v2.55.0/builtin/merge.c#L1692-L1765). Capture must select ordered parents `[observedTarget, originalCandidate]` from the immutable plan and independently validate the merge inputs and unchanged workspace identity. Harness output or mutable Git metadata cannot select parents.

Retain merge diagnostics for the resolver through a fixed child-owned `MergeReport` page under the existing read-only workspace tool. Do not expose arbitrary attempt-assets paths. Plain `tee` does not provide a hard retained-file bound. The selected implementation approach is a bounded-copy mode in the existing guardian binary: precreated private empty regular log, no symlink/reuse, explicit byte budget, and failure on overflow or write/force errors. The wrapper must require copier success and a valid saved merge exit before launching the harness. Missing or malformed status and unavailable diagnostics must not become successful empty output.
