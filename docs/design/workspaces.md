# Local workspace foundation

`WorkspaceService[F]` authorizes project/session ownership and governing or human roles. `WorkspaceRepository[F]` is the host filesystem/Git boundary. The `host` module implements `GitWorkspaceRepository`; the server has no route or role binding that launches it. M2 will bind it into the local supervisor. Workspace contracts remain in the single mutable `cq.api` 0.1.0 model.

## Preparation and admission

Each attempt owns one directory below an explicitly supplied absolute workspace root outside the actual enclosing Git checkout. Both checkout top-level and the workspace root’s existing ancestors are resolved before containment checks; source subdirectories and root symlink aliases cannot bypass placement. A specification freezes project, owning session, attempt, source repository and full commit object ID. An exclusive file lock protects preparation/quarantine for that attempt. A concurrent operation receives an explicit conflict; callers do not automatically repeat an uncertain creation.

Preparation resolves the committed base, persists ownership, creates a detached locked Git worktree, verifies its HEAD and common Git directory, then atomically persists the observation. Worktrees share committed objects, with separate checkout/index state. Governing uncommitted/staged changes are not copied. Checkout hooks are disabled and submodule recursion is disabled. Full submodule support is not implemented.

Admission (`Open` or `Quarantined`) is separate from the observed creation record. The latter contains verified base, Git common directory and observation time. It is evidence of preparation, not a live observation of the workspace after agents run. Quarantine retains that observation and the filesystem. A failed or uncertain creation records quarantine and leaves any directory/registration available for inspection. A pending ownership record is never silently treated as a completed creation. Missing/inconsistent ownership records fail explicitly. Repeated preparation returns the same verified record only for identical ownership/base, open admission and reverified Git top-level/common-directory identity. Replacement or missing worktree identity quarantines the record without discarding its previous observation.

Records use generated codecs, bounded reads, fsync and atomic rename. Restart can read completed or quarantined records; it does not adopt harness processes. Candidate integration, process ownership and proof of termination are M2/M3 work.

## Lifecycle and removal

Admission is `Open`, `Quarantined` or `Removed`. A workspace exists for every job the session launches: the managed governor itself, each child, each host validation check, each reviewer-declared check and each integration's Git job. Candidates are captured as commits under `refs/cq/candidates/<attempt>` in the shared object store, so a worktree is not needed once its result has been collected.

Workspace removal does not depend on shutdown. Claude Code 2.1.285 ends its MCP servers with SIGINT, SIGTERM 100 ms later and SIGKILL after a further 400 ms, so nothing a host starts after the signal can be relied on (D96; the earlier shutdown sweep of D93 was cut after about half a second and left every workspace `Open`). Removal therefore happens at two points, and nothing on the shutdown path waits for one.

**Eager release in the owning session.** `JobSupervisor.release` removes the workspace of a `Settled` job whose record is `Open`; the owner of the job calls it as soon as the last host reader of the tree has finished:

| Workspace | Released | Why the tree is no longer needed |
| --- | --- | --- |
| Child attempt (worker, reviewer, planner, explorer) | when its publication ends `Completed` | evidence files are published artifacts, the candidate is a commit under `refs/cq/candidates/<attempt>`, and the workspace capability ends with the attempt |
| Host validation check | when its output has been captured | the evidence is the retained stdout/stderr; the tree is a checkout of the candidate commit |
| Reviewer-declared check | when its publication has finished or failed | as above; it never ran in the reviewer's own workspace |
| Integration Git job | when the job has settled | the job works on the governing repository; its evidence is under `checkouts/` and `payload/`, and recovery reads only those and the job journal |
| Managed governor (`cq run`) | after `receipt.json` and the final delivery | its result is read from the retained output and assets |
| Workspace of the governing session's own work (I30) | when its publication ends `Completed` with a captured candidate | as for a child; it has no job, so its owner removes it through the workspace service |

A workspace the governing session opened for its own work ([local dispatch](local-dispatch.md#the-governing-sessions-own-work)) is quarantined whenever it is not captured: the session cancelled it, its capture failed (for example because the session committed in it), the claim was lost, the host shut down while it was open, or the session submitted it with no member ready, so that there was no candidate to capture. It is also kept when the server denies the captured result (`The server refused the result: …`). The record's reason begins `The governing session's workspace was not captured and its edits are retained here:` and names the cause; what the session wrote is never removed by the host, and a failed or cancelled attempt publishes its partial work (status and diff) as a failed Worker's does.

A child whose result failed, was cancelled, lost admission or was rejected by the server is quarantined as before, with its admission and directory in `DispatchStatus.workspace`; an `Uncertain` job is quarantined by the supervisor. A child left `PublicationPending` keeps its `Open` workspace until its publication completes. Quarantined workspaces stay until an operator inspects them. A release that fails (for example a Git error) leaves the record `Open`; it is not retried in the session and is picked up by the next startup.

Removing a worktree is bounded at five minutes, the watchdog's drain at `grace + kill + 10 s`. `SessionRelease`, the running session's workspace service, therefore never lets a removal stand between shutdown and the receipt: once the session is stopping (`SupervisorWatchdog.stopping`) a requested removal — a cancelled check's, a cancelled integration job's, the managed governor's — is postponed and returns the `Open` record, and a removal already in progress is no longer awaited (it continues in the background).

**Startup recovery of ended sessions.** `cq host` and `cq run` fork `WorkspaceCleanup.recover` in the background once the session has recorded itself (after `run.json`, before the first MCP request is served), so startup is not delayed. It takes every sibling session directory of the state root that has no `recovery.json` (below), oldest first by the modification time of `run.json`, and examines those whose `run.json` names the same project and source repository; a session of another project or repository is passed over. A directory whose `run.json` is absent, is not a regular file or cannot be stat-ed is not skipped: it comes last in that order and is reported as described under Convergence. A session's host is known to be gone when the exclusive lock on its `journal/owner.lock` can be acquired: every host takes that lock before it writes `run.json` and holds it for its lifetime, and the operating system releases it when the process ends, however it ends. A session whose lock is held is listed under `live` and not touched; that includes a host that holds its lock and has not written `run.json` yet. The lock is held for the whole recovery of a session, which also excludes a concurrent `cq job upload`. For each ended session:

1. Every job the journal still shows unsettled is recorded as `Uncertain` with the diagnostic `cq job upload` gives it (`SessionDelivery.interrupt`): its owner is gone and nothing observed its termination. This needs no server. The receipt reports how many jobs were recorded.
2. If something is left that `SessionDelivery.flush` would deliver (`SessionDelivery.remainder` reads this without changing anything), the retained deliveries are reconciled exactly as `cq job upload` does, with collector authority granted for that session. That covers the governing final publication, a child publication, a run of a reviewer-declared check (`children/*/checks/**`), an attached Pi or Codex usage sample (`pi-usage/*`, `codex-usage/samples/*`) and a retained span (`spans/`). This delivers the `Finish` usage of a session that was killed in its finish sequence. A child whose owner died before sealing its publication never gets a `receipt.json`; it counts as delivered once the `Unknown` outcome that reconciliation commits for it is acknowledged. A session with nothing left to deliver and no integration entry (step 4) requests no grant.
3. Every `Open` workspace is then disposed of from the job journal: an unsettled job's is quarantined (`Owning session ended before the job settled; termination is unconfirmed`); a child's is removed only when its `receipt.json` says `Completed` and is otherwise retained with `Child result is not published as Completed; run cq job upload`; every other settled job's is removed. Removal uses the same identity re-verification and quarantine-on-mismatch as below. A workspace of the governing session's own work has no job. The sweep finds it through the dispatch tickets that no job names: it is removed when its `receipt.json` says `Completed` and quarantined otherwise (`The governing session's host ended with this workspace open; its edits were not captured and are retained here`), and the receipt lists it as quarantined whether this sweep or the reconciliation of step 2 kept it. That reconciliation delivers an `Unknown` outcome for the attempt, whose gap says that its host ended before the work was published. `cq job upload --session` prints every such workspace that still exists, with its directory and reason.
4. What only `cq job upload --session` resolves is read and left alone (`WorkspaceCleanup.unresolved`). For each entry of `integrations/` and `integration-requests/` the server's integration record is read with the session's collector authority; no reservation or observation is sent, no Git update is launched, no work is prepared and no combination is published. The entries that remain are named in the receipt problem together with `cq job upload --session`: an `integrations/` journal whose reservation is `Pending` (or is missing after execution was admitted, or holds another intent), an `integration-requests/` ticket whose reservation exists without a terminal resolution although the session has no journal of it, and a `combinations/` entry whose frozen `plan.json` has no acknowledged publication.

**Convergence.** A session that startup recovery has finished with gets `recovery.json` (`SessionRecovery { outcome, reason, recordedAt, host, build }`) in its own directory, written while its journal lock is held, and every later startup skips it without taking its lock, requesting a grant or replaying a flush:

- `Recovered`: `cq job upload --session` would find nothing to deliver and nothing to resolve, and no workspace is `Open`. An explicit flush of a `Recovered` session acknowledges no batch. Quarantined trees stay for the operator and do not keep the session pending. Neither does a record that was never committed and so can never be delivered or resolved: a child, check or usage sample holding only a partial ticket upload, an `integration-requests/` ticket whose preparation never froze an intent (no journal, no reservation on the server), a `combinations/` ticket without a frozen plan. The marker reason and the receipt state how many of each were retained for inspection; `cq job upload --session` keeps reporting them.
- `Abandoned`: the session can never be examined, because bytes of its `run.json` or of a job record were read and do not parse, decode (malformed UTF-8 included) or validate as that record, and no host holds its lock. This is recorded once, whichever project's host finds it, instead of at every startup of every project that shares the state root.

A session is left unmarked, reported with a problem in the receipt and examined again at the next startup while:

- a record cannot be reached: listing, stat-ing or reading `run.json`, the job journal or a delivery directory fails (an input/output error, however the runtime wraps it; a missing permission), `run.json` or a job record is absent, is not a regular file or exceeds its byte bound, or the journal exceeds its record limit. None of these says anything about the record's content, so none writes `Abandoned`;
- a delivery fails or is left unacknowledged;
- an integration or combination is left for `cq job upload --session` (step 4), or one could not be read or the server could not be asked about it;
- a workspace is retained (`Removal failed`, an unreadable record, a child not published as `Completed`);
- the recovery was cut.

Those cases do not converge by themselves: each startup takes the lock again, requests a grant when something is undelivered or an integration has to be looked up, and reports the problem in its receipt. A session directory without a reachable `run.json` cannot be attributed to a project, so every startup of every project that shares the state root reports it until the record is back or the operator removes the directory. One exception is passed over without a report and without a marker: a directory that holds nothing but `journal/owner.lock`. A host takes that lock before it writes `run.json` and writes everything else afterwards, so such a directory was left by a host that ended before it recorded itself, and it holds nothing to recover or deliver. A fault in one session's examination is that session's problem only: the pass goes on to the later sessions and writes its receipt.

`host` is the contract model version and the executable of the host that wrote the marker. `build` is the source revision that host was built from: `Clean { revision }` when the source tree was exactly that commit, `Modified { revision }` when it had changed, staged or untracked files, and `Undetermined { reason }` when no revision could be read (no Git, or sources that are not the top of their own work tree); a modified or undetermined build is never recorded as a clean revision. The build reads it from `dev/source-revision` at every compilation (`server / sourceBuild` in `build.sbt`) and compiles it in as `cq.server.ProducingBuild`, so the JVM classpath and the native executable that `./dev/check native` builds from that classpath, and `dev/package` then packages, carry the same value. Deleting `recovery.json` makes the next startup examine the session again; `cq job upload --session` ignores the marker.

The recovery is bounded by `WorkspaceCleanup.Default`: five minutes (the receipt then records `deadlineExceeded`) and 4096 examined sessions per startup, applied after the unrecovered sessions have been ordered, so that the oldest are handled first and each startup makes progress; sessions of other projects or repositories are passed over without counting. Its outcome is `workspaces/cleanup.json` in the *starting* session and is logged; it never fails the session. `WorkspaceCleanupReceipt.totals` counts the examined and live sessions, the markers written, the removed, quarantined and retained workspaces, the acknowledged delivery batches, the problems and the sessions not reached (`unexamined`); `live` and `sessions` (per ended session the removed attempts, the quarantined and retained ones with reasons, the acknowledged delivery batches and any problem) list the first entries that fit the receipt's 1 MiB bound. The receipt is written even when there was nothing to recover and when single sessions could not be examined, so an absent receipt means the recovery was cut or the state root itself could not be listed. It may be cut at any instant: each removal or quarantine rewrites its own `workspace.json` before the next begins. A removal that was cut — by the end of the host, or by the watchdog — leaves an `Open` record whose tree is gone, or lacks its `.git` entry, or whose registration is gone as well. The next removal of that record finishes it (below) instead of quarantining it.

**Shutdown.** The finish sequence stops the session's children, integrations, combinations and revalidation rounds with their jobs, writes the receipt (`cq run`) and delivers the `Finish` usage, and only then calls `SessionRelease.finish`, which runs the postponed removals for what is left of the drain less two seconds and then lets the host exit with its own status; a removal still running at that point is left to the next startup. The sequence is safe to cut at any instant. The attached peer still closes on MCP input EOF, owner death, heartbeat or operation deadlines, and on SIGINT/SIGTERM from the owning harness; `AttachedProgram` and `cq run` keep their JVM shutdown hook (`TerminationGuard`), which holds the exit until children are stopped and the `Finish` usage (and for `cq run` `receipt.json`) is delivered. That is an optimisation for harnesses and operators that allow it: when the host is killed first, the next startup's reconciliation delivers the `Finish` outcome instead, as `Unknown` with the interruption gap, and without the Codex response records that a final poll would have collected after the last five-second poll. The supervisor watchdog's drain is `grace + kill + 10 s` after shutdown begins; a host whose finish sequence makes no progress, such as a stalled fsync, halts with exit 75 at that deadline.

Removal reverifies the worktree from inside (`--show-toplevel`, `--git-common-dir`, `--absolute-git-dir`) against the recorded observation and the source repository's common directory, then runs `git worktree remove --force --force` (the second `--force` releases CQ's own lock) and `git worktree prune` from the source repository, and records `Removed`. A workspace whose recorded Git directory no longer matches, including one whose `.git` file still points at a relocated state root, is never deleted: its record is quarantined with a `Removal refused` reason and the directory and registration stay for the operator.

A tree without a `.git` entry is what a cut removal leaves (Git deletes the working tree first and refuses to remove one whose `.git` is missing). Its identity is then taken from the record instead of from inside the tree: the directory is the record's own `workspaces/<attempt>/tree`, the source repository's common directory is the recorded one, and the recorded registration (`<common>/worktrees/<name>`) either no longer exists or its `gitdir` file still names this directory. If so, what is left of the tree is deleted without following symbolic links, the registration (if any) is removed through Git, and the record becomes `Removed`; a registration that names another directory quarantines the record as above. `Removed` records keep their observation and cannot be prepared again.

The startup recovery first prunes the source repository's registrations whose directories no longer exist and logs how many. Git never prunes a locked registration, so entries locked with CQ's own `CQ attempt` reason are unlocked first; other locks are left alone.

## Bounded Git commands

`BoundedHostCommand` drains combined stdout/stderr on a virtual thread, caps retained bytes, and imposes process/output-drain/termination deadlines. It retains the launched process handle and terminates observed descendants on process timeout. Failure propagates and workspace preparation quarantines its result. CLI Git identity lookup uses this helper too. Git callers use an explicit environment with ambient `GIT_*` redirections removed, global/system Git configuration disabled, and interactive prompting disabled. This helper is not the M2 harness supervisor: whole-hierarchy lifecycle, descendant escape/uncertainty handling, collector draining and parent-exit cancellation still require implementation.

## Verification

Shared public-service scenarios run against a manual dummy and actual scratch Git repository. Real-only checks verify separate content/index state, detached HEAD, durable record reads after repository-object recreation, quarantine after Git creation succeeds but acknowledgement is lost, and silent/oversized command output bounds. No harness is launched by these checks. See [evidence](../validation/m1-workspaces.md).
