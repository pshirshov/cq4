# Bounded adaptive execution cohorts

M4 implementation contract after `6669db9`, independently approved by Astra after correction. Implements R16 using the existing four roles, transient worksets, claims, child results and operational usage audit. No new ledger, persistent item owner or model version. The [Planner assessment boundary](../validation/m4-cohort-assessments.md) and [selector foundation](../validation/m4-cohort-selection.md) are implemented. The latter includes structured-evidence normalization and records the remaining connected adaptation and real-evaluation acceptance work.

## Observable contract

Before a managed workflow starts a child, the host considers a bounded pool of selected work for that role/mode. It returns groups with exact member revisions, a decision identity and short reasons. The governor claims one complete group and starts it using those references. Host admission verifies that the execution matches the choice. Full candidate narratives, compatibility comparisons and previous results stay outside the governor's context.

Selection must establish these properties:

- Only selected descendants are candidates. Contextual milestones never introduce sibling work.
- The entire group shares a compatible operation and a common context witness; a chain of pairwise overlap is insufficient. There are two exceptions. A Planner organisation group (`CohortReason.PlannerOrganisation`, rule 1 below) carries no witness and instead requires every member to be organisable within the same workflow roots. An implementation group (rule 3 below) needs no shared producer: its common context is the Planner's Compatible assessment of the exact complete group, and it carries a producer witness only when every member shares one.
- Every member remains separately identified and receives its own outcome.
- A recommendation is neither a claim nor an execution. The ordinary atomic claim still decides concurrent ownership.
- Membership is immutable once execution starts. A new round may produce different groups without changing earlier assignments or spend.
- Decisions expose examined, excluded and unexamined counts. Savings remain unmeasured unless the evaluation has a matched accepted-quality comparison.

## Protocol and ownership

Extend the existing local `dispatch` protocol with an idempotent selection operation. Its input contains a fresh request identity, explicit roots, desired role/mode, optional previous result, guidance/artifact handles and bounded execution limits. Harness choice remains a configured route selected when starting the child. No additional user command or dispatched role is introduced.

The compact reply contains a retained decision handle, candidate counts and a bounded list of choices. Each choice supplies a generated dispatch request identity, exact member revisions, role/mode, previous handle, cohort execution identity, context handles and reason codes. A Start using that identity must match the frozen selection; the parent does not reconstruct narrative input. Replaying an identical selection request returns its existing decision. Reusing its identity with different input is a conflict.

Freeze selection inputs independently of the subsequently acquired claim fence. Start supplies that fence and a configured harness route, verifies current ownership of exactly the selected members, and repeats the existing claim/revision checks before execution and result admission. Acquiring another valid fence neither changes the selection nor resets progress history. Losing a claim never makes a recommendation authoritative.

The host retains complete decision evidence through the existing collector/artifact boundary before advertising choices. Session-local choice state belongs to the supervisor. Restart does not resume its hierarchy; retained artifacts and immutable usage assignments remain inspectable. Direct `cq run` continues to support explicitly assigned work, while workflow runs require selection before new execution. Status, cancellation and existing integration reconciliation remain available.

## Candidate bounds and scope

Initial measurable limits:

| Bound | Initial value |
| --- | --- |
| Selected/context closure | Existing 1,024-item graph limit |
| Candidate pool per round | 32 items |
| Group size | At most four members, below the existing 16-member dispatch ceiling |
| Choices returned per round | At most eight |
| Full candidate content considered per round | 256 KiB |
| Shared input budget | Existing child assembly byte limit, with explicit exclusion before dispatch |

Use snapshot-consistent graph pages and bounded item/claim reads. The host may discover the existing bounded closure through summaries; only the candidate pool receives full content inspection. Fail explicitly on changed snapshots or unavailable data; do not reinterpret them as empty selections. Counts distinguish discovered summaries, candidates whose content was inspected, candidates excluded after inspection, and candidates whose content was not loaded because of the pool/byte limit. Narrower roots remain available when the graph itself exceeds its bound.

The bounded full-content read accepts at most 32 exact revisions and returns fitting views plus explicit omitted revisions. The server visits only those requested records; the host receives at most 256 KiB of encoded candidate views. Ready records incompatible with the requested operation have a separate count; automatic Worker implementation considers tasks. When an inspected pool yields no choices, a separate inspection cursor advances to later candidates without incrementing their offer history.

Use existing readiness reasons for ordinary automatic selection. Planner selection inside a workflow additionally treats a Selected, unarchived, non-terminal entry whose only non-readiness is an unsatisfied `BlockedBy` as eligible: blocking constrains execution, not planning. An explicitly rooted terminal record remains eligible for planning its reopening only while it is not blocked. Other operations keep the ordinary readiness rule. Active claims belonging to other sessions are excluded with their reason. Selection grants no lease; acquisition races return the ordinary conflict and require another round. Standalone review and a supplied exact previous candidate/proposal retain their frozen membership and existing applicability checks rather than silently selecting only the currently ready subset. A frozen member whose draft (title, body, labels, archived flag, content, citations) is unchanged since the recorded revision remains applicable at its current revision: producing derived records or editing references revises an item without changing its content, and the host compares the recorded revision's draft with the current one through history reads before continuation, review and integration. A changed draft still makes the previous result stale. A multi-member Worker continuation of a previous candidate needs no new compatibility assessment, because that candidate was produced for exactly these members: it is offered as `ExactPrevious`. A multi-member continuation of a previous result without a candidate still needs an assessment at the exact current revisions (below), so it is offered as `AssessmentRequired` first.

A Planner may also select an explicitly rooted terminal record to propose a reviewed correction or reopening. It must be unarchived and have no unsatisfied blockers; claim, reservation and content checks still apply. Terminal descendants are not automatically rediscovered, and Worker readiness is unchanged. Selection, start verification and readiness counts use this operation-specific predicate. The graph continues to report the record's terminal state.

Worker Implement and ResolveConflict additionally require every Task member to have a `PartOf` milestone that is Open (an Open milestone is never archived). Selection excludes a Task without a milestone with `CohortReason.NoMilestone` and a Task whose milestone is Complete or Cancelled with `CohortReason.ClosedMilestone`, counts either as excluded and never offers it. StartChoice verification and input assembly, which also covers a direct `Start`, refuse them with "Work refused: T12 has no milestone. A Planner must assign each Task to a milestone under plan review before work starts" and "Work refused: T12's milestone M3 is Complete. Reopen M3 or reassign T12 to an Open milestone before work starts" (the same text with "Cancelled" for a Cancelled milestone). The refusal names both remedies: reopening the milestone, and reassigning the Task to an Open milestone. The host reads each distinct milestone record once per selection, verification or assembly (`MilestoneRecords`); the milestone is not part of the cohort fingerprint. The ledger's [closure gate](ledgers.md#references) refuses closing a milestone over a Ready or Active Task, so a Task reaches this state only by being reopened under a milestone that is already closed. That reopening revises the Task, and an earlier choice then fails verification as no longer current before the milestone is read; the verification and assembly checks refuse a choice or a direct `Start` that names the reopened revision. Explorer, Planner, Worker/Probe and Reviewer dispatch of the same Task is unaffected. An existing Task without an Open milestone stays refused until it is linked to one: by a Planner organisation round (rule 1 below) through a reviewed `PartOf` `Reference`, or directly by a Human or the Governor (see [workflows](workflows.md)). A Task under a closed milestone is also admitted again once that milestone is reopened, or once its `PartOf` is removed and it is assigned to an Open milestone. Under a drive the bound session reopens only a milestone the drive selects; for a milestone outside the drive it reassigns the Task (see [driver](driver.md#write-time-boundary)). The governor does not create the milestone itself.

## Whole-group compatibility

Start with a conservative, language-independent policy. Shared labels, filename overlap and a shared milestone are never sufficient evidence.

1. Explorer, Planner and Worker/Probe may share a direct producer context when every member is selected, ready for the same operation, free of intra-group dependency conflicts (except for Planner groups, which Blocks/BlockedBy never excludes, because blocking constrains execution, not planning) and within the collective input bound. The same producer must be present for every member. Additions are tested against the complete group, not merely the last member.
   Planner organisation (Decision 10): a Planner group may also be formed without a shared producer when every member is organisable, meaning an explicitly rooted Milestone or an entry derived (`DerivedFrom`) from a producer that is itself Selected in the same roots. Such groups carry `CohortReason.PlannerOrganisation` and no producer witness; the Blocks/BlockedBy independence check does not exclude them, so a Planner can propose `PartOf` links to the rooted milestone and ordering links between Tasks across goals. The member bound, collective input bound and fairness still apply. Proposal authority is unchanged: every existing `Reference` endpoint must still be a Proposed assigned member, so a `Reference` cannot link a milestone outside the roots, and a new milestone is created first and linked in a later round. A `Produce` assigns its new Tasks to a milestone directly (see [proposals](proposals.md)). The ledger changes each item at most once per batch, so one proposal links at most one Task to a given milestone; further links take later rounds.
2. Candidate/plan/audit review of a previous result preserves that exact result's member set and candidate/proposal identity. It cannot fuse independently produced candidates into one review. This shares review where the prior execution already established joint context.
3. Fresh implementation uses a stored Planner compatibility assessment for the exact complete group. Without an applicable assessment, selection groups pending ready Tasks of the same selection, up to the member bound, when they are free of intra-group dependency conflicts and within the collective input bound, whatever produced them, and offers the group to a Planner (`AssessmentRequired`); Tasks derived from different Defects can therefore share one candidate. The choice names a producer witness only when every member shares that producer. A Task that an applicable assessment already names is not offered for assessment in another cross-producer group, so an Unknown or Incompatible verdict leaves its members as singletons. An assessment that was started and left no applicable verdict (the Planner failed or abstained, or its result was not admitted or not forwarded) counts as Unknown: the next selection records the group as `Deferred` under its assessment fingerprint and offers each member to the Worker alone as `UnknownAssessment`, subject to that member's own execution history. A group continuing an exact previous result is split the same way, with that result carried as an artifact. Compatible assessments permit an automatic shared Worker choice after structural validation. Unknown or incompatible assessments yield explicit singleton/split reasons. Labels or common checks alone never establish compatible edits or independent acceptance. Existing explicit multi-member worker execution remains supported, with its whole-member claim, isolated candidate, checks and independent per-member review.
4. Conflict resolution preserves the combined plan's exact members and source identity. Regrouping cannot substitute members into that plan. A [host rebase](git-integration.md#host-rebase-onto-an-advanced-target) is not a cohort operation: it dispatches no child, keeps the reviewed result's exact members, and lands a commit no model authored whose only new coverage is the configured checks the host reran on it.

### Planner compatibility evidence

Extend the existing Planner report with bounded optional whole-group assessments and an Assessed member disposition distinct from Proposed ledger mutations. A compatibility-only report requires no fabricated ledger mutation. Each assessment records exact member revisions, Compatible/Unknown/Incompatible disposition, one shared change objective, dependencies and possible interference, and a separate acceptance/validation mapping for every member. Acceptance mappings reference the current frozen criteria; named checks must exist in the configured check inventory. Each assessment covers at least two members and at most the group bound, all within the Planner's assignment. Overlapping proposed groups are rejected rather than silently resolved.

The wire mapping uses zero-based criterion indexes into the exact frozen task acceptance list. Every index must occur exactly once. This supports repeated or large criterion text without copying it into the assessment. Each mapping names its configured checks and includes an explicit inspection method. Host validation uses the materialized original task content and configured check inventory; server result admission independently verifies current task revisions and criterion coverage. Assessment applicability must also compare the original host input's check definitions with the configured ones, not merely match check names, and requires the assessment's Git base to be the intended execution base or one of its ancestors. An integration that moves the target therefore leaves an unused assessment applicable while the assessed member revisions and the check definitions are unchanged; a base that is not an ancestor of the execution base (a rewritten target, an unrelated candidate) does not apply. A member revised since the assessment still needs a fresh one for its group. The host establishes ancestry through `ExecutionBase.ancestor` in the session repository, once per assessment source and selection: it first checks that the repository holds the assessed base (`git cat-file -e`) and then asks `git merge-base --is-ancestor`. A base the repository does not hold, such as one assessed in another clone or a commit since collected, is not an ancestor: that assessment does not apply and a new one is requested. An inspection Git itself fails, for example on an unreadable repository or a missing execution base, fails the selection instead of counting as either answer, and the failure names the assessment artifact and both commits. Several carried assessments can apply at once after the target has moved. The host orders them: an assessment whose base descends from another's precedes it, and among equal or unrelated bases the result the server received later comes first (then the artifact ID). A group that shares a member with a group earlier in that order is ignored. Two verdicts for one group, or two groups naming one Task, therefore resolve to the newest assessment, whatever order the handles were passed in; a Task whose group was ignored and that no remaining group names is offered for assessment again. Code that landed between the assessed base and the execution base was not seen by the Planner: the assessment remains model-declared evidence, and the shared candidate is still checked, reviewed per member and checked again on the commit that lands.

The host reads the admitted assessment result by handle, validates the entire group/revisions and bounds, and retains it with the selection evidence. It treats semantic compatibility as model-declared evidence; it is not permission to mutate, a passing check or task acceptance. A stale, malformed, incomplete, Unknown or Incompatible assessment cannot authorize automatic implementation fusion. One shared validation command never substitutes for the per-member mappings or subsequent independent review.

When ordinary selection has two or more pending ready implementation Tasks but no applicable assessment, it exposes a bounded Planner choice to assess them before selecting a shared Worker. The Tasks need not be related by a producer: being selected together, ready and mutually independent is enough to ask, and the Planner's verdict decides. Installed workflow/Planner instructions request that assessment automatically. Reviewer/Plan accepts either a ledger proposal or compatibility assessment as a reviewable subject; applying a ledger proposal still requires actual proposed mutations. No fifth role or extra user command is required.

## Adaptation and progress

Between rounds, re-read revisions, graph evidence, claims and compact prior outcomes. New producers or discriminating evidence can change the common context witness. An oversized group splits before input assembly. A blocked or failed member is separated from eligible independent work; later results still refer to the original immutable assignment.

When a subgroup needs context from an earlier larger result, carry that result as an artifact handle. Do not put a smaller member set into the old exact-previous chain. A new execution receives its own identity, claim and per-member outcomes; historical group costs retain the old membership.

A prior Planner assignment may partition into its declared non-overlapping assessment groups; the original plan is retained as an artifact. A previous candidate requires explicit continuity. A review that requests changes for some members and accepts the others continues the whole group on that candidate as one `ExactPrevious` Worker choice (D113): the accepted members stay assigned, the worker receives the review as its previous result, whose `report.Review.members` carries each member's verdict and findings, and integration still requires a later review that accepts every member of the corrected candidate. When a Blocked or otherwise excluded member, a group above the member bound or an Unknown or Incompatible assessment applying at the candidate prevents an intact correction, selection returns `CandidateContinuity` instead of silently changing the Git base. A fresh request with the candidate/review as an artifact starts from the current head of the configured integration target (the governing session's base without a target), observed at selection, verification and attempt start, and advertises `FreshFromBase`; continuation and revision attempts keep starting from the previous candidate. The host never derives a new execution base from artifact ordering. The execution base is part of the operative-input fingerprint, so an advanced target head is a changed input that re-offers an otherwise deferred member and invalidates a selection made against the old head. Outside such a whole-group continuation, review-declared accepted members are excluded from further implementation selection while the matching revisions and passing reported checks apply, as is a group whose members were all accepted; this is a phase decision, not ledger acceptance or a substitute for integration checks.

Track selection/execution history within the governing session by member, mode and an operative-input fingerprint. Canonicalize member order, guidance order and evidence order. Exclude selection/request IDs, attempt IDs, fences, timestamps, harness choice and collector envelopes. Include operative item content/references, the exact candidate or proposal content and substantive evidence payloads. Re-uploading identical content under another artifact handle, or merely editing labels/provenance, does not reset deferral. This is a structural content comparison, not proof of semantic novelty.

Include configured check definitions and candidate identity among operative host inputs. A changed validation command is a changed execution condition. Separate assessment applicability from progress: cosmetic revision changes can require exact-revision assessment refresh, but neither revision churn nor refreshed envelopes reset a failed Worker's eligibility. Only substantive assessment/input changes affect that fingerprint.

For host-generated `AssessmentRequired` Planner choices, progress also records the exact member revisions requiring assessment. This permits one assessment per revision set while ordinary Planner and Worker progress remains semantic. Each member uses the whole-group assessment key, so changing one member's revision permits reassessment of the complete group. Selection and Start verification derive this distinction from the retained host choice, including any subgroup. A started assessment is not offered again for the same revisions and input; when no verdict followed, its members fall back to singleton Worker choices (rule 3 above), so an assessment that fails cannot strand them. An earlier assessment's member identities may identify a refresh subject without a common producer; stale revisions cannot authorize implementation. Applicable current groups take precedence over stale alternatives. Independent Astra approved this refinement before implementation; its verification is tracked with the selector evidence.

Structured Validation evidence contributes the declared check, candidate, observed job target/phase/exit/problem and stdout/stderr content digests. Job identities, revisions, timestamps and transcript part handles are publication metadata. Combination evidence contributes repository/target, observed target commit, candidate and member identities, excluding its publication and claim envelope. Collector authorship and internal project/session/candidate consistency are checked before normalization. These comparisons do not establish successful validation or authorize integration.

Validation reached through an admitted result is also normalized, including inherited Worker checks in a Reviewer result. The observation must match the result's collector, project, check name and candidate. Reads share a per-selection cache and the existing artifact byte and selection deadline bounds; at most nine result sources each reference eight observations. Output manifests are read and integrity-checked as immutable artifacts; their bounded content digest is trusted as host collector evidence. Selection does not reconstruct the potentially 32 MiB native output from its parts. Opaque Input/Prompt/Transcript artifacts still compare their literal bodies; this normalization is specific to Validation and Combination evidence.

Record both the group fingerprint and one fingerprint per assigned member, so changing the requested grouping cannot reset an unchanged member's history. Per-member fingerprints project independent feedback onto that member while retaining genuinely shared candidate and check conditions. Feedback about one member does not by itself enable retries of another.

An unchanged unsuccessful assignment is not repeatedly eligible. A changed operative item input, new admitted Explorer/Probe observation or independent review feedback permits reconsideration. A worker's own unchanged failed result is not new evidence authorizing its retry. Already produced work is not repeatedly selected for the same phase merely because integration has not changed the task's status. The reply explains deferred work and the condition needed to reconsider it.

An attempt that left no result has not executed its input in this sense (D145). When a selected child fails with no result and its receipt advises `Retry` (phase `Failed`: malformed output, a report that violates a shape rule, a rejected admission, a failed process), the supervisor publishes the receipt's fault as a `text/plain` Evidence artifact of the governing attempt and releases the group and member fingerprints that the attempt recorded (`CohortFailure.fault`, `CohortProgress.finished`). The next Select offers the same input again, as a new choice with its own ticket and receipt, and appends that artifact to the choice's `artifacts`, so the retried child reads the fault. The artifact is context, not operative input: selection and Start verification leave it out of the fingerprint, so progress keeps comparing the input that failed. The host sets no retry count. When an attempt ends in the same fault text as the attempt before it on the same input, that is an unchanged failure: the input stays deferred until an operative input changes. The host reports how every child attempt of a driven run ended, with the group fingerprint of its input, to the server (see [driver](driver.md#attempt-outcomes)): under a drive the unchanged failure stops the driver with `Failure`, a cycle that changed nothing and left an input offered again continues the drive, and the same input failing a second time before any cycle changes something stops it with `Failure` whatever the fault texts. An attempt with an admitted result, whatever it reports (Abstained, ChangesRequested, Blocked, a Worker's own Failed disposition), keeps the deferral above, as does a cancelled attempt (a cancellation by the Governor or by the host's shutdown is no fault of the child, so it publishes nothing and two of them are not a repeated fault), an attempt whose outcome is `Unknown` or whose publication is pending, and one whose fault could not be published. The release and the publication run before the child's terminal status becomes visible: until then `Status` reads the child as `Publishing`, so a Select that follows a `Failed` status finds the input already released (`DispatchExecution.observed`). A failed `AssessmentRequired` Planner is not retried: its members fall back to singleton Worker choices as described above.

Choose least-attempted eligible members, then least-offered members, then their first-seen sequence and deterministic ID tie-breaking. Update offered history only for choices actually returned; inspecting an item without returning a choice cannot penalize it. Preserve this session-local history across graph snapshots and new selection request IDs. New arrivals do not displace equally eligible unoffered older work. With 32 inspected singleton candidates and eight returned choices, the next rounds offer the unreturned candidates before re-offering the first eight. Report remaining/unexamined counts. A blocked group cannot monopolize the next round. A governing session is not limited in how many selections it makes or children it starts; only the number of children active at once is bounded. Cancellation and exhausted limits yield an explicit remaining-work summary.

## Usage and inspection

Freeze the chosen execution identity and member set in the existing Assignment when a child actually starts. Shared assignments count once and expose references from every member. A following exact-member review may retain the same cohort execution identity; a split or regroup creates a new one. Unused recommendations produce no fictitious attempt or spend. Governing selection overhead remains unattributed unless an observed boundary supports narrower attribution.

Retain the decision artifact link with the child ticket and expose it in bounded inspection. Record common witnesses, singleton/exclusion reasons, pool limits, exact revisions and applicable prior result handles. Usage summaries and evaluation reports consume the existing audit. Display actual shared/direct usage and coverage; do not invent a per-member split or equate fewer prompts with measured token savings.

## Verification

- Shared dummy/PostgreSQL cases: common whole-group producer; one assessment across producers, fused on Compatible and split on Unknown; pairwise-chain rejection; labels/milestone-only rejection; contextual sibling exclusion; blocked/claimed members; revision drift; bounded scans and collective byte limits; exact whole-group compatibility/acceptance/check mapping and malformed/stale assessment refusal.
- Actual supervisor fixtures: idempotent selection/start, mutation of choice membership/mode rejection before ticket/job creation, automatic shared exploration/planning, Compatible assessment → shared implementation/validation/exact-group review, Unknown assessment → singleton, unchanged-failure deferral despite fresh IDs/fences/harness/reordered handles, 32-to-eight fairness across changing snapshots, split/regroup without historical usage changes, per-member mixed outcomes and explicit unexamined counts.
- Assessment applicability across a moved target: an assessment at an ancestor base still fuses its unchanged members, a diverged base or changed check definition asks for a new assessment, and a revised member asks for one for its group only. A base absent from the repository is no ancestor (`CandidateWorkspaceLocal`); a failed inspection names the artifact and the commits; conflicting and overlapping carried assessments resolve to the newest base, and at one base to the later result, in either handle order.
- An assessment without a verdict: after the assessment choice starts and no assessment is recorded, the next selection offers every member alone, for unrelated Tasks, for a same-producer pair and for a continuation of a previous result without a candidate; a member whose own Worker already ran stays deferred.
- An attempt without a result (`CohortProgressLocal`, `CohortSelectionDummy`): after a `Failed` receipt with no result and `next` `Retry` the same input is offered again with the fault among the choice's artifacts and passes Start verification; a different fault is offered again with the newer artifact; the same fault twice in a row stays `Deferred`; an admitted result stays `Deferred`.
- Progress/applicability separation: a cosmetic member revision triggers assessment refresh while the unchanged failed Worker stays deferred; a substantive configured-check change permits reconsideration.
- Real harness corpus: a related multi-item case exercises a shared investigation/planning/review execution and subsequent independent acceptance; collect actual hierarchy usage and retain singleton reasons where work cannot safely share execution. Reuse existing consumer quality oracles and the shared audit.
- Independent Astra design and implementation review before calling this R16 complete. Full M4 still requires worked process examples, live named reviewer checks and all nine refreshed routes.
