# Local child dispatch

The supervisor role exposes a private loopback MCP endpoint alongside the scoped domain MCP endpoint. The server owns durable domain state and artifacts; this local host owns subprocesses, workspaces, prompt assembly and publication. All contracts remain in the single mutable `cq.api` 0.1.0 model.

## Parent and child boundaries

The governor receives `GoverningInput`: project identity, configured model routes, check names, process limits and the human request. Its local `dispatch` tool provides these basic generated commands:

- `Start`: `DispatchRequest` with exact item revisions, guidance revisions, artifact handles, optional prior result handle, claim fence, harness, role/mode, and process limits (startup, heartbeat, termination and retained output; a child has no execution deadline).
- `Status`: owned attempt ID and a wait from zero to 20 seconds.
- `Cancel`: owned attempt ID. Stop intent is applied immediately, with journal/cancellation work performed independently.

Managed dispatch adds `Select` and `StartChoice` for [adaptive cohorts](cohorts.md). `Revalidate` reruns the failed checks of an admitted worker result ([revalidation](reviewer-checks.md#governor-requested-revalidation)). `PrepareIntegration`, `Integrate`, `IntegrationStatus`, `Combine` and `CombinationStatus` provide [reviewed integration and combination](git-integration.md) through the same tool.

There are no prompt/result narrative fields in the dispatch request. Identical request replay returns the same attempt; a changed request using the same ID conflicts. A governing session may run up to four active children at once, provided their member sets are disjoint (each child runs under its own claim), and at most 32 children in total. Member, guidance and artifact limits remain those of [input materialization](dispatch-input.md). Dispatch start waits at most one second for ticket persistence; a missed acknowledgement disables admission and requests cancellation.

The host resolves input, loads the installed instructions for the assigned role, publishes input/prompt artifacts and launches the configured harness in a detached workspace. Claims are renewed every 20 seconds for three minutes. Claim ownership/membership and exact assigned revisions are checked again before result admission. Child limits cannot exceed the governing configuration. Configuration selects every model/provider explicitly and verifies the installed harness version.

Children receive only the local `workspace` capability and their scoped domain read tools. Direct attempts to call local dispatch or mutate ledgers are denied. The workspace tool lists at most 200 entries or reads at most 8,192 Unicode code points. Files are bounded to 256 KiB of strict UTF-8; directories are bounded to 10,000 entries. Absolute paths, parent traversal, Git metadata and symlink traversal are denied. This implements the cooperative-agent misuse boundary; it does not claim adversarial operating-system isolation.

## Candidate and validation evidence

Worker reports are checked against their assigned identities and role. A `CandidateReady` report triggers host Git capture: verify the original worktree/common-directory identity and fixed HEAD, stage the isolated tree, reject submodules, write a commit with the frozen base as parent and atomically create an attempt-specific candidate ref. The commit message names the assigned members with their titles and known producers, carries a `CQ-Attempt` trailer and, for a combined candidate, the source integration in the body and a `CQ-Integration` trailer; the author stays the host identity. A worker that changes HEAD loses admission. Neither the governing checkout nor its index is used for capture.

`SupervisorSettings.checks` contains up to eight named `ValidationCheck` records: `name`, argument-vector `command`, `executionMillis`, `retainedOutputBytes` (the bound of the published stdout/stderr transcripts; a check is not stopped for its output size), `attempts` (1–3) and `revalidations` (0–3). Commands are host configuration, not model-supplied shell strings. Each runs through the guardian in a separate workspace rooted at the candidate. Output manifests and `ValidationObservation` retain the exact command, candidate and process outcome. Unknown cleanup rejects child result admission; ordinary failed checks remain explicit failed validation evidence and direct the parent toward revision. No checks means no host checks were performed.

### Intermittent checks

A check that fails is run again on the same commit, in a fresh workspace, until it passes or has run `attempts` times; `attempts: 1` keeps the single run. Every run publishes its own `ValidationObservation` and output. The check's `ValidationEvidence` names the last run in `artifact` and the failed runs before it in `failures`. A check that passed on a rerun is *intermittent*: its state is `Passed`, it does not block review or integration, `ChildCounts.validationIntermittent` counts it, and its failed runs stay retrievable by handle. A check that fails every run ends `Failed` after exactly `attempts` runs. A run whose cleanup is unconfirmed (`Unknown`) is never repeated, and a stopped child or closed integration admission starts no further run. There is no quarantine or skip list: the bound is the only relief, and a check that needs its reruns is visible in every result that used them.

A failure that outlasts its automatic reruns can still be rerun once more on request: see [governor-requested revalidation](reviewer-checks.md#governor-requested-revalidation).

The same policy applies wherever the host runs a configured check: worker candidates, the checks a candidate reviewer requests (see [reviewer checks](reviewer-checks.md)) and the merged commit of a [host rebase](git-integration.md#host-rebase-onto-an-advanced-target). Integration cites the failed runs of the evidence it relies on in a second host-observed Task evidence entry, after the entry that cites the passing observations; host preparation and server reservation verify that each cited failure is a settled failed run of that check on that commit by the evidence's author.

The full immutable `ChildResult` contains request, candidate/base, structured per-member report and validation handles. A reviewer receives the previous result directly from its handle and reads that candidate through its assigned workspace. Reviewer outcomes remain model declarations; neither an accepted review nor a completed attempt constitutes final semantic acceptance or branch integration.

The parent receives a `DispatchStatus` of at most 12 KiB: status, owned IDs, per-outcome counts, next action, optional 300-code-point blocker, result handle, publication coverage, the child's workspace state and `quietMillis`. `workspace` is absent while no workspace has been prepared for the attempt; once the child publishes it carries the `WorkspaceAdmission` (`Open`, `Quarantined`, `Removed`) and, for a retained `Open` or `Quarantined` workspace, its directory, so a governor can inspect a quarantined tree without reading the session's workspace records. The live status is updated again after publication: a server admission rejection quarantines the workspace, and a `Completed` attempt's workspace is removed at once (see [workspaces](workspaces.md)); the sealed `receipt.json` keeps the state at publication. `quietMillis` is the time since the child's running job last wrote output and is absent otherwise (always in a sealed receipt); the host never stops a child for being quiet, and the governor reports a long-quiet child to the operator instead of cancelling it (see [process guardian](process-guardian.md#deadlines-that-stay-and-deadlines-that-went)). Full successful narratives stay behind the result handle. Explicit bounded artifact reads support necessary semantic drill-down. This bounds dispatch traffic; actual model token efficiency still requires repeated consumer evaluations.

## Delivery and shutdown

Every child registers its frozen assignment and parent-linked attempt in the operational usage audit before launch. A multi-member assignment is shared attribution with a frozen cohort identity. Native collectors and immutable delivery batches use the same mechanism as the governing attempt. `cq job upload --session ...` replays both governing and child queues; it does not launch work. Publication failure with an existing spool returns `PublicationPending`, hides the result handle and requests delivery recovery.

When the governor ends, the host requests child termination and joins normal collection/publication. A supervisor-only watchdog also observes the governor's in-memory guardian state independently of journal persistence. It is acquired before the job resources and disarmed only after their finalizers complete. It has no deadline while the session runs. Governor termination, an owner signal or failure-path finalization begins shutdown and arms a deadline of grace + kill + ten seconds; repeated shutdown cannot extend it.

Expiry forces the supervisor process to exit **75** without waiting for shutdown hooks or blocked I/O. This is an **unresolved shutdown**, not proof of process settlement, durable quarantine or delivered usage. It fences all retained JVM continuations. Guardian control-pipe closure separately starts bounded descendant cleanup; that additional drain is not included in the supervisor-exit claim. Preserve the entire session directory and inspect/reconcile unfinished records before reuse. Any earlier receipt describes the observation at its timestamp and does not override exit 75. Interrupted pre-publication attempts are reconciled by `job upload` with immutable partial evidence, explicit unknown outcomes and quarantine; see [recovery](../validation/m2-recovery.md) and the [operations guide](operations.md).

Reviewed integration/combination, interrupted delivery recovery and real consumer evaluation are implemented and independently reviewed in [M4](../validation/m4-review.md). Recovery does not reconstruct a running governor or resume its dispatch service; the selected lifetime model permits hierarchy termination with its owner. Interactive collection retains the [declared harness limits](../drafts/20260926-usage-observability.md). Packaged live verification and human acceptance remain tracked in [M6](../validation/m6-package.md).
