# Operational usage audit

The `UsageService[F]` / `UsageRepository[F]` boundary implements accounting separately from `LedgerService`. PostgreSQL stores immutable assignments, attempts, meter definitions, observations, attempt outcomes and host spans. Mutable meter projections and observation-head pointers are derived accounting state. These tables are outside the fourteen workflow ledgers. No usage operation creates an item revision or ledger change event.

All types remain in the single mutable `cq.api` 0.1.0 model. Breaking development changes are permitted; version bumps require explicit user instruction.

## Identity and attribution

- Assignment identity freezes project, member IDs, direct/shared/unattributed classification, optional cohort execution and optional evaluation/scenario/assessor identity. Direct work has exactly one member and may belong to a cohort execution without becoming shared; shared work has two or more; unattributed overhead has no members. Registration checks that members exist in the authenticated project. Archive and later regrouping cannot alter an assignment.
- An attempt freezes assignment, parent attempt, session, role, harness/provider/model, the reasoning effort it was launched with (absent when the launch stated none), collector version and start time. A retry that performs model work gets a new attempt. Repeated registration of the same identity/content is idempotent; changed content is a conflict.
- A meter identifies one contributing counter stream within an attempt. It freezes increment/cumulative semantics and the baseline for resumed cumulative counters. A counter reset requires a new meter. Increment meters have zero token baselines and no cost baseline.
- An observation has a UUID, native source identity/position, occurrence time, raw counter fields, native inclusion semantics, cost basis, completeness/gaps and optional evidence artifact. Receipt time is assigned by the service. Uploads retain both raw and normalized numerical evidence. Host callers register meters and upload observations; the governing model does not forward these values.

Task views return direct totals and references to shared assignments. Shared totals are explicitly separate and must not be added across task views. Project/cohort/session/evaluation views visit each matching meter once. A declared work assignment is not a provider measurement of causal cost for individual members.

The report returns at most 200 shared assignments (identity, frozen members, attribution, cohort and evaluation scope) and an explicit `sharedAssignmentsTruncated` flag. Meter aggregation continues over all matching pages. Observation drill-down has pages of 1–200 entries with a 512 KiB encoded byte budget. Attempt and outcome-history drill-down use the same row/byte bounds. `status attempts` lists assignment/execution identity, attempt metadata and the effective outcome, including attempts without meters. The list is ordered by start time, newest first, with the attempt ID breaking a tie (D162); the usage view shows the same order, because it reads the same selection. A page continues after the attempt that ended the page before it (`after`), whose start time the server reads, so the continuation key is the pair of start time and ID and no page repeats or skips an attempt; an `after` that is no attempt of the project is refused as `Invalid`. The start time is read from the attempt's stored body, so each page sorts the attempts its filter matches: no index serves this order. The continuation requires the original audit snapshot cursor; concurrent audit changes require an explicit restart. `status outcomes --attempt UUID` traverses append-only outcome history in server-sequence order.

## Normalization and corrections

Normalized input includes cache reads/writes. Normalized output includes reasoning. Cache/reasoning counters remain available as subsets; total tokens add input and output only. Raw fields remain unchanged in the observation record. A missing cache category cannot silently become zero when converting exclusive input into inclusive input.

Each counter distinguishes observed, estimated, missing and unsupported values. Observed/estimated require a nonnegative integer; missing/unsupported omit it. Summaries expose known counts, unknown contribution counts and estimated contribution counts. A partial total retains any known input/output lower bound and an unknown marker. Measured zero has zero unknown contributions. Attempts without meters and meters without observations are explicitly incomplete. Reports separately count running attempts, open attempts, unknown process outcomes, and attempts whose effective outcome reports coverage gaps. The last two may overlap and must not be summed as distinct attempts.

An attempt without an outcome is **running** or **open** (D150). It is running when a CQ host launched its process and observes it: every child, and the governing attempt of `cq run`. `InstallationInfo.managedAttempts` counts exactly these over the installation. It is open when it is the governing attempt of an attached session (no parent, role Governor, the attached collector label; `AttemptObservation` in `core`): that attempt is the operator's own harness, CQ launches no process for it, and its outcome is `Unknown` even when the session ends in order. The server holds no fact that tells a live attached session from one whose host was killed before its final delivery: it has no session record, a session may hold no claim, and a host's credential can be granted again at any time. It therefore reports such an attempt as started with no outcome delivered and never as running, and it does not count attempts whose session is known to have ended, because that is not derivable. `AttemptCoverage.open`, `PhaseUsage.open` and `AttemptView.observed` (false for an attached governing attempt) carry the distinction. The governing attempt of an attached session is registered when the session first does governing work, not when its harness opens the MCP connection (D160): at the first tool call, whatever the tool and whether it reads or writes, at the first usage record of a Pi response, or at the first request to the Pi driver. A read counts because only the session's model or its operator makes a tool call, and because usage observed for the session is stored under this attempt. What a harness sends by itself when it opens the connection registers nothing: `initialize`, notifications, `ping`, `tools/list`, a listing of resources or prompts, which the host does not serve, and the Pi extension's question for the session directory. The attempt's start time is the time of that registration. When the server cannot be told (an error or a timeout on the assignment or the start), the request that asked for the registration is answered with that failure, the host keeps serving, and the next governing request registers again with the record the first try wrote, so the server learns of one start; the first governing request is allowed the two server calls of the registration on top of its own deadline. A session counts as recorded once both calls succeeded, and only a recorded session delivers a Finish. A host that ends in order before any governing work has told the server of no attempt and removes its session directory, which held nothing but its lock. A host killed at that point leaves the directory with the lock: the startup recovery of a later host removes it once it holds that lock, and until then `cq job upload --session DIR` reports that no session is recorded in it. A host whose registration failed and that ended without another governing request leaves the record and the undelivered start; recovery or `cq job upload` delivers them and closes the attempt as `Unknown`. An open attempt is closed by the host's final delivery, by the startup recovery of a later host of the same project and repository that finds the session directory under its session root, or by `cq job upload --session DIR`; each records `Unknown` at the time it runs. That recovery runs once the later host has recorded its own session, so a harness that only opens the connection recovers nothing. [Closing open governing attempts](../interactive.md#closing-open-governing-attempts) is the operator procedure. A complete observation does not establish complete attempt coverage; cancellation alone does not establish missing usage.

Costs use exact decimal strings, currency, provider-estimate/price-table/actual-billing/unknown basis and optional pricing version. Price-table estimates require a version. Totals remain grouped by attribution, currency, basis and pricing version; billing and estimates are not combined. Present pricing versions are nonblank, at most 300 characters and contain no NUL. Absent versions have a distinct group; an empty present version is invalid. Monetary arithmetic uses exact decimal addition/subtraction without a fixed precision context. Unknown costs have no amount or currency and are counted separately. No subscription price or missing monetary value is converted into a billing claim.

For increment meters, each source position contributes once. For cumulative meters, the greatest source position replaces the previous cumulative contribution after subtracting the frozen baseline. Older delivery is retained without inflating the current total. Uncorrected decreases in cumulative tokens or cost are rejected.

A correction appends a new observation at the same meter position and must name the current observation it supersedes. The original remains immutable. The effective head and the affected meter projection change in the same transaction. Repeating an observation UUID returns its original receipt; repeating the same contributing source-position content also returns the existing receipt. A conflicting UUID or an unlinked replacement is rejected. Correction retries cannot apply the delta twice.

Attempt outcomes are immutable records with authenticated actor, receipt time and server-assigned sequence. The first outcome has no `supersedes`; each correction must name the current outcome request. An accepted correction becomes effective by server sequence, independently of client finish timestamps. Retrying any already recorded request returns its original value without advancing the sequence or changing the effective outcome. Only an explicit authorized outcome correction changes its gaps; late observations do not clear them. Previous outcomes remain traversable through the bounded outcome-history view.

Overlapping aggregate/component evidence can be uploaded as `Detail` against the same meter with an explicit exclusion reason. It remains in the raw audit and does not contribute to the meter total. Installed-harness collectors select the authoritative contribution stream from observed harness semantics; [native collector evidence](../validation/m2-collectors.md) and [live evaluation evidence](../validation/m4-review.md) establish that separately from synthetic accounting fixtures.

## Phases and host spans

`Usage.Phases` reports, for a filter, one `PhaseUsage` per phase that has an attempt or a span: attempts, running attempts, open attempts, host spans, Running host spans (`runningSpans`), wall time, token totals and grouped costs. Every attempt carries its `UsagePhase` (Govern, Explore, Probe, Plan, Work, Review, and Combine for a conflict resolver). Wall time is the sum of `finishedAt − startedAt` over the phase's attempts with an outcome and over its spans; a running attempt is counted in `running`, an open one in `open`, a Running host span in `runningSpans` (and in `spans`), and none of them adds wall time. `running` counts attempts only and `runningSpans` spans only; `cq status` and the browser table show their sum as “Running”. Wall time is busy time per phase, not elapsed time: phases overlap (the governor's attempt spans the whole session, a reviewer waits for the checks it requests, an integration contains the checks of its rebased commit), so the rows must not be added up.

A `PhaseSpan` is host time outside any attempt. It has an identity, the assignment it belongs to, the session, a phase (Check, Combine, Integrate or Await), start and finish times, an `AttemptState` and, on a Check span, the optional name of the configured check it ran (`check`). It carries no tokens and no cost. Registration (`HostUsage.Span`, Collector/Human scope) requires a registered assignment, one of the four host phases and `finishedAt ≥ startedAt`; a Check, Integrate or Combine span may be registered Running, with `finishedAt = startedAt` (it has not finished, so it adds no wall time); a name is refused on an Integrate or Combine span, and a blank name, one longer than 300 characters or one containing NUL is refused on any span, each without advancing the audit cursor. A Check span without a name is accepted. A span of the phase Await is described under “Waits on the operator”. A span of the phases Check, Combine and Integrate is registered Running when its work starts and finished once when it ends (“Running host spans” below); it never changes otherwise. Spans are stored in `cq_usage_spans` and are part of project archives.

What the host records:

| Work | Span | Times | State |
| --- | --- | --- | --- |
| One run of a configured check: on a worker's candidate, each rerun of a failed run, a reviewer-declared check, a governor-requested revalidation round, a check of a rebased commit | Check, identity derived from the check job | The job's registration (registered Running then) to its last recorded transition (its settlement) | The job's outcome: Completed (exit 0), Failed, Cancelled (stopped by its owner, including a run interrupted by a lost claim) or Unknown (unconfirmed cleanup) |
| One integration | Integrate, identity derived from the integration ID | `PrepareIntegration` to the resolution; registered Running once the reviewed worker, and so its assignment, is known | Completed for Recorded; Failed for NotApplied and for a failed preparation; Cancelled for a discarded integration |
| One combination preparation | Combine, identity derived from the request ID | The first `Combine` request to the published plan; registered Running as soon as the source integration names the original worker, and so the assignment, is known, before the preparation claims, reads members or observes the target | Completed when Ready; Failed when the preparation failed before its plan was frozen; Unknown when the owner shut down with its publication pending, or when recovery or `cq job upload` found it Running |
| One wait of an attached governing session on the operator (an Open Question or a Requested Operator Action) | Await, on the assignment of the governing attempt; identity derived from the session, the awaited item and the start of the wait | The host observing the wait begin to the last time it observed the session still waiting; the wait is registered Running when it begins, observed again whenever the blocked items grow and at least every five minutes, and ended once | Completed when a person settled the item; Cancelled when the session released it or ended while waiting; Unknown when recovery or `cq job upload` found it Running |

- **Running host spans.** The host registers a Check, Integrate or Combine span with state Running when the work starts and finishes it once, so a read during a check or an integration sees it, and a host that dies before its publication leaves a Running span instead of nothing. The fixed fields are the identity, the assignment, the session, the phase, the check name, the parent (“Span parent” below) and the start time (for a check, the `createdAt` of the job record). Registration of a host span that already exists follows these rules, in this order:
  1. A registration whose fixed fields differ from the stored span is refused (`Invalid`).
  2. Identical content returns the stored span (replay).
  3. A terminal registration with `finishedAt ≥ startedAt` for a stored Running span finishes it. This happens once.
  4. A Running registration for a terminal span returns the stored span unchanged: a start replayed after the finish is not a conflict.
  5. A terminal registration for a terminal span with another finish time or state is refused as a conflict.

  Only a first registration and the finish (rule 3) advance the audit cursor; every replay and refusal leaves the stored span and the cursor unchanged. A terminal span with no earlier Running registration is accepted. The rules are `cq.core.HostSpans`. The phase report counts a Running span in `spans` and in `runningSpans` of its row and adds no wall time for it; once finished it adds `finishedAt − startedAt` and leaves `runningSpans`. The per-check report lists a Running run under the state Running with no wall time, so its runs and wall time still equal the Check row. Counting a Running span to the read time belongs to the unit report. A backup of a project is refused while a Check, Integrate or Combine span is Running (as for a running attempt: settle the work, or let recovery or `cq job upload` close it); a Running wait on the operator is carried as it stands.
- **Span parent.** A `PhaseSpan` has an optional `parent` (`SpanParent`) that names the unit that requested the span: an attempt (`SpanParent.Attempt`) or another span (`SpanParent.Span`). It states who requested the span and nothing more: it does not state that the parent waited for it (a reviewer's check request returns after at most 20 s while the check goes on, and children run beside the governing attempt). The time accounting uses it to compute a unit's own time. The parent is a fixed field of a span, of a Check, Integrate or Combine span and of a wait alike: a registration for an existing span with another parent, with a parent where none is stored, or without the stored parent is refused (`Invalid`), and the Running registration and the finish of one span carry the same parent, as do recovery and `cq job upload` when they close a span as Unknown. An attempt named as parent must be a registered attempt of the project (otherwise `Missing`); a span named as parent need not be registered yet, because the start of a host span may be retained and replayed later, so a child's start can reach the server before its parent's; a span that names itself is refused (`Invalid`). Every refusal leaves the stored span and the audit cursor unchanged, and the stored span returns its parent wherever a span is read. The phase report and the per-check report do not change. The host sets the parent at each site:

  | Span | Parent |
  | --- | --- |
  | Check of a rebased commit | the Integrate span of that integration |
  | Reviewer-declared check (and each rerun) | the reviewer's attempt |
  | Governor-requested revalidation round | the governing attempt |
  | Integration | the governing attempt |
  | Combination preparation | the governing attempt |
  | Wait on the operator | the governing attempt |
  | A worker's candidate check and each rerun | the governing attempt |

  A worker's candidate check names the governing attempt, not the worker's attempt, because it starts after the worker ended and the governing session's host runs it when the child settles. Spans stored before the parent existed carry none (the PostgreSQL repository keeps the parent in the stored span body; the update step of an installed database adds it as null). Project archives carry the parent inside the stored span.
- **Check name.** The host sets the name of the configured check (`ValidationCheck.name`) on every Check span it records: a worker's candidate check, each rerun of a failed run, a reviewer-declared check, a governor-requested revalidation round and a check of a rebased commit. Spans stored before the name existed carry none.
- **Per-check report.** `Usage.Checks` (result `UsageChecks`, a `CheckReport`) takes the same filters as the phase report (project, Task, cohort, session, evaluation) and returns one `CheckUsage` per check name and `AttemptState`: the number of runs and their summed wall time (`finishedAt − startedAt`). Spans without a name form one group with no name (listed first). Entries are ordered by name in UTF-8 byte order, then by state name, and at most 200 are returned with an explicit `truncated` flag. In one read snapshot the runs and wall time over all entries equal the `spans` and span wall time of the Check row of the phase report for the same filter; the report carries the audit cursor of that snapshot. Project archives carry the name inside the stored span.
- **Display.** `cq status phases [--task|--cohort|--session|--evaluation RUN [--scenario NAME]]` prints the phase report and then one row per check name from `Usage.Checks` for the same filter: runs, runs per outcome (Completed, Failed, Cancelled, Unknown) and total wall time as `h:mm:ss`; `--json` prints the two typed results one per line. The browser usage view (project, Task and session scopes) shows the same rows as the table "By check" next to "By phase". Spans without a name are one row, `(unnamed)`, listed first. Check rows of different names overlap in time and must not be added up, like the phase rows. A truncated report (more than 200 entries) is announced after the rows and its figures are lower bounds. The phase rows and their note are unchanged.
- **Assignment.** A span belongs to the assignment of the dispatch whose members the work covers: a worker's or reviewer's own assignment for the checks run for that child, and the original worker's assignment for what the governing session runs on its result (revalidation, integration with the checks of its rebased commit, combination preparation). The governing session finds that assignment in the dispatch ticket of the child that produced the result. A check that covers several members therefore lands once on the Shared assignment that holds them all; a task filter for any member includes it, as it includes that assignment's attempts, and nothing is divided between members.
- **Work excludes Check.** A child's attempt ends when its native job settles, not when its result is published, so a worker's host checks are Check time and not Work time. A reviewer's declared checks run while the reviewer waits for them: that time is in both Review and Check.
- **Unresolved work.** An integration that is Ready but never applied when its owner shuts down ends as Cancelled, a Pending one as Unknown, and a combination whose publication is still pending as Unknown; each ends at the time the host last finished working on it, not at the shutdown. Before its members are known (the reviewer handle or the source integration was refused) the work has no assignment and records no span.
- **Delivery.** Spans travel in the same immutable delivery batches as attempts, so recovery replays them and the identity makes the replay idempotent. Every Check, Integrate and Combine span has its own queue under `spans/` in the session directory, named by the span's identity, and holds at most two immutable batches: the start (the span Running) at sequence 0 and the finish at sequence 1. The start is retained when the work starts and sent in the background: a start that cannot be delivered neither fails nor delays the work, it stays retained and is replayed. The finish is retained when the work ends and sent with the queue; retention never waits for a send, and a batch another sender of the process has in flight is left to it, so a start the server holds up does not delay the finish (the server then receives the finish first, and the start that follows is a replay by rule 4). The Combine start is registered as soon as the source integration names the original worker, before the preparation claims, reads members or observes the target. A worker's check spans are also sealed with its publication and a reviewer-declared check's span with that check's evidence (the finish is retained in the queue before it is sealed, so both carry the same record); a replay of either is idempotent by rule 2 or 4. A send that fails leaves the batches retained; the session's final delivery and `cq job upload` send them.
- **Interrupted work.** A host that ends after a start was delivered and before the finish leaves the span Running on the server. The startup recovery of a later host and `cq job upload --session DIR` close every started span whose finish is not retained as Unknown, ending at the time they run (not before its start), as they close the open governing attempt; a span already finished is left as it is, and a started span the server never received is delivered together with its closing finish. Such a span ends at the recovery time, not at the time the work stopped: the overstatement is the one attempts reconciled by recovery have.
- **Residual gap.** Work whose start never reached the server (the host died, or the server was unreachable, before the start was delivered) is absent from a read until the start is delivered; a read of that time sees nothing of it.

### Waits on the operator

A span of the phase Await carries an `AwaitedSpan`: the awaited item, the blocked items, a truncation flag and an observation number (starting at 1). Spans of other phases carry none of these, and an attempt cannot have the phase Await. The blocked items are the union of the items the host observed the awaited item blocking (its `Blocks` references) at any time during the wait. The set holds at most 200 items; once an item is left out the truncation flag is set and stays set, and the set never shrinks. The whole wait is attributed to each blocked item, whenever the link was written: a Task linked after the wait began has the wait from its start, and a Task whose link was removed keeps it. A session filter sees a wait by its session, a Task filter when the blocked items contain the Task (and, as for every span, when the Task is a member of the span's assignment). Waits on several items at once are separate overlapping spans; nothing is merged, and the Await row is busy time like the others, so it is not added to them.

Registration of a wait that exists already. The fixed fields of a span are its assignment, session, phase, awaited item, parent (“Span parent” above) and start time. The rules apply in this order:

1. A registration whose fixed fields differ from the stored span is refused, whatever its observation number.
2. The same observation number with identical content returns the stored span.
3. The same observation number with other content is a conflict.
4. A lower observation number returns the stored span unchanged (a stale replay, not a conflict), also when the stored span has ended.
5. A higher observation number on a Running span replaces it when the finish time does not decrease, the blocked items contain the stored ones and the truncation flag is not cleared; otherwise it is refused.
6. A higher observation number on an ended span is refused: an ended span is immutable.

Every replay and every refusal leaves the stored span and the audit cursor unchanged; only the first registration and an accepted replacement (rule 5) advance the cursor. The rules are `cq.core.AwaitedSpans`, which the service and the host tests share.

Host recording. The host (`AwaitedWatch` with `OperatorWaits`) registers the span Running when the wait begins, registers a new observation when the union of the blocked items grows and at least every five minutes (the refresh interval) while the wait lasts, and ends it once, at the moment it observed the end: Completed when a person settled the item, Cancelled when the session released it or ended while still waiting. The span is on the assignment of the session's governing attempt. `AwaitedWatch` serves attached sessions only; a `cq run` session does not wait on the operator through it, and records no Await span.

Retention and delivery. `SpanDelivery` writes each span once at sequence 0 of an immutable queue and cannot carry refreshes, so waits have their own store: the directory `waits/` of the session holds one record per wait however long it lasts, named by the span identity, holding the latest observation and the observation number the server last acknowledged. Each observation replaces the record atomically (a temporary file, then a rename), and the host writes the record before it sends it. A send that fails leaves the record; the next observation replaces it and a round that observes nothing sends it again. The session's final delivery, the startup recovery of a later host and `cq job upload --session DIR` send every record whose latest observation is not acknowledged. When recovery or `cq job upload` finds a wait still Running it first ends it as Unknown with the finish time of its last observation, as it closes the governing attempt. A record acknowledged as ended is left as it is, and a second final delivery sends nothing.

Reading. The phase report shows the Await phase as its own row (`spans` are the waits, wall time the sum of their recorded durations); a Running wait adds its recorded duration and is counted in `runningSpans` of that row. Under a Task filter the report also states in `truncatedWaits` how many waits with the truncation flag do not name the Task, because such a wait may concern it; under any other filter it is zero.

Unobserved time. A Running wait says nothing about the time after its finish time. That time is unobserved: it is neither waiting nor idle. A Running wait is uncertain by up to the refresh interval of five minutes (and by longer when the host stopped observing, until recovery ends it as Unknown at its last observation).

Not recorded: a worker's check run whose start never reached the server when its supervisor died before sealing the worker's publication (their evidence is not published either; a delivered start is closed as Unknown by recovery); the finish of an integration that only `cq job upload` resolved after its supervisor died during the Git update (recovery closes its Running span as Unknown at the time it runs); an attempt reconciled by recovery ends at the recovery time, not at its job's settlement. Attempts registered before the settle-time rule keep their publication time as `finishedAt`, so historical Work wall time includes the worker's checks.

## Unit times

`UsageSelection.Units` (`UsageService.units`) reads the units of a scope with total and own time, category totals and a coarse split of elapsed time (Decision 14, rules 1 to 6, 9, 10 and 14; Decision 16). It is computed at read time from one repository snapshot by `TimeAccounting.compute`; nothing is stored. Measurements are in [unit-times-read.md](../validation/unit-times-read.md).

**Units and how each ends.**

| Record | Class | End |
| --- | --- | --- |
| Attempt with an effective outcome | governing when it has no parent and the Governor role, otherwise other | closed at the outcome's `finishedAt` |
| Attempt without an outcome, observed | as above | running: observed to the read time |
| Attempt without an outcome, not observed (attached governing attempt) | governing | open: observed to the latest recorded instant of its session |
| Check, Integrate or Combine span, terminal | other | closed at `finishedAt` |
| Check, Integrate or Combine span, Running | other | running: observed to the read time |
| Await span, terminal | operator wait | closed at `finishedAt` |
| Await span, Running | operator wait | observed to its `finishedAt`, the last observation |

Finish times are host-clock values; the read time is a server-clock value. A host whose clock differs from the server's moves a Running unit's figures by that difference.

**Categories and own time.** A category is the unit kind (attempt or span), the phase and, on a Check span, the check name; spans without a name are one category. The kind is part of the key because a conflict resolver's attempt and a combination preparation's span both have the phase Combine. A category reports its units, its total (sum of durations) and its own total. **Own time is structural**: a unit's duration minus the union of its direct children's intervals clipped to it. It is not inference, working or waiting time and bounds none of them, and the reply has no inference figure and no tool time. **Totals of different categories overlap when work runs in parallel or nested and must not be added.** A parent that is not among the selected units counts as none, so a child under a Task filter whose governing attempt is outside the scope is listed with its stored parent and own time equal to its duration.

**The five states.** The window is partitioned into running (some unit other than a governing attempt and other than an operator wait is in progress), waiting for the operator, governing session only, unobserved (the tail of an open interval) and idle. Each instant has exactly one state, so the five figures sum to the window length. They are the only figures of the reply that add up.

**Windows.** Without an explicit window the window runs from the earliest start to the latest observed end of the scope's units; a scope without units has no window and all figures are zero. An explicit window (`0 <= from <= until`) is part of the selection: a row is selected when it starts before `until` and has no recorded end or ends after `from`; a Running host span and a Running wait have no recorded end for this rule. Durations, own times, category totals and the split count only the part inside the window; the listing keeps each unit's true start and recorded end.

**Latest recorded instant of a session.** For each session with an open attached governing attempt in the selection the reader returns the maximum start, effective outcome finish and span start and finish over all attempts and spans of that session, taken over the whole session and not over the selected rows. It is not under the bound.

**Bound.** One read covers at most 20,000 units (`UsageService.MaxUnits`), attempts and spans together after the window predicate. The service asks the reader for 20,001 rows; when they come back it builds nothing and fails with `Limit`. An explicit window is the way out. PostgreSQL runs one `SELECT ... FROM (attempt rows UNION ALL span rows) u LIMIT ?` without ORDER BY; no index, stored column or projection is added.

**Paging and the read time.** The whole computed set is sorted in memory by start time and then identity and the page (1 to 200) is cut from it. The continuation holds the last unit of the page before, the audit cursor and the read time of the first page, whole or not at all. A read without a continuation takes the read time from the server clock and returns it. A read with a continuation is computed at the read time it carries, so the pages of one listing agree on window, split, category totals and per-unit figures while the cursor is unchanged; a changed cursor is `Resync`, a read time after the server clock or an `after` that is no unit of the set is `Invalid`.

**Truncated waits.** Under a Task filter the reply counts the project's waits with the truncation flag that the filter does not select and whose blocked items do not name the Task. The count is capped at 20,000 (`UsageService.MaxTruncatedWaits`) and reports "at least" at the cap; under other filters it is zero.

**Residual gap.** Work whose start has not reached the server (the host died or the server was unreachable before the start was delivered) is absent from a read; the time is classified by what the snapshot holds (for example governing session only or unobserved), and appears once the start is delivered.

## Storage, access and retention

The initial PostgreSQL DDL includes indexes for assignment membership, cohort, evaluation/scenario, session, attempt and source position. Writes serialize on a separate project audit cursor, not the ledger change cursor. Ingestion accesses the target meter, relevant observation/head, and that meter's projection. It does not reload item content or update unrelated task/cohort aggregates. Meter token projections have a fixed shape. Monetary projections use separate rows keyed by meter, currency, cost basis and pricing version. Ingestion updates only the previous/new contribution groups in the same audit transaction; corrections remove zero-measurement groups and retain measured zero amounts. Cumulative cost changes only with the effective latest observation. Historical cumulative corrections remain audit evidence without changing the current cost.

Summary reads use PostgreSQL repeatable-read snapshots without locking the audit clock. They fold matching meter projections in pages of 200; raw drill-down uses the committed audit sequence. Total work is proportional to the matching meters rather than every historical raw observation. Query-plan/scale measurements are retained in the [access evidence](../validation/m3-query-access.md). A project-wide report naturally reads that project's matching meters. Scoped cost queries aggregate the matching monetary projection rows in PostgreSQL and return at most 200 groups under the shared 512 KiB page budget. This bounds application memory and result size; database aggregation work remains proportional to matching groups, rather than the complete raw audit. Summary and its first cost page share the same read snapshot. `Costs` continuation carries the complete group key and snapshot cursor; changed audit state returns `Resync`. Ordering is UTF-8 byte order (PostgreSQL `C` collation), including attribution and optional pricing version. CLI `status costs` and browser “More costs” expose continuation without dropping monetary evidence.

Only Collector/Human service scopes may register or ingest audit data. Governor/worker ledger permissions do not confer telemetry-writing permission. An authorized late observation is admitted after claim release or result rejection because usage ingestion has no work-claim precondition. Signed project/role credentials and host-only HTTP ingestion enforce transport scope. The host acquires a signed collector credential for the project and logical session and keeps it out of harness environments. Artifact publication verifies that the attempt belongs to the collector’s session. Usage admission requires the authenticated project’s Collector/Human authority; `Scope` is supplied by the authenticated adapter.

CQ retains numerical records, frozen membership, corrections and published artifact bytes in PostgreSQL. There is no deletion/retention job or supported artifact purge command. Local supervisor journals, streams and Git objects have separate storage and recovery responsibilities; see the [retention boundaries](operations.md#retention-boundaries). Archiving or finishing work does not erase its historical accounting.
