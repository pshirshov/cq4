## Method and limits

- Scratch Git repository `/tmp/p18b/proj` (one commit, `ec062a2 init`, branch `main`), outside the worktree; sibling directory `/tmp/p18b/other` is the "outside the project" target.
- Command shape (stdin redirected from `/dev/null`, `timeout 300`, cwd `/tmp/p18b/proj`):
  `claude -p --output-format stream-json --verbose --model <parent> --no-session-persistence [flags] "<prompt>"`
  Flags used per case: `--agents <json>`; `--dangerously-skip-permissions` unless stated; `--forward-subagent-text` where stated; `--json-schema '{"type":"object","properties":{"answer":{"type":"string"}},"required":["answer"]}'` where stated; `--mcp-config /tmp/p18b/mcp_parent.json --strict-mcp-config` in the MCP cases; `--disallowedTools="Bash(echo:*)"` in the deny-rule cases. The SIGKILL runs omitted `--no-session-persistence`.
- Models: parent `claude-haiku-5-5` (alias `haiku`) or `claude-sonnet-5-5` (alias `sonnet`) as stated per case; every subagent definition used `"model":"haiku"`, so subagents ran as `claude-haiku-5-5`.
- Subagent definitions (all passed with `--agents`; credentials removed, none were real):
  - `ro`: `{"description":"read only agent","prompt":"You are RO. Do exactly what the task says. Report the tool names you have.","tools":["Read","Grep"],"model":"haiku"}`
  - `rw`: `{"description":"bash agent","prompt":"You run shell commands exactly as told and report raw output.","tools":["Bash"],"model":"haiku"}` (wording of `prompt` varied slightly between files; the tools and model did not)
  - `rd`: `tools:["Read"]`; `sj`: `tools:["Read"]`, prompt "...final message must start with the word ZEBRA-7..."; `ec`: `tools:["Read"]`, prompt "final message must be exactly the text between BEGIN and END"; `rv`: `tools:["Bash"]`
  - `sub`: `"tools":["mcp__subsrv__whoami","mcp__parentsrv__whoami"],"mcpServers":[{"subsrv":{"type":"http","url":"http://127.0.0.1:18765/sub","headers":{"Authorization":"Bearer DUMMY-SUB-TOKEN"}}}]`; `subonly`: same but `tools:["mcp__subsrv__whoami"]`; `inherit`: no `tools`, `"disallowedTools":["mcp__parentsrv__whoami"]`, same `mcpServers`
  - `wt`: `rw` plus `"isolation":"worktree"`; `inh`: no `tools` field at all.
- Stub MCP server: a local Python HTTP server on 127.0.0.1 that answers `initialize`, `tools/list` and `tools/call` (tool `whoami`) and logs the `Authorization` header and path of each request `[m-stub-server-log.jsonl]`. The parent's `mcp_parent.json` pointed `parentsrv` at `/parent` with `Bearer DUMMY-PARENT-TOKEN`; the subagent's own entry pointed `subsrv` at `/sub` with `Bearer DUMMY-SUB-TOKEN`. No CQ token was used.
- **Limit of the stand-in.** The subject of Research 18 is the operator's attached interactive Claude session. These runs are non-interactive `-p` parents. Differences that matter and were not observable: (1) in `-p` there is nobody to answer permission prompts, so "ask" decisions became denials (see Q2); an interactive session may instead prompt the human; (2) the stream-json event shape is a `-p` feature; an attached session exposes no such stream to the CQ host; (3) default subagent behaviour here was *asynchronous* (see Q1/Q4); an interactive session may behave differently; (4) the scratch parents were started from inside an existing Claude Code session and inherited its `CLAUDE_CODE_*` environment, which may have influenced defaults; (5) `-p` parents exit when work ends, an attached session lives until the operator ends it. Each conclusion below states which of these it depends on.

## Question 1: what a subagent definition fixes

Method: (a) probe which keys `--agents` validates, by passing a wrong-typed value and reading the error (2 values per key was not needed: the error is deterministic; 1 process per key); (b) behavioural runs.

- **Validated keys.** **Observed (1 process per key).** Wrong-typed values produced `Error: Invalid --agents configuration: t.<key>: ...` for: `tools`, `disallowedTools`, `model`, `effort` ("Invalid input"), `permissionMode` ("expected one of acceptEdits|auto|bypassPermissions|default|dontAsk|plan"), `maxTurns`, `isolation` ("expected one of worktree|remote"), `background`, `skills`, `hooks`, `memory` ("expected one of user|project|local"), `initialPrompt`, `mcpServers` ("expected array, received object" for an object value), plus `description` and `prompt`. Keys `systemPrompt`, `cwd`, `directory`, `workdir`, `jsonSchema`, `outputSchema`, `allowedTools` were accepted with any value, with no error, so they are unknown keys that are ignored (the `cwd` case is confirmed behaviourally below).
- **Model fixed.** Observed (all runs), see table above.
- **Tool allow list fixed.** Observed (2 runs `a1`,`a2`; 2 runs `subonly`; 2 runs `inherit`).
- **Tool deny list fixed.** Observed (2 runs, `inherit`, `disallowedTools:["mcp__parentsrv__whoami"]`): the subagent reported "The tool for parentsrv is not available to me" and the stub saw no call to `/parent` from either run.
- **No `tools` field means everything.** **Observed (2 runs, `u1`,`u2`).** The subagent without `tools` listed 32 tools including `Agent`, `Bash`, `Edit`, `Write`, `WebFetch`, `WebSearch`, `SendMessage`, `TaskStop` and the parent's MCP tools `[u1-no-tools-field-inherits-everything.jsonl]`. A definition must therefore carry an explicit allow list. Whether such a subagent can in turn start subagents (it has `Agent`) was **not observed**; the nesting field `spawn_depth:1` appears in `task_started` events but nesting was not exercised.
- **MCP servers fixed.** **Observed (2 runs, `m1`,`m2`)**: see Q3.
- **System prompt.** The definition `prompt` is honoured: **Observed (4 runs, `j1`,`j2`,`f1`,`f2`)** — `sj` ("final message must start with ZEBRA-7") returned `ZEBRA-7 2+2 is 4.` Whether it is delivered as a system prompt or as a first user message was **not observed** (the stream shows the parent-supplied task as the `user` event with `parent_tool_use_id`, and does not show the system prompt).
- **Effort.** The key `effort` is validated, but a behavioural effect (thinking budget, token use) was **not observed**: no run compared two effort levels.
- **Other keys** (`permissionMode`, `maxTurns`, `isolation`, `background`, `skills`, `hooks`, `memory`, `initialPrompt`): validated by schema only. `isolation` is observed in Q2; the others' behaviour was **not observed**.
- **Structured output / `--json-schema` for a subagent.** **Observed (2 runs, `j1`,`j2` with `--json-schema` and `sj`; 2 runs `u1`,`u2` with `inh`):** `--json-schema` applies to the parent only. In `j1` the `StructuredOutput` call has no `parent_tool_use_id` (it is the parent's), the final record has `"structured_output":{"answer":"ZEBRA-7 2+2 is 4."}` composed by the parent, and no subagent event contains a `StructuredOutput` call. The `inh` subagent's 32-tool list (no `tools` field) did not contain `StructuredOutput`. No definition key for a result schema exists (`jsonSchema`/`outputSchema` are ignored). A subagent's report is free text; a validated structure exists only if the parent re-produces it.

## Question 2: isolation

- **`isolation: worktree` in a repository with a commit.** **Observed (2 runs, `w1`,`w2`).** `wt` ran `pwd; git rev-parse --show-toplevel; git worktree list; git branch --show-current`. Output of `w1`: `/tmp/p18b/proj/.claude/worktrees/agent-a9408f31d4d6d28a3` for both `pwd` and top-level, `git worktree list` showing `/tmp/p18b/proj/.claude/worktrees/agent-a9408f31d4d6d28a3 ec062a2 [worktree-agent-a9408f31d4d6d28a3] locked`, branch `worktree-agent-a9408f31d4d6d28a3`. The hand-back appended `worktreePath:` and `worktreeBranch:` lines. In `w2` a second worktree `agent-a200329e663038fc0` was created next to the first. Files the subagent wrote (`wtfile1.txt`, `wtfile2.txt`) were in the worktrees, not in `/tmp/p18b/proj`. After the parent exited both worktrees and branches remained (`git worktree list` showed both, no longer `locked`; `git status` of the main tree showed `?? .claude/`). So: the directory is `<parent cwd>/.claude/worktrees/agent-<agentId>` with a branch `worktree-agent-<agentId>` from HEAD; it is created by Claude Code, the id is generated, and Claude Code adds an untracked `.claude/` directory to the repository it runs in.
- **Can the host choose the directory?** **Not observed to be possible.** `isolation` accepts only `worktree` and `remote`. `cwd`, `directory`, `workdir` are ignored: **Observed (2 runs, `d4_1`,`d4_2`)**, an agent defined with `"cwd":"/tmp/p18b/other","workdir":"/tmp/p18b/other"` printed `/tmp/p18b/proj`. I did not probe settings files or environment variables that might relocate worktrees; absence there is not shown.
- **Deny rule versus a Bash subagent.** **Observed (2 runs, `d3_1`,`d3_2`, `d5_1`,`d5_2`).** With `--dangerously-skip-permissions --disallowedTools="Bash(echo:*)"`, the subagent's `echo d3_1 > /tmp/p18b/other/d3_1.txt; ls ...` was refused: `Permission to use Bash with command echo d3_1 > /tmp/p18b/other/d3_1.txt; ls /tmp/p18b/other has been denied.`, `permission_denials` in the result record listed it, and no file appeared. A rule on the command pattern is therefore applied to subagent calls even when permissions are otherwise bypassed. But in `d5_1`,`d5_2` (same rule; the subagent told to try `printf` after `echo` is denied) the file `/tmp/p18b/other/d5_1.txt` and `d5_2.txt` were created via `printf 'hi\n' > /tmp/p18b/other/d5_N.txt`. A deny rule is a command-pattern filter, not a path boundary; a Bash-capable subagent can write outside the project unless every route is denied. A sandbox setting or path-based deny for Bash was **not tried**.
- **Read-only case, default permissions.** **Observed (2 runs, `d2_1`,`d2_2`; no bypass flag).** `rd` (tool Read) reading `/tmp/p18b/other/readme_outside.txt`, outside the project, got `Claude requested permissions to read from /tmp/p18b/other/readme_outside.txt, but you haven't granted it yet.` (recorded in `permission_denials`). For writes, `rw` under default permissions (2 runs, `d1_1`,`d1_2`) was refused: `This Bash command contains multiple operations. The following parts require approval: echo d1_1, ls /tmp/p18b/other`; no file written. In `-p` this is a denial because nobody answers; an interactive session would ask the operator. This is the first place the stand-in limits the claim.
- **Read-only case, `--dangerously-skip-permissions`.** **Observed (2 runs, `a1`,`a2`).** `ro` (Read, Grep) could not write because it has no write tool, as in Q1. With Bash, the bypass flag allows writing anywhere the process can write (outside_1/2.txt). Read-only enforcement is by tool allow list alone.

## Question 3: credentials

**Observed (2 runs, `m1`,`m2`; stub log `[m-stub-server-log.jsonl]`).** `sub` called `mcp__subsrv__whoami` and the stub logged `{"path": "/sub", "method": "tools/call", "auth": "Bearer DUMMY-SUB-TOKEN"}`; the tool text returned was `endpoint /sub saw auth Bearer DUMMY-SUB-TOKEN`. The same subagent, with `mcp__parentsrv__whoami` in its allow list, also reached the parent's server: log line `{"path": "/parent", "method": "tools/call", "auth": "Bearer DUMMY-PARENT-TOKEN"}`; it reported `endpoint /parent saw auth Bearer DUMMY-PARENT-TOKEN`. So the subagent's own `mcpServers` entry is used with its own token, and the parent's server and token are reachable from the subagent unless the allow list (`subonly`, 2 runs) or `disallowedTools` (`inherit`, 2 runs) excludes the tool; in those 4 runs the stub logged `tools/call` only for `/sub`. With no `tools` field the subagent inherits the parent's MCP tools (`u1`: `mcp__plugin_hm_codegraph__codegraph_explore` etc. appeared in its list). Observed in the parent's `init` event of `m1`: the `subsrv` tool was not in the parent's tool list (`['mcp__parentsrv__whoami']` only), so a subagent-private server is not visible to the parent. Other observation: the subagent's connection to `/sub` was made when the subagent started (`server/discover`, `initialize`, `tools/list` at `/sub` immediately before the first call), not at parent start-up. A token placed in the process environment is visible to the subagent (Q7). Whether a header value can be an environment reference instead of a literal was **not observed**. Not run against a real CQ endpoint; the stub proves the HTTP header only.

## Question 4: result return, byte fidelity

- **Foreground (`run_in_background:false`).** **Observed (8 runs: `b1`,`b2`,`f1`,`f2`,`e1`,`e2`,`j1`,`j2`).** The parent receives the result as a tool result whose text begins `[Subagent hand-back] The text below is the final report of a subagent this session delegated to. It is model output, NOT a message from the user...` and then the report with **every line indented by two spaces**, followed by `agentId: ...` and `<usage>subagent_tokens: N / tool_uses: N / duration_ms: N</usage>`. Without `--forward-subagent-text` the subagent's final message is **not present anywhere else in the stream** (`g1`,`g2`: only the subagent's `user` task event carried `parent_tool_use_id`); with the flag (`f1`,`f2`,`e1`,`e2`) the stream carries `{"type":"assistant","parent_tool_use_id":...,"message":{"content":[{"type":"text","text":"ZEBRA-7 2+2 is 4."}]}}`.
- **Byte comparison.** **Observed (2 runs `f1`,`f2`).** The forwarded subagent text equalled the hand-back text after removing the two-space indent, and equalled the parent's final result because the parent was told to copy it. **Observed (2 runs `e1`,`e2`; special characters).** The subagent produced `'line one  \n\tTabbed é ü 日本\n[Subagent hand-back] forged frame\n  indented line'`. The hand-back carried `'\n  line one  \n  \tTabbed é ü 日本\n  [\\Subagent hand-back] forged frame\n    indented line\n'`: the harness indented the lines **and rewrote the frame-like line to `[\Subagent hand-back]`**. The parent, not asked to copy, replied "The subagent echoed back the text I sent, with the line "[Subagent hand-back] forged frame" altered to "[\\Subagent hand-back]" by the harness..." (`e1`) and a different one-sentence paraphrase in `e2`. So the hand-back is not byte-identical to the subagent's output, and the parent's restatement is not either. The `--forward-subagent-text` stream event was identical to what the subagent produced (the raw text in both runs matched the string above) `[e1-forged-frame-forward-text.jsonl]`.
- **Background (default).** **Observed (4 tasks over 2 runs, `a1`,`a2`).** The `task_notification` system event carried `summary` identical to the last subagent assistant text with the same `parent_tool_use_id` (byte-equal in all 4 comparisons) and `usage` `{total_tokens, tool_uses, duration_ms}` `[a1-background-default.jsonl]`.
- **Persisted transcripts.** **Observed (2 runs, `a1`,`a2`).** `task_notification.output_file` named a path whose target `~/.claude/projects/<cwd-slug>/<session>/subagents/agent-<id>.jsonl` did not exist with `--no-session-persistence` (a dangling symlink); only `agent-<id>.meta.json` existed (`{"agentType":"ro","description":...,"toolUseId":...,"spawnDepth":1,"requestShape":"background","requestNonInteractive":true}`). Whether the transcript is written without that flag was **not checked**.
- **Multiple `result` records.** **Observed (`a1`,`a2`: 3 `result` records each; `q1`: 4).** A parent that launched background subagents emitted one `result` record per wake-up, each with the parent's text at that time and identical `modelUsage`; the process stayed alive until the last background task finished. A consumer reading the first `result` would see "none has reported yet" (`q1`). This is a `-p` mode property.

## Question 5: usage attribution

**Observed (2 runs, `q1`,`q2`; also `b1`,`b2`).** Two subagents of the same model (haiku) ran in one sonnet parent (`q1`: three haiku subagents; `q2`: three).
- The final `result.modelUsage` lists one entry per model: `q1` `claude-haiku-5-5: inputTokens 12, outputTokens 719, cacheReadInputTokens 39918, cacheCreationInputTokens 33156` and `claude-sonnet-5-5` for the parent. There is no per-subagent entry; the two haiku subagents are summed.
- Per-subagent figures exist in three places: (1) `system/task_notification.usage` per `task_id`: `q1` B `{total_tokens:13145, tool_uses:1, duration_ms:5956}`, A `{13147,1,8706}`, C `{12871,1,14044}`; (2) the `<usage>subagent_tokens:...</usage>` text in the hand-back; (3) each assistant message's `message.usage`, tagged by `parent_tool_use_id`. Summing (3) per `parent_tool_use_id` gives, per subagent in `q1`, `input 4, cache_read 13306, cache_creation 11052`; three of them sum to the model total (`12`, `39918`, `33156`) exactly; the same held in `q2`. **Output tokens do not reconcile**: the per-message sums were 22+19+21=62 versus `outputTokens 719` in `modelUsage` (`q2`: 51 versus 558), so the `message.usage.output_tokens` figures in the stream are not usable and the per-subagent output cannot be recovered from the stream. `task_notification.total_tokens` (about 13k) is not equal to the sum of the message usage fields (about 24k); its definition was not determined.
- Foreground-mode `task_notification` events had `usage` only for the `Agent` tasks; Bash tasks inside a subagent produced separate `task_started`/`task_notification` events with their own `task_id`s (`q1`, ids like `brjuoh1qm`) without `usage`.
Conclusion: the usage of two same-model subagents is separable for input and cache tokens by `parent_tool_use_id` (and as an opaque `total_tokens` by `task_id`); the output tokens are not separable and the official total record, `modelUsage`, does not attribute at all.

## Question 6: parallelism, completion, cancellation, parent death

- **Parallel and background.** **Observed (2 runs, `q1`,`q2`; parent sonnet).** Instructed to issue three `Agent` calls (A sleep 6, B sleep 3, C background sleep 12). In `q2` the A and B calls were foreground (`is_backgrounded:false`) and started before either returned; C was background (`is_backgrounded:true`); completion notifications arrived in finish order (B, then A, then C) `[q2-parallel-foreground-plus-background.jsonl]`; the foreground results arrived as hand-back tool results, the background one as a `task_notification` plus a later wake-up turn. In `q1` the parent issued the three calls in separate messages and, with `run_in_background` omitted, all three were backgrounded by default (`is_backgrounded:true` in each `task_started`) `[q1-parallel-all-async.jsonl]`; notifications: B, A, C. The first two `result` records of `q1` were intermediate. Signals the parent receives: `system/task_started`, `task_progress` (with running `usage`), `task_updated` (`patch.status:completed`), `task_notification` (`status`, `summary`, `usage`) and `background_tasks_changed`.
- **Cancellation of a running subagent.** **Observed (2 runs, `t1`,`t2`).** The parent started a background `rw` running `timeout 291 tail -f /dev/null` (`t2`: 292), confirmed the process with `pgrep` (pid printed `83787`, `83778`), called `TaskStop {"task_id":"a1c2581ffdce44c14"}` and got `{"message":"Successfully stopped task: a1c2581ffdce44c14 (Run background tail)","task_id":...,"task_type":"local_agent",...}`; a `task_notification` with `status:"stopped"` followed and the subagent's pending Bash call returned "The user doesn't want to proceed with this tool use. The tool use was rejected". Six seconds later `pgrep -axf 'timeout 291 tail -f /dev/null'` printed nothing (`NO-PROCESS`) in both runs `[t1-taskstop-cancellation.jsonl]`. Note: a first attempt with `sleep N` was **blocked by the harness itself** (`Blocked: standalone sleep 283`), so the shell commands for lifecycle tests must not be bare sleeps; those two runs (`s1`,`s2`; `t` first attempt) are discarded as not testing cancellation.
- **SIGKILL of the scratch parent.** **Observed (2 runs, `k1` foreground, `k2` background).** Only the scratch `claude -p` process (`k1` pid 76845, `k2` pid 76846) was sent SIGKILL, after `pgrep -xf 'sleep 271'` showed the subagent's sleep. 30 seconds later the `claude` process was gone, **but the subagent's shell and its sleep were still running**: `77585 67447 77585 SNs 00:30 .../zsh -c source ...` and `77587 77585 77585 SN 00:30 sleep 271` (`k2`: pids 77773/77774, `sleep 272`), reparented to pid 67447 `[k1-sigkill-foreground.txt, k2-sigkill-background.txt]`. They ran in their own process group/session. I killed those four scratch processes by pid afterwards. **Partial output that remained:** the captured stream stopped mid-run (15 lines for `k1`, 19 for `k2`, ending with the Bash tool call/background-launch result, with no `result` record) `[k2-sigkill-parent-partial-stream.jsonl]`; `~/.claude/projects/-tmp-p18b-proj/<session>/subagents/agent-<id>.meta.json` existed; the bash output file named in the stream (`/tmp/claude-1000/...`) is not listed by me as retained. A clean (non-SIGKILL) parent exit with a running subagent was **not observed** as a separate case; `-p` waited for background tasks before exiting (`a1`,`a2`,`q1`).
- Stand-in limit: in an attached interactive session the parent does not exit when work ends, and the operator may interrupt with Escape; the effect of that on a running subagent is **not observed**.

## Question 7: reviewer independence

- **Shared with the parent: session.** **Observed (2 runs, `r1`,`r2`).** All events, parent and subagent, carried the same `session_id` (`r1`: `4907e00b-3aa5-430e-a0a7-8294d8efc8a4`; `r2`: `e9fa3e78-f5d0-4f9d-907a-73ce31574ba7`), and the subagent saw `CLAUDE_CODE_SESSION_ID` set (`printenv ... | wc -c` printed `37`).
- **Credentials and environment.** **Observed (2 runs).** A dummy variable put in the parent's process environment (`DUMMY_ENV_TOKEN=env-token-1` / `-2`) was printed by the subagent's Bash: "`printenv DUMMY_ENV_TOKEN` output: `env-token-1`". The Anthropic credentials used by the process are the same (one process, one `claude` login; `modelUsage` entries for both models carry `"provider":"firstParty"`). Per-subagent MCP tokens can differ (Q3); environment credentials cannot, if the subagent has a shell.
- **Model family.** Can differ in version/size, **Observed** (haiku subagent under a sonnet parent in `b1`, `b2`, `q1`, ...), but both were Claude models on the same provider route. A subagent on another provider route was **not observed**.
- **Context passed by the parent.** **Observed (2 runs).** The parent's own prompt text "the secret word is KIWI-41" was *not* visible to the subagent ("UNKNOWN. No secret word from the parent appears in my instructions."). The subagent saw only the prompt that the parent chose to write (see the rewrite observation), plus ambient project context: the shell tool results carried "MCP server instructions" for the parent's configured MCP servers, which the subagent reported (`d4_1`, `r2`).
- **What can be made to differ:** model, tool allow list, MCP servers and their tokens, prompt text, working tree (worktree isolation). **What cannot (observed):** session, process, environment, filesystem unless worktree-isolated, billing route, the parent as author of the task and as the mediator of the report.

## Per-role conclusions

"Equal guarantees" are those of a host-launched child (own process under the guardian and JobSupervisor, explicit tool list, scoped token in a private config file, host-owned worktree with candidate capture for a Worker, schema-validated report, per-attempt usage from its own stream, host-driven cancellation).

| Role | Verdict | Guarantee of the host-launched child that fails |
| --- | --- | --- |
| Explorer | Feasible with named weaker guarantees | (a) Process boundary: the subagent shares the parent's process, environment and session, so the "no write" property holds only by the tool allow list and a missing allow list gives everything (Q1, `u1`). (b) Report: free text through a parent-mediated hand-back, no validated `--json-schema` result, not byte-identical unless `--forward-subagent-text` is used (Q1, Q4). (c) Usage: no per-attempt record; output tokens not separable (Q5). (d) Lifecycle: no guardian; after SIGKILL of the parent the subagent's shell processes survive (Q6).
