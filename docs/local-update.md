# Updating the local native release

`run-local.sh` starts `.local/release`; it does not build source. After committing changes, stop that launcher with Ctrl-C and wait for `CQ stopped`, then run:

```sh
./update-local.sh
./run-local.sh
```

Both commands use `CQ_LOCAL_STATE`, defaulting to `/srv/nvme/tmp/cq4-playground`. The updater requires an existing owned local state and installed package. It never signals a pre-existing server or database process. It holds the launcher lock for the entire update, so local startup remains unavailable while the build runs. Allow time for the native build and installed verification.

The operator-run updater snapshots HEAD into a detached worktree and refuses uncommitted runtime inputs. It runs `dev/package-local`: native compilation and bounded startup/API/browser-asset smoke against disposable databases. Testing is separate: `./test-local.sh` runs fast, UI, PostgreSQL and native gates, stopping on the first failure. Build evidence stays under `STATE/updates/ATTEMPT`. Any failure before installation retains the current release; inspect the named log. The candidate directory is retained for inspection. Retrying creates a new attempt and rebuilds it.

After verification it starts only the stopped local database, checks its migration checksum, creates a custom-format PostgreSQL backup, verifies its inventory, and stops the database. Equal schema/model hashes are accepted. The current transition is pinned in `dev/local-update-step.json` as `attempt-events-and-live-claims`: it names the schema and model hashes of the installed release (`37dc475`) and of this one, and the hash of `dev/local-update.sql`. Since the installed release the schema gained the column `cq_usage_clock.attempt_events` and the index `cq_claims_live`, with which reading a project's [work cursor](design/claims.md) no longer counts every attempt and claim of the project; the model did not change. A schema or model transition that the step does not name is refused; a model change on an unchanged schema is accepted only as an `unchanged-data` step, which runs no SQL. Changing a checksum declaration alone is insufficient.

Before it changes anything the updater refuses a database in which a project's fence counter differs from the number of the project's claims (`claims-per-fence.log`): this release computes the work cursor from that equality, which holds for every database only CQ wrote. After the backup it applies the pinned SQL in one transaction: it adds the column as `server/src/main/resources/db/001-ledgers.sql` declares it, sets it for every project to the number of the project's attempts plus the number of those with a recorded outcome, creates the index, and records the new schema hash. It takes the fingerprints of every table before and after (`data-before.json`, `data-after.json`) and then verifies the step:

- the database records the schema hash of the new package;
- no table was created or dropped, and no table other than `cq_usage_clock` and `cq_schema_migrations` changed;
- every usage clock row is the row it was with the count of its project's attempt events added, and every project with attempts has such a row;
- the updated database has the structure the new schema declares, so the column and the index are the only objects added: the updater declares that schema in a scratch database (`cq_update_structure`, dropped again) and compares the two structures as `pg_dump --schema-only` prints them. The entries of a table are compared without their order, because a column that this or an earlier update added stands last in its table, wherever the schema file declares it.

The receipt names the step, the number of usage clocks and the sum of their attempt events. If the SQL, a verification or the package replacement that follows fails, the updater restores the backup into the database in one transaction, which removes the column and the index with the tables it recreates, drops any table the SQL created (the backup does not know it), verifies the restored fingerprints against those taken before, and leaves the previous package installed. The SQL changes nothing when it is applied to a database it was already applied to, and an update from this release to itself runs none.

Session directories of the installed release stay readable: no type of their files changed. The agent configuration saved for the installed release is used as it is. From this release on an attached host records its session and registers its governing attempt at the session's first tool call ([usage audit](design/usage-audit.md)); a session directory holding nothing but `journal/owner.lock` belongs to a harness that opened the connection and made none, and holds nothing to recover or upload.

Project archives are not converted by any update; [project backup](project-backup.md) says which earlier archives the current release refuses. Active claims, unfinished managed attempts and pending integrations prevent installation. Root attached Governor attempts identified by the attached-session collector may lack outer usage outcomes; those audit records remain unchanged and do not prevent replacement. The receipt and `unsettled-work.log` report each category separately, including the incomplete attached Governor count. This exemption does not establish that a harness has stopped; stop consumer runs before shutting down the launcher.

The updater moves the current release to `.local/release-before-ATTEMPT`, installs the verified candidate, and records the source revision, manifest identities and backup hash in `receipt.json`. Restart the launcher and reload the browser. Existing interactive host journals must be reconciled under the normal host recovery rules; this command does not start harnesses or settle their work.

**The harness integrations need no regeneration for this update.** Generated for one checkout with the installed release and with this one, the files of all three harnesses are identical (`cq configure claude|codex|pi --settings FILE --replace`: 22 files, among them the Claude Code commands and `.claude/settings.local.json`, the Codex skills, `.codex/config.toml` and `.codex/hooks.json`, the Pi extension and prompts, and `.mcp.json`). The instruction texts that changed (those of the implementing and conflict-resolving Worker, of the candidate Reviewer, and the YOLO mode section) are not in generated files: the host serves them, so a session has them once its host is the new package's. Restart running harness sessions after the update. `cq doctor harness` still reports a generated file whose content differs from what this package generates. `cq configure --replace` rewrites the files this package generates and removes none; nor does it remove an allow rule: it adds the rules of the state root the settings file names to `permissions.allow` of `.claude/settings.local.json` and leaves every rule that is there, so after the state root of a project is moved the rules of the former one stay and keep allowing Claude Code's file tools under it. Delete them by hand when that directory should no longer be writable without a prompt.

An interruption during replacement attempts to restore the previous package. Unverified recovery leaves `STATE/.cq-update-recovery.json`, which the launcher refuses. Inspect its receipt and logs, stop any owned update processes, and restore the matching **previous package and database backup**. Verify their recorded hashes and the database's schema before removing the marker. If a restore of the backup itself failed (`database-rollback.log`), it ran in one transaction, so the database is as the failed SQL left it; the updater has stopped the database, and the backup named in the receipt is the state to restore by hand. Never launch a package against an unverified database. Keep the previous release and `before.dump` together; rollback after subsequent use also discards database writes made since that backup. Automatic pruning is deliberately absent.

Focused updater checks:

```sh
nix develop -c python3 dev/update-local-check.py -v
nix develop -c python3 dev/update-local-check.py --postgres -v
```

The shared replacement contract runs against in-memory and real-directory adapters. The focused check also verifies that the pinned step matches this tree's schema, model and SQL, that the column and the index its SQL adds are the ones the schema declares and the schema without them is the one the step starts from, that the structures of two databases compare without the order of a table's entries, and that a step of another kind or another transition is refused. The optional PostgreSQL case uses a disposable cluster, checks the retained backup and package replacement, verifies refusal on a mismatched schema, and exercises the rollback of a failed replacement. For SQL applied after the backup it checks that an install without it leaves the rows alone, that the receipt names the changed tables, that applying it again changes nothing, and that SQL that fails and a replacement that fails after it, also one whose SQL created a table, each restore the backup. For the pinned step it builds a database of the schema the step starts from, with a column moved to the end of its table as an earlier update leaves one, and with claims, attempts and usage clocks; it checks that a project with a fence counter other than the number of its claims is refused before any change, that a failed replacement and each of nine departures of the SQL from what the step may do (no count stored, no hash recorded, another change to a usage clock, a change to another table, no index, another index, a further index, another declaration of the column, a table created) are refused and leave the database as the backup holds it, without the column and the index, and that the pinned SQL then leaves exactly the expected rows and structure, gives every project the work cursor the installed release counted, and changes nothing when applied again. A restore that cannot run leaves the marker, the previous package and a stopped, undamaged database. Full native/package gates are operator delivery evidence, not implied by these focused checks.
