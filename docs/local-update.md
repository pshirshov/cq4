# Updating the local native release

`run-local.sh` starts `.local/release`; it does not build source. After committing changes, stop that launcher with Ctrl-C and wait for `CQ stopped`, then run:

```sh
./update-local.sh
./run-local.sh
```

Both commands use `CQ_LOCAL_STATE`, defaulting to `/srv/nvme/tmp/cq4-playground`. The updater requires an existing owned local state and installed package. It never signals a pre-existing server or database process. It holds the launcher lock for the entire update, so local startup remains unavailable while the build runs. Allow time for the native build and installed verification.

The operator-run updater snapshots HEAD into a detached worktree and refuses uncommitted runtime inputs. It runs `dev/package-local`: native compilation and bounded startup/API/browser-asset smoke against disposable databases. Testing is separate: `./test-local.sh` runs fast, UI, PostgreSQL and native gates, stopping on the first failure. Build evidence stays under `STATE/updates/ATTEMPT`. Any failure before installation retains the current release; inspect the named log. The candidate directory is retained for inspection. Retrying creates a new attempt and rebuilds it.

After verification it starts only the stopped local database, checks its migration checksum, creates a custom-format PostgreSQL backup, verifies its inventory, and stops the database. Equal schema/model hashes are accepted. The current transition is pinned in `dev/local-update-step.json` as `installation-settings-and-attempt-effort`: it names the schema and model hashes of the installed release (`63db1c2`) and of this one, and the hash of `dev/local-update.sql`. Since the installed release the schema gained the table `cq_installation_settings`, which holds the server's default [agent configuration](design/local-dispatch.md), and a stored attempt (`cq_usage_attempts.body`) gained the field `effort`, without which this release cannot read it. A schema or model transition that the step does not name is refused; a model change on an unchanged schema is accepted only as an `unchanged-data` step, which runs no SQL. Changing a checksum declaration alone is insufficient.

After the backup the updater applies the pinned SQL in one transaction: it creates the table as `server/src/main/resources/db/001-ledgers.sql` declares it, adds `"effort": null` to every stored attempt that lacks the field, and records the new schema hash. It takes the fingerprints of every table before and after (`data-before.json`, `data-after.json`) and then verifies the step:

- the database records the schema hash of the new package and no stored attempt lacks `effort`;
- the only new table is `cq_installation_settings`, it is empty, and no table other than `cq_usage_attempts` and `cq_schema_migrations` changed;
- every attempt row is the row it was with a null `effort` added where it had none, and nothing else;
- the updated database has the structure the new schema declares: the updater declares that schema in a scratch database (`cq_update_structure`, dropped again) and compares the two structures as `pg_dump --schema-only` prints them.

The receipt names the step, the number of attempts and how many were transformed. If the SQL, a verification or the package replacement that follows fails, the updater restores the backup into the database in one transaction, drops the table the step created (the backup does not know it), verifies the restored fingerprints against those taken before, and leaves the previous package installed. The SQL changes nothing when it is applied to a database it was already applied to, and an update from this release to itself runs none.

**Session directories of the installed release are unreadable to this one.** `run.json`, a child's `ticket.json` and the delivery batches that were not acknowledged hold an attempt, and no update converts files of a session directory. Startup recovery and `cq job upload --session DIR` therefore fail on a session directory that the installed release wrote. Before updating, end the harness sessions and let their deliveries be acknowledged (`cq job upload --session DIR` with the installed release reports `Acknowledged 0` when nothing is left); what an earlier session directory still held undelivered after the update is lost to the server.

**Save an agent configuration: without one no child starts.** This release starts a child only on the models the agent configuration assigns to the child's role, and an installation that was just updated has none: every `StartChoice` is refused and names the role to assign. This step is required after the update, not optional. `cq agents init --settings FILE --save installation` writes a starting configuration from the harness entries of a settings file as the server's default (`--save project` for one project; without `--save` it prints the text); with more than one harness in the file each harness's reviews go to the other harnesses first. Edit it under *Agent models* in the browser. `cq doctor agents HARNESS --settings FILE` checks that every role can run ([doctor](doctor.md)).

Project archives are not converted by any update; [project backup](project-backup.md) says which earlier archives the current release refuses. Active claims, unfinished managed attempts and pending integrations prevent installation. Root attached Governor attempts identified by the attached-session collector may lack outer usage outcomes; those audit records remain unchanged and do not prevent replacement. The receipt and `unsettled-work.log` report each category separately, including the incomplete attached Governor count. This exemption does not establish that a harness has stopped; stop consumer runs before shutting down the launcher.

The updater moves the current release to `.local/release-before-ATTEMPT`, installs the verified candidate, and records the source revision, manifest identities and backup hash in `receipt.json`. Restart the launcher and reload the browser. Existing interactive host journals must be reconciled under the normal host recovery rules; this command does not start harnesses or settle their work.

**Regenerate every harness integration.** After this update, run `cq configure --replace` for all three harnesses in every project before starting a harness session there: `cq configure claude --settings FILE --replace`, `cq configure codex --settings FILE --replace` and `cq configure pi --settings FILE --replace` ([auto-driver](auto-driver.md)). Generated with the installed release and with this one for the same checkout, these files differ:

- Claude Code: the commands `.claude/commands/cq/advance.md`, `begin.md`, `review.md` and `upstream.md`, and `.claude/settings.local.json`, which gained the two rules that allow Claude Code's file tools in the workspaces of the state root's sessions ([interactive](interactive.md#a-workspace-of-the-governors-own));
- Codex: the skills `.agents/skills/cq-advance`, `cq-begin`, `cq-review` and `cq-upstream`;
- Pi: the extension `.pi/extensions/cq-host.js` with its `cq-host.json`, and the prompts `.pi/prompts/cq:advance.md`, `cq:begin.md`, `cq:review.md` and `cq:upstream.md`.

`.mcp.json`, `.codex/config.toml`, `.codex/hooks.json` and the drive and park commands are the same. The earlier files do not work with this release. Their instructions tell the session to name a harness when it starts a child, and the host now refuses a `StartChoice` or `Start` that does so: the host starts the models the agent configuration assigns to the role. The dispatch tool also gained `Seats` and the three commands of the Governor's own work (`OpenWorkspace`, `SubmitWorkspace`, `SelfReview`), so the tool list a Pi extension was generated with differs and the extension refuses the host (`CQ tool contracts changed; rerun cq configure pi and restart`). `cq doctor harness` reports the files to regenerate: each generated file whose content differs from what this package generates is listed as failed. `cq configure --replace` rewrites the files this package generates and removes none: a file that an earlier package generated and this one no longer does stays where it is, `cq doctor` does not report it, and it is deleted by hand. The installed release wrote no such file.

An interruption during replacement attempts to restore the previous package. Unverified recovery leaves `STATE/.cq-update-recovery.json`, which the launcher refuses. Inspect its receipt and logs, stop any owned update processes, and restore the matching **previous package and database backup**. Verify their recorded hashes and the database's schema before removing the marker. If a restore of the backup itself failed (`database-rollback.log`), it ran in one transaction, so the database is as the failed SQL left it; the updater has stopped the database, and the backup named in the receipt is the state to restore by hand. Never launch a package against an unverified database. Keep the previous release and `before.dump` together; rollback after subsequent use also discards database writes made since that backup. Automatic pruning is deliberately absent.

Focused updater checks:

```sh
nix develop -c python3 dev/update-local-check.py -v
nix develop -c python3 dev/update-local-check.py --postgres -v
```

The shared replacement contract runs against in-memory and real-directory adapters. The focused check also verifies that the pinned step matches this tree's schema, model and SQL, that the table its SQL creates is the one the schema declares and the schema without it is the one the step starts from, and that a step of another kind or another transition is refused. The optional PostgreSQL case uses a disposable cluster, checks the retained backup and package replacement, verifies refusal on a mismatched schema, and exercises the rollback of a failed replacement. For SQL applied after the backup it checks that an install without it leaves the rows alone, that the receipt names the changed tables, that applying it again changes nothing, and that SQL that fails and a replacement that fails after it each restore the backup. For the pinned step it builds a database of the schema the step starts from with attempts that state no effort, checks that a failed replacement and each of six departures of the SQL from what the step may do (no effort added, no hash recorded, another change to an attempt, a change to another table, another structure of the new table, a setting written) are refused and leave the database as the backup holds it, without the new table, and that the pinned SQL then leaves exactly the expected rows and changes nothing when applied again. A restore that cannot run leaves the marker, the previous package and a stopped, undamaged database. Full native/package gates are operator delivery evidence, not implied by these focused checks.
