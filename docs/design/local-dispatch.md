# Local child dispatch

The supervisor role exposes a private loopback MCP endpoint alongside the scoped domain MCP endpoint. The server owns durable domain state and artifacts; this local host owns subprocesses, workspaces, prompt assembly and publication. All contracts remain in the single mutable `cq.api` 0.1.0 model.

## Parent and child boundaries

The governor receives `GoverningInput`: project identity, check names, process limits and the human request. It is told no models: the host starts the models the project's agent configuration assigns to the role of each child ([units and attempts](#units-and-attempts)). Its local `dispatch` tool provides these basic generated commands:

- `Start`: `AssignedWork` with exact item revisions, guidance revisions, artifact handles, optional prior result handle, claim fence, role/mode, and process limits (startup, heartbeat, termination and retained output; a child has no execution deadline). It names no harness.
- `Status`: owned attempt ID and a wait from zero to 120 seconds. It reads the current state or the result of an attempt; a Governor waits with it where its harness has no cheaper way to learn that work ended (see [Waiting for work](#waiting-for-work)).
- `Cancel`: owned attempt ID. It cancels the whole unit of that attempt. Stop intent is applied immediately, with journal/cancellation work performed independently.
- `Seats`: owned attempt ID. It returns the `UnitSeats` of the attempt's unit: every model the host tried and how each seat ended.

Managed dispatch adds `Select` and `StartChoice` for [adaptive cohorts](cohorts.md). `Revalidate` reruns the failed checks of an admitted worker result ([revalidation](reviewer-checks.md#governor-requested-revalidation)). `PrepareIntegration`, `Integrate`, `IntegrationStatus`, `DiscardIntegration`, `Combine` and `CombinationStatus` provide [reviewed integration and combination](git-integration.md) through the same tool.

There are no prompt/result narrative fields in the dispatch request. Identical request replay returns the same attempt; a changed request using the same ID conflicts. A governing session may run up to four active children at once, provided their member sets are disjoint (each child runs under its own claim). The number of children a session starts over its lifetime is not bounded: an attached session lives as long as its harness session, and each child's records are bounded on their own. Member, guidance and artifact limits remain those of [input materialization](dispatch-input.md). Dispatch start waits at most one second for ticket persistence; a missed acknowledgement disables admission and requests cancellation.

## Units and attempts

One `StartChoice` (or direct `Start`) is one **unit**. The host (`DispatchUnits`) asks the server which models the agent configuration assigns to the role of the work under the governing harness (`AgentsAction.Resolve`), each time a unit starts and never from a copy: a configuration saved during a session applies to the next unit. A route that names no provider takes the provider of the settings entry of its harness. The plan the unit runs is retained as `units/<choice>.json` of the session directory (a `ResolvedAssignment` with the providers filled in). A role that does not resolve fails the start with `Fault.Invalid`, which names the role and the key of the configuration to set; nothing falls back to the settings file. `cq agents init --settings FILE [--save installation|project]` writes a configuration to start from: each harness of the settings file runs its settings model in every tier, the planner, worker and explorer roles run the governing harness, and the reviewer role of each harness is a `fallback` over the other harnesses of the settings file, in its order, with the governing harness last, so a review is a self-review only when the other harnesses abstain. With one harness in the settings file every role runs it, and the command notes that every review is then a self-review.

A unit owns one **attempt** for each candidate it launches: an ordinary child with its own `AttemptId`, `Assignment`, ticket, publication, admission and usage record, whose `DispatchRequest` carries the unit's request ID and the harness of its route. `UnitProgress` decides what is launched: every seat of an `all` panel at once; as many seats of an `any` panel as `min` still needs, in listed order; a seat's next candidate only when one abstains (`fallback`, `rr`), and none after the first under `first`. A candidate abstains when no model ran for a reason that is none of the work's (no settings entry, a launch that failed, a provider refusal of a class the host recognises); everything else is a failure of its seat.

The governing session sees **one status for the unit**, under the ID of the unit's first attempt, which stays its handle whichever candidate delivers. `Status`, `Cancel` and `Seats` accept the ID of any attempt of the unit. While the unit runs, the status is that of a running attempt; an attempt that has ended shows nothing of how it ended until the unit has.

| How the unit ended | Its status |
| --- | --- |
| At least `min` seats delivered, one seat or one delivered review | That attempt's status, as a single child's. |
| Several reviews delivered and they agree | The first delivered review's status; `next` as that review advises. |
| Several reviews delivered and they differ, in a member's verdict or in the next step they advise | The dissenting review's status with the aggregate verdict counts, `next: Arbitrate`, blocker `Reviewers disagree on …: read Seats`. The dissenting review is the first that gave a disputed member its worst verdict, or, when only the advised steps differ, the first that does not advise acceptance. |
| A seat failed and the others met `min` (Q69) | As decided above, with `seat N failed and the other seats decided: FAULT` added to the blocker. |
| Fewer than `min` delivered and a seat failed | The first failed seat's status as that attempt ended (`Failed` with `next: Retry`; `Unknown` and `PublicationPending` keep their own `next`). |
| Fewer than `min` delivered and none failed | Phase `Abstained`, `next: ResolveBlocker`, blocker naming every candidate and reason. |
| Cancelled | The cancelled attempt's status; when the unit was stopped between two candidates, a `Cancelled` status of its own. A cancellation is never an abstention, and nothing is started after it. |

The release of the unit's input runs once, for the unit, before its end is visible: a failed unit publishes its fault and is offered again or, on the same fault twice, stays deferred (D145); an abstained unit is released without a fault and offered again as it was. When the unit ends, its `UnitSeats` are published as a `Panel` artifact of the governing attempt (`NativeArtifacts.id(governing, "unit-" + choice)`).

Units hold disjoint members (D83); the attempts of one unit share them. Every attempt counts against the bound of four active children, and a unit whose first seats do not fit together is refused. A candidate that follows one that ended takes over its slot in the same step, so a later candidate never waits for a slot and a unit is never stalled by another unit's start.

Under a drive the unit is a lineage member as its request, in flight until the unit has ended, and each attempt is a member under it. Every attempt is settled with its own outcome when the unit ends: an abstention is no attempt on the input, a failed seat the others made up for is a plain failure, and the failed seats of a failed unit are retryable when the input is offered again.

## The governing session's own work

In the YOLO process mode an interactive Governor may make a change itself and review a candidate itself ([process modes](workflows.md#process-modes)). Three dispatch commands carry that, and they are in the tool of every mode so that its schema never depends on the mode:

| Command | What the host does | Reply |
| --- | --- | --- |
| `OpenWorkspace { request, members, previous, fence }` | Assembles the input a Worker Implement child of these members would get (current claim and revisions, an Open milestone, `previous` an admitted worker result with a candidate, or a candidate review of one), registers an attempt of the **Governor** role in phase Work under the governing attempt, and prepares a workspace for it: the locked detached worktree a Worker gets, at the candidate of `previous` or at the head of the integration target. No job is started. | Status with phase `Editing`, `next: Submit` and the absolute directory in `workspace`. |
| `SubmitWorkspace { attempt, members }` | Checks `members` against the report contract of a Worker (`ChildContracts.report`); a report that fails it is refused and the workspace stays open. Then, in the background: collects the named evidence, captures the candidate (`CandidateWorkspace.capture`: `HEAD` must still be the base, everything but `.work` is committed by the host), runs every configured check on it, and publishes a `ChildResult` whose `request.work` is `Worker(Implement)`. | Status at once (`Validating`, `next: Wait`); the end is read with `Status`. |
| `SelfReview { request, result, members, fence }` | `result` is an admitted worker result with a candidate, the Governor's or a Worker's (Q60), on which every configured check has passed as its revalidation rounds left it; otherwise the call is refused and nothing is registered. Registers a second Governor attempt, in phase Review, and publishes a `ChildResult` with `request.work = Reviewer(Candidate)`, `previous = result`, the verdicts and the subject's effective validation. | The status of that review, as a reviewer child's: `result` is the handle `PrepareIntegration` takes. |

`Status` and `Cancel` take the attempt as for a child. `Cancel` of an open workspace discards it as work and keeps it on disk ([workspaces](workspaces.md#lifecycle-and-removal)). The same code settles these attempts and a child's (`AttemptSettlement`: claim renewal, capture, checks, publication), so admission, the review by a Reviewer child, integration, revalidation and a correction with `previous` read the result as a candidate like any other. An attempt of the session's own work has no settings entry, no native output and no usage of its own; its outcome carries the gap `No meter: the work was done in the governing session, whose usage is that session's own`.

**Where it is refused.** `AttachedWorkflow` refuses the three commands unless the activation's mode is YOLO, naming the mode. `WorkflowExecution` applies the phase limit and the selection as to the child that would do the work (a workspace as Worker Implement, a review as Reviewer Candidate). `LocalControl` refuses them to a batch Governor in the server's words (Q62). Before anything is registered, and again before a submitted workspace is captured, the host reads the project's mode as it is now and refuses in the server's words when the project has left the YOLO mode; a refused submission leaves the workspace open for `Cancel`. A result the server still denies, because the mode changed while the checks ran, ends its attempt as `Failed` with the denial as its blocker and its outcome's gap: a denial is the server's answer and is not delivered again, by the session, by recovery or by `cq job upload`, while a request the server did not answer stays `PublicationPending`. The server decides in the end: it admits a Governor-role result only in the YOLO mode and for an interactive session, and reserves a self-reviewed integration only with a configured check or the operator's exemption.

**A unit of its own kind.** The session's own work is a unit of `DispatchUnits` with one seat that no agent configuration resolved (`UnitWorker.Governing`), and takes every rule a unit has from there instead of repeating it:

- its members are held as any unit's (D83): no child and no second workspace starts on them, and none of them starts while a child covers them;
- it holds **no child slot**: no process runs for it, so four children may run beside an open workspace and a workspace opens although four children run. The checks of a submitted workspace run as host jobs, like those of a revalidation, and are not counted either;
- it keeps the workflow unsettled (`governor workspace <attempt> (Editing)`), so no other workflow is activated over it, and a result of its members is not revalidated meanwhile;
- `Cancel` and the host's shutdown stop it as they stop a child;
- it publishes no `Panel` artifact and retains no `units/<request>.json`: no model was chosen for it.

**What a waiter is told.** While the workspace is open the Governor itself is working, and nothing must wait for that: the unit's `Started` event is written to `units.jsonl` when the session hands the workspace back (`SubmitWorkspace`) or the unit is stopped, and its `Ended` event if and only if its start was. A self-review ends in the call that makes it and writes neither. From its submission a workspace is work of the host that is not a child: a Claude Code session calls its status once inside the turn and starts the background waiter only if the checks still run, a Codex or batch session waits in the status call, and the Pi extension follows the unit from the reply that shows it `Validating`.

`OpenWorkspace` and `SelfReview` reply once the host has done its part, so a call is allowed the longest wait on top of a request's deadline (`DispatchWaits.millis`). A workspace that is not open within that time is answered with `Conflict` (`The workspace is still being prepared: repeat OpenWorkspace …`); the repetition with the same request waits again and never opens a second one.

**Isolation.** The host guarantees what becomes a candidate: only the content of the workspace directory, captured by the host on the workspace's base, checked by the host on that commit. It does not confine the session: an attached harness is the operator's own process with its own tools, the host cannot see an edit it makes elsewhere, and a status diff of the operator's checkout could not be attributed because the operator may be working there. The instructions of the mode forbid editing anywhere else. [Interactive](../interactive.md#a-workspace-of-the-governors-own) says what each harness needs to work in the directory.

## Waiting for work

Every response of a governing model re-reads its whole context, so a Governor that polls a status while a child runs pays for its context once per poll: in three measured runs, 29–35 % of the tokens read were responses that only asked again (I33). A child is therefore started and then waited for outside the model.

The host appends one event to `units.jsonl` of its session directory when it starts working on a unit and when it stops: a child unit under the ID of its first attempt (one pair of events however many candidates or seats it runs), an integration (each time it is prepared or applied), a combination, a check revalidation. `cq wait [--session DIR] [--attempt ID]… [--integration ID]… [--combination ID]… [--revalidation ID]… [--json]` reads that file alone, with no server and no credential. Without `--session` it waits on the session of the one CQ host of its checkout that runs (exit 5 when several do), found through the records hosts leave in the checkout's CQ directory; this is the command line a Claude Code session is given. Named units: it ends at the first of them that has ended, at once when one already has, so nothing is missed between a start and the wait. No names: it ends at the next end among the units active when it starts, and at once when there are none. It has no timeout of its own; it reads the file again every 250 ms (a local file-stat interval). It exits 3 when the host no longer holds the lock on `journal/owner.lock`, also when that host left nothing unfinished, and 4 when the directory is no session. While it runs it holds a shared lock on `waiters.lock` of the session directory, by which the Stop hook knows that the session will be woken.

Who runs it depends on what the harness can do (probe of 2026-10-05, Claude Code 2.1.285, Codex 0.159.2, Pi 0.99.1):

| Governor | How it waits | Why |
| --- | --- | --- |
| Claude Code, attached | For a child, the model runs `<executable> wait` as a background Bash command with `timeout` 7200000 and continues or ends its turn; the command's exit starts a turn. It then reads each ended unit with one status call. For an integration being prepared or applied, a combination, a revalidation and a workspace it submitted it starts no command: it calls the status once inside its turn with `waitMillis` 120000, and falls back to the command only if the work still runs when the call returns. With a driver on, the Stop hook lets the turn end only while that waiter runs ([driver](driver.md#continuation-query)). | A background command's exit wakes an idle session and steers a busy one. The default background lifetime is 30 minutes and the maximum 2 hours. The notification carries the exit code and an output file, not the output. Work that ends within seconds ends before the turn does: in a real session of 2026-10-06 (Claude Code 2.1.285) all three preparations, of 1–5 s each, had ended when the session stopped, the hook found nothing running, and each stop was answered with a resume directive. |
| Pi, attached | The CQ extension runs `cq wait` itself and injects a `CQ: … ended: …` message with `triggerTurn`. The model starts nothing. | Pi has no background tool; an extension message starts a turn or arrives at the next tool-call boundary. |
| Codex, attached | The model calls `Status`, `IntegrationStatus` or `CombinationStatus` with `waitMillis` 120000 inside its turn and repeats the call while the work continues. It is told to begin an `exec` script that makes the call with `// @exec: {"yield_time_ms": 150000}`. With a driver on, the Stop hook blocks a stop while work runs with the order to make that call. | Nothing wakes an idle Codex session when a background terminal exits ([openai/codex#32188](https://github.com/openai/codex/issues/32188)), so it cannot leave its turn. A shell call cannot hold the turn: `exec_command` and `write_stdin` return after at most 30 s (`MAX_YIELD_TIME_MS` in Codex's unified exec, 0.156.1–0.160.0), and in a real session of 2026-10-06 (0.160.0) a 267 s child cost 22 responses that way. A tool call of an MCP server is allowed `tool_timeout_sec`, which `cq configure` sets. A script of the `exec` tool, through which 0.160.0 made every tool call in that session, is handed back unfinished after 30 s by default (`DEFAULT_CODE_MODE_EXEC_YIELD_TIME_MS`) and is then asked for every 10 s; its first-line pragma and the `wait` tool take a longer time, with no upper limit in the source read. Not observed in a real session. When upstream delivers the wake-up, Codex can wait as Claude Code does. |
| Batch Governor of `cq run` | `Status`, `IntegrationStatus` or `CombinationStatus` with `waitMillis` 120000, repeated while the work continues. | A batch Governor has no shell and nothing tells it; the host-side wait is all it has. |

A status call waits at most 120 s (`DispatchWaits.MaxMillis`). The bound is the idle time after which the providers still served the prompt cache in the measured runs (kept after 146 s, lost by 356 s; I33 analysis of 2026-10-05); the call returns at once when the work ends, so the bound matters only while it runs. The attached host allows a request 30 s and, for a dispatch command that waits, that wait on top; a request that does not wait keeps the 30 s. Each harness is configured to allow the tool call longer than the host does, so that the host's answer or failure arrives first: Codex `tool_timeout_sec = 155` and Claude Code `"timeout": 155000` on the `cq` server of the attached integration, per-request timeouts of the same sizes in the Pi extensions, and 150 s on the local dispatch endpoint of a managed Governor (its other endpoints keep 30 s).

`cq configure claude` approves the command for the session's shell: `Bash(<executable> wait)` in `permissions.allow` of `.claude/settings.local.json`, the exact command line. The rule has no wildcard on purpose: Claude Code's own rule guidance calls prefix wildcards "prefix STRING matches with NO flag-level analysis", and whether a prefix rule can approve a compound command could not be established from the 2.1.285 bundle. Nothing is approved for a Codex shell: a Codex session runs no command to wait, and `cq configure codex` no longer writes `.codex/rules/cq.rules`. Every integration starts the host with `--executable <executable>`, without which a Claude Code or Codex host refuses to start, and the host of a Claude Code session puts that command line into the governing instructions of `session Context`. `cq wait` only reads, and takes a shared lock on a file opened for reading, so a sandbox that lets the session's shell read the state root is enough.

The host resolves input, loads the installed instructions for the assigned role, publishes input/prompt artifacts and launches the configured harness in a detached workspace. Claims are renewed every 20 seconds for three minutes (`ClaimRenewal`). A renewal the server *refuses* — the claim was released, taken over or expired, the fence is stale, or the claim no longer covers the assignment — stops the child at once with `Work claim refresh failed: <fault>`. A renewal the server left *unanswered* (`ServerUnavailable`: connection refused, the 10-second HTTP deadline, a 5xx status) is logged and retried at the next tick, so a server restart does not cancel running children; only when the next tick would leave less than 30 seconds of the lease the host last obtained is the child stopped, with `Work claim refresh failed: Claim renewal unanswered N times over M ms; its lease is about to expire: <cause>`. The same policy covers the checks of an integration preparation and of a revalidation round, which fail with that reason; combination preparation renews once and has no loop. Claim ownership/membership and exact assigned revisions are checked again before result admission. Child limits cannot exceed the governing configuration. Configuration selects every model/provider explicitly and verifies the installed harness version.

Children receive only the local `workspace` capability and their scoped domain read tools. Direct attempts to call local dispatch or mutate ledgers are denied. The workspace tool lists at most 200 entries or reads at most 8,192 Unicode code points. Files are bounded to 256 KiB of strict UTF-8; directories are bounded to 10,000 entries. Absolute paths, parent traversal, Git metadata and symlink traversal are denied. This implements the cooperative-agent misuse boundary; it does not claim adversarial operating-system isolation.

## Candidate and validation evidence

Worker reports are checked against their assigned identities and role. A `CandidateReady` report triggers host Git capture: verify the original worktree/common-directory identity and fixed HEAD, stage the isolated tree, reject submodules, write a commit with the frozen base as parent and atomically create an attempt-specific candidate ref. The commit message names the assigned members with their titles and known producers, carries a `CQ-Attempt` trailer and, for a combined candidate, the source integration in the body and a `CQ-Integration` trailer; the author stays the host identity. A worker that changes HEAD loses admission. Neither the governing checkout nor its index is used for capture.

`SupervisorSettings.checks` contains up to eight named `ValidationCheck` records: `name`, argument-vector `command`, `executionMillis`, `retainedOutputBytes` (the bound of the published stdout/stderr transcripts; a check is not stopped for its output size), `attempts` (1–3) and `revalidations` (0–3). Commands are host configuration, not model-supplied shell strings. Each runs through the guardian in a separate workspace rooted at the candidate. Output manifests and `ValidationObservation` retain the exact command, candidate and process outcome. Unknown cleanup rejects child result admission; ordinary failed checks remain explicit failed validation evidence and direct the parent toward revision. No checks means no host checks were performed.

### Intermittent checks

A check that fails is run again on the same commit, in a fresh workspace, until it passes or has run `attempts` times; `attempts: 1` keeps the single run. Every run publishes its own `ValidationObservation` and output. The check's `ValidationEvidence` names the last run in `artifact` and the failed runs before it in `failures`. A check that passed on a rerun is *intermittent*: its state is `Passed`, it does not block review or integration, `ChildCounts.validationIntermittent` counts it, and its failed runs stay retrievable by handle. A check that fails every run ends `Failed` after exactly `attempts` runs. A run whose cleanup is unconfirmed (`Unknown`) is never repeated, and a stopped child or closed integration admission starts no further run. There is no quarantine or skip list: the bound is the only relief, and a check that needs its reruns is visible in every result that used them.

A failure that outlasts its automatic reruns can still be rerun once more on request: see [governor-requested revalidation](reviewer-checks.md#governor-requested-revalidation).

The same policy applies wherever the host runs a configured check: worker candidates, the checks a candidate reviewer requests (see [reviewer checks](reviewer-checks.md)) and the merged commit of a [host rebase](git-integration.md#host-rebase-onto-an-advanced-target). Integration cites the failed runs of the evidence it relies on in a second host-observed Task evidence entry, after the entry that cites the passing observations; host preparation and server reservation verify that each cited failure is a settled failed run of that check on that commit by the evidence's author.

The full immutable `ChildResult` contains request, candidate/base, structured per-member report and validation handles. A reviewer receives the previous result directly from its handle and reads that candidate through its assigned workspace. Reviewer outcomes remain model declarations; neither an accepted review nor a completed attempt constitutes final semantic acceptance or branch integration.

The parent receives a `DispatchStatus` of at most 12 KiB: status, owned IDs, per-outcome counts, next action, optional 300-code-point blocker, result handle, publication coverage, the child's workspace state and `quietMillis`. `workspace` is absent while no workspace has been prepared for the attempt; once the child publishes it carries the `WorkspaceAdmission` (`Open`, `Quarantined`, `Removed`) and, for a retained `Open` or `Quarantined` workspace, its directory, so a governor can inspect a quarantined tree without reading the session's workspace records. The live status is updated again after publication: a server admission rejection quarantines the workspace, and a `Completed` attempt's workspace is removed at once (see [workspaces](workspaces.md)); the sealed `receipt.json` keeps the state at publication. `quietMillis` is the time since the child's running job last wrote output and is absent otherwise (always in a sealed receipt); the host never stops a child for being quiet, and the governor reports a long-quiet child to the operator instead of cancelling it (see [process guardian](process-guardian.md#deadlines-that-stay-and-deadlines-that-went)). Full successful narratives stay behind the result handle. Explicit bounded artifact reads support necessary semantic drill-down. This bounds dispatch traffic; actual model token efficiency still requires repeated consumer evaluations.

## Delivery and shutdown

Every child registers its frozen assignment and parent-linked attempt in the operational usage audit before launch. A multi-member assignment is shared attribution with a frozen cohort identity. Native collectors and immutable delivery batches use the same mechanism as the governing attempt. `cq job upload --session ...` replays both governing and child queues; it does not launch work. Publication failure with an existing spool returns `PublicationPending`, hides the result handle and requests delivery recovery.

When the governor ends, the host requests child termination and joins normal collection/publication. A supervisor-only watchdog also observes the governor's in-memory guardian state independently of journal persistence. It is acquired before the job resources and disarmed only after their finalizers complete. It has no deadline while the session runs. Governor termination, an owner signal or failure-path finalization begins shutdown and arms a deadline of grace + kill + ten seconds; repeated shutdown cannot extend it.

Expiry forces the supervisor process to exit **75** without waiting for shutdown hooks or blocked I/O. This is an **unresolved shutdown**, not proof of process settlement, durable quarantine or delivered usage. It fences all retained JVM continuations. Guardian control-pipe closure separately starts bounded descendant cleanup; that additional drain is not included in the supervisor-exit claim. Preserve the entire session directory and inspect/reconcile unfinished records before reuse. Any earlier receipt describes the observation at its timestamp and does not override exit 75. Interrupted pre-publication attempts are reconciled by `job upload` with immutable partial evidence, explicit unknown outcomes and quarantine; see [recovery](../validation/m2-recovery.md) and the [operations guide](operations.md).

Reviewed integration/combination, interrupted delivery recovery and real consumer evaluation are implemented and independently reviewed in [M4](../validation/m4-review.md). Recovery does not reconstruct a running governor or resume its dispatch service; the selected lifetime model permits hierarchy termination with its owner. Interactive collection retains the [declared harness limits](../drafts/20260926-usage-observability.md). Packaged live verification and human acceptance remain tracked in [M6](../validation/m6-package.md).
