Workflow execution requires these choices. Forward handles directly; never reconstruct the chosen assignment or child prompt. A selection acquires no claim and creates no child attempt. Read candidate counts and reasons, including unexamined and ineligible work.

An implementation selection may return a Planner choice to assess whether the selected tasks, related or not, can share one candidate. After that child finishes, forward its result in artifacts to another Select for Worker Implement. When it ended without a verdict (it failed, abstained or its result was not admitted), Select Worker Implement again without it: the host treats the group as Unknown and offers each task alone. Unknown/incompatible evidence splits work; claim each new group exactly, releasing an earlier larger claim if necessary. For review, Select with the exact previous result and reviewer mode. Carry earlier larger results as artifact context when selecting a subgroup. A child that failed without an admitted result (its status is Failed with no result and next Retry: malformed output, a report that failed admission, a failed process) has not used up its input: Select the same work again, and the host offers it with that attempt's fault among the choice's artifacts. The assessing Planner above is the exception: it is not offered again, and its tasks are offered alone. The input of a cancelled child stays deferred. A child whose phase is Abstained ran on no model: no assigned model could run the work. Its input is not used up, but do not select it again at once: continue other work and report it with its blocker. When the same fault follows twice in a row the host defers that input. Use substantive new evidence or changed operative input before retrying deferred work. The host loads child instructions and full input/results. Do not compose child prompts, reconstruct proposal drafts or copy full results between roles. Preview stored proposals and apply their handles only after deciding they are appropriate. Use bounded drill-down for a concrete unresolved question.

NoMilestone means a selected Task has no milestone, and ClosedMilestone that its milestone is no longer Open, so Worker Implement and ResolveConflict refuse it. For NoMilestone, link the existing Task to an Open milestone whose objective covers it yourself: change with Reference(Task, PartOf, milestone, present true) and both current revisions, one request per Task because every link revises the milestone. ClosedMilestone has two remedies, and which one applies depends on the drive. Reopen the milestone, by replacing its draft with status Open, when no driver is on or the milestone is a selected member of the drive; its Tasks then stay in the drive. When a driver is on and the milestone is outside the drive, as it is when the drive is rooted at the Task, reassign the Task in two requests: first remove its old PartOf with Reference(Task, PartOf, old milestone, present false), then add PartOf to an Open milestone whose objective covers the Task. One request cannot do both, because a request changes the Task once. A driven session never reopens, replaces or restores a milestone outside the drive: that write is refused as an out-of-set change and stops the drive with Failure. When no Open milestone fits, obtain one in the way the project's process mode prescribes.
